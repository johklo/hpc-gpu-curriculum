운영자가 매일 만지는 것들이다. 노드 상태 점검에서 시작해 사용자 환경, GPU 자원, 모니터링으로
넓힌다. 장애가 났을 때 어디부터 볼지에 대한 순서를 갖는 것이 이 모듈의 쓸모다.

## 아침 점검 순서

밤사이 클러스터가 멀쩡했는지 확인하는 순서다. 위에서 아래로 그대로 따라 하면 된다. 여기서
클러스터(cluster)는 여러 서버를 묶어 하나의 계산 자원처럼 쓰는 묶음이고, 그 안의 서버 한 대가
노드(node)다. 노드에 작업을 나눠 주는 프로그램이 스케줄러(scheduler)이고, 이 클러스터는
스케줄러로 Slurm을 쓴다. 사용자가 제출한 작업이 자원을 기다리며 늘어서는 줄이 대기열(queue)이다.

전체 상태 요약부터 본다.

```bash
sinfo -s                    # 파티션별 idle/alloc/down 노드 수를 한 줄로 요약한다
sinfo -R                    # 빠진 노드와 그 사유. 어제 없던 줄이 생겼는지 본다
squeue --start | head       # 대기 중인 작업과 예상 시작 시각
```

파티션(partition)은 노드를 용도별로 나눈 묶음이다. 학습용 GPU 노드와 디버깅용 노드를 다른
파티션에 둔다. `sinfo -s`에서 down이나 drain 개수가 어제보다 늘었으면 그 노드부터 확인한다.

스토리지와 밤사이 오류를 본다.

```bash
df -h /home /scratch                       # 사용률이 90%를 넘으면 그날 안에 손댄다
dmesg -T | grep -i xid | tail              # 밤사이 GPU 오류가 찍혔는지
journalctl -p err -S "18 hours ago" | tail # 지난밤의 시스템 오류만
```

여기까지 이상이 없으면 대기열이 정상적으로 흐르는지 확인하고 끝낸다. 이상이 있으면 아래의 해당
섹션으로 넘어가 원인을 좁힌다.

## 노드 상태 점검

문제 신고가 들어오면 순서를 정해두고 본다. 부하, 프로세스, 메모리, 디스크, 네트워크 순이다.

```bash
uptime                      # 1·5·15분 부하 평균. 코어 수보다 크면 과부하다
top -b -n1 | head -20       # CPU를 먹는 프로세스 확인
ps aux --sort=-%mem | head  # 메모리를 먹는 프로세스 확인
systemctl --failed          # 실패한 서비스 목록
```

부하 평균은 코어 수와 비교해서 읽는다. 128코어 노드에서 부하 20은 한가한 상태고, 부하 300은
대기열이 쌓였다는 뜻이다. 부하가 높은데 CPU 사용률이 낮으면 I/O 대기를 의심한다. `top`의
`wa` 값이 그 단서다.

Slurm이 보는 상태와 실제 상태가 다를 수 있다. 노드가 `DRAIN`이면 이유부터 확인한다.

![유휴에서 할당으로, 드레인을 거쳐 다시 유휴로 돌아오는 노드 상태 전이](img/node-states.svg)

```bash
sinfo -R                              # 드레인된 노드와 사유를 한 번에 본다
scontrol show node gpu07 | grep -i reason
scontrol update NodeName=gpu07 State=RESUME   # 원인을 고친 뒤 복귀시킨다
```

## 노드 상태값의 의미

Slurm이 노드에 붙이는 상태값(state)이 무슨 뜻인지 알아야 `sinfo` 출력을 읽는다.

| 상태 | 뜻 | 어떻게 그 상태가 되는가 |
| --- | --- | --- |
| `idle` | 비어 있고 작업을 받을 수 있다 | 작업이 없거나 방금 끝났다 |
| `alloc` | 노드 전체가 작업에 배정됐다 | 한 작업이 노드의 모든 자원을 잡았다 |
| `mix` | 자원 일부만 배정됐다 | GPU 8장 중 몇 장만 쓰는 작업이 있다 |
| `drain` | 새 작업을 받지 않는다 | 운영자가 뺐거나 헬스체크가 실패했다 |
| `down` | 스케줄러가 노드와 통신하지 못한다 | slurmd가 죽었거나 노드가 꺼졌거나 링크가 끊겼다 |
| `fail` | 곧 죽을 노드로 표시됐다 | 하드웨어 경고를 받았거나 관리자가 수동 표시했다 |

`drain`과 `down`은 다르다. `drain`은 운영자가 의도적으로 뺀 상태라 돌던 작업은 끝까지 돈다.
`down`은 스케줄러가 노드를 잃은 상태라 그 위의 작업도 함께 실패한다. `down`이 뜨면 노드가 켜져
있는지, `slurmd`가 살아 있는지, 관리 네트워크가 붙어 있는지 순서로 확인한다.

```bash
scontrol show node gpu07 | grep -iE "State|Reason"
ssh gpu07 systemctl status slurmd     # 노드에 붙는지, 데몬이 사는지 함께 본다
```

## 장애 신고 분류

신고를 받자마자 노드에 들어가는 대신 범위부터 가른다. 무엇을 묻느냐가 조사 시간을 좌우한다.

| 질문 | 왜 묻는가 |
| --- | --- |
| 언제부터인가 | 최근 변경이나 특정 시각의 사건과 맞춰 본다 |
| 작업 ID가 무엇인가 | `sacct`로 종료 코드와 자원 사용량을 바로 본다 |
| 한 노드인가 여러 노드인가 | 한 대면 하드웨어, 여럿이면 공용 요소를 의심한다 |
| 다시 돌리면 또 그런가 | 재현되면 조사가 쉽고, 아니면 그 순간 지표를 찾는다 |
| 본인만 그런가 다른 사람도 그런가 | 사용자 코드 문제와 클러스터 문제를 가른다 |

한 노드에서만 나는 문제는 그 노드의 하드웨어나 버전을 보고, 여러 노드에서 동시에 나는 문제는
공유 스토리지, 네트워크, 스케줄러, 드라이버 배포처럼 여럿이 함께 쓰는 요소를 본다. 한 사용자에게만
재현되면 그 작업 스크립트와 환경을 본다.

되묻는 질문은 정해두고 순서대로 던진다. 즉흥으로 물으면 빠뜨린다.

- **작업 번호.** `sacct -j <번호>`로 종료 코드와 자원 사용량이 바로 나온다. 번호 없이 "느리다"만
  으로는 조사가 길어진다.
- **언제부터인가.** 오늘부터인지 원래 그랬는지에 따라 볼 곳이 다르다. 특정 시각부터면 그 시각의
  변경 이력과 맞춰 본다.
- **이전에는 되던 것인가.** 한 번이라도 됐다면 환경 차이이고, 처음부터 안 됐다면 요청이나 코드
  문제다.
- **바뀐 것이 있는가.** 코드, 데이터 경로, 모듈 버전, 노드 중 무엇을 바꿨는지 물어 범위를 좁힌다.

사용자 문제와 시스템 문제를 가르는 첫 확인은 세 가지다. 같은 작업이 다른 노드에서도 실패하는지,
다른 사용자도 같은 증상인지, 최소 예제로도 재현되는지다. 셋 다 그렇다면 클러스터 쪽을 보고, 이
사용자와 이 코드에서만 나면 작업 쪽을 본다.

에스컬레이션은 기준을 정해 둔다. 애매할 때 판단이 흔들리지 않게 표로 고정한다.

| 상황 | 대응 | 넘기는 곳 |
| --- | --- | --- |
| 한 작업만 실패, 재현됨 | 운영자가 로그로 조사 | 담당 운영자 |
| 한 노드 하드웨어 의심 | 드레인 후 진단 | 하드웨어 담당 |
| 여러 노드 동시 장애 | 공용 요소부터 차단 | 인프라 팀, 즉시 |
| 데이터 유실·보안 의심 | 작업 중단하고 상태 보존 | 책임자, 즉시 |

## 메모리와 스토리지

메모리는 `free`의 `available` 열만 보면 된다. `free` 열은 캐시를 제외한 값이라 낮게 보이는
것이 정상이다.

```bash
free -g                     # available 열을 본다
vmstat 1 5                  # si/so가 0이 아니면 스왑이 일어나는 중이다
df -h /home /scratch        # 사용률과 남은 용량
df -i /home                 # inode 고갈. 작은 파일이 많으면 용량보다 먼저 찬다
du -sh /scratch/* | sort -h # 누가 얼마나 쓰는지
```

공유 스토리지에서 자주 겪는 문제는 용량이 아니라 inode 고갈과 메타데이터 부하다. 학습 데이터를
작은 파일 수백만 개로 두면 용량은 남아도 파일시스템이 느려진다. 이런 데이터는 묶음 포맷으로
바꾸는 편이 낫다.

쿼터(quota)는 사용자나 그룹이 쓸 수 있는 용량과 파일 수의 상한이다. 상한이 없으면 한 사람이
파일시스템을 가득 채워 모두가 멈춘다. 홈은 작게, 스크래치는 크게 잡는 것이 보통이다. 예를 들어
`/home`은 사용자당 50GB에 파일 100만 개, `/scratch`는 그룹당 20TB에 파일 500만 개처럼 둔다.

```bash
lfs quota -u alice /scratch          # Lustre에서 사용자 쿼터와 현재 사용량
xfs_quota -x -c 'report -h' /home    # XFS 프로젝트 쿼터
```

스크래치는 백업하지 않는 임시 공간이라 오래된 파일을 자동으로 지운다. 30일 이상 손대지 않은
파일을 정리한다는 정책을 미리 공지하고, 지우기 전에 목록을 사용자에게 보낸다. 쿼터에 걸린
사용자는 작업이 조용히 실패하므로, 90퍼센트 도달 시 경고 메일을 보내면 문의가 준다.

I/O가 의심되면 장치별로 확인한다.

```bash
iostat -x 1 5               # %util이 100에 가까우면 포화 상태다
iotop -oPa                  # 실제로 I/O를 일으키는 프로세스
```

## 사용자와 실행 환경

계정은 보통 LDAP이나 AD로 중앙에서 관리한다. 노드마다 로컬 계정을 만들면 UID가 어긋나 공유
스토리지의 파일 소유권이 깨진다.

소프트웨어는 환경 모듈로 제공한다. 같은 라이브러리의 여러 버전을 충돌 없이 두기 위해서다.

```bash
module avail                # 설치된 모듈 목록
module load cuda/12.4 nccl/2.21
module list                 # 현재 적재된 모듈
module purge                # 전부 내린다. 작업 스크립트 첫 줄에 두면 재현성이 올라간다
```

작업 스크립트에서 `module purge`로 시작해 필요한 것만 적재하면 사용자의 셸 설정에 영향받지
않는다. 재현이 안 되는 작업을 조사할 때 이 부분을 먼저 본다.

모듈 파일은 공유 스토리지의 한 경로에 두고 모든 노드가 같은 것을 읽게 한다. 예를 들어
`/apps/modulefiles`를 `MODULEPATH`에 넣어 두면 노드마다 따로 설치할 필요가 없다. 새 버전을
올릴 때는 기존 버전을 지우지 않고 나란히 둔다. `cuda/12.4`를 쓰던 작업이 어느 날 갑자기
`cuda/12.6`으로 바뀌면 재현이 깨지기 때문이다. 최소 두 세대, 보통은 마지막 세 개 버전을
유지하고, 더 오래된 것은 공지 후 3개월 뒤에 내린다.

컨테이너(container)는 애플리케이션과 라이브러리를 한 이미지로 묶어 어느 노드에서 실행해도 같은
환경을 보장하는 방식이다. HPC에서는 루트 권한 없이 도는 Apptainer(예전 이름 Singularity)를 주로
쓴다. 이미지는 사용자마다 받게 두지 말고 공유 캐시에 미리 받아 둔다.

```bash
apptainer pull /apps/images/pytorch_24.05.sif docker://nvcr.io/nvidia/pytorch:24.05-py3
srun --gres=gpu:1 apptainer exec --nv /apps/images/pytorch_24.05.sif python train.py
```

`--nv` 옵션이 호스트의 GPU 드라이버를 컨테이너 안으로 넣어 준다. 이미지 하나가 보통 5~15GB라,
500명이 각자 받으면 스토리지와 레지스트리 대역폭이 함께 터진다. 공용 이미지 몇 개를 관리자가
받아 두고 경로를 안내하는 편이 낫다.

## 로그와 1차 분류

로그는 세 군데를 본다. 커널, 시스템 데몬, 애플리케이션이다.

```bash
dmesg -T | tail -50                    # 커널. OOM, 하드웨어 오류, Xid가 여기 남는다
journalctl -u slurmd -n 100 --no-pager # 특정 서비스
journalctl -p err -S "1 hour ago"      # 최근 한 시간의 오류만
```

`dmesg`에서 `Out of memory: Killed process`가 보이면 커널이 프로세스를 죽인 것이다. 작업이
아무 메시지 없이 사라졌다는 신고의 상당수가 여기에 해당한다. `Xid`로 시작하는 줄이 보이면 GPU
문제이고, 모듈 08에서 이어 본다.

작업 단위로는 Slurm의 기록을 본다.

```bash
sacct -j 12345 --format=JobID,State,ExitCode,MaxRSS,Elapsed
```

`ExitCode`가 `0:9`면 SIGKILL, `0:15`면 SIGTERM이다. 시간 초과로 스케줄러가 죽인 경우
`State`가 `TIMEOUT`으로 남는다. `MaxRSS`가 요청한 메모리에 근접했다면 메모리 부족을 의심한다.

로그를 볼 때 시각을 맞추는 것이 중요하다. `dmesg`는 기본적으로 부팅 후 경과 시간을 찍으므로
`-T`를 붙여 실제 시각으로 바꿔야 다른 로그와 나란히 놓을 수 있다. 노드마다 시간이 어긋나 있으면
인과가 뒤집혀 보이므로 시간 동기화부터 확인한다.

```bash
timedatectl status | grep -E "synchronized|NTP"
chronyc tracking | head -3            # 기준 서버와의 오차
```

어느 로그에서 무엇이 나오는지 알아 두면 찾는 시간이 준다.

| 증상 | 볼 곳 | 찾을 문자열 |
| --- | --- | --- |
| 작업이 조용히 사라졌다 | `dmesg -T` | `Out of memory`, `Killed process` |
| GPU가 사라졌다 | `dmesg -T` | `NVRM: Xid`, `GPU has fallen off the bus` |
| 노드가 대기열에서 빠졌다 | `journalctl -u slurmd` | `error`, `Node ... not responding` |
| 작업이 시작되지 않는다 | `journalctl -u slurmctld` | `job_id`, `Requeue` |
| 파일 접근이 실패한다 | `dmesg -T` | `Lustre`, `evicted`, `nfs: server` |
| 네트워크가 끊긴다 | `dmesg -T` | `link is down`, `mlx5_core` |

여러 노드에 걸친 문제는 한 대만 봐서는 모른다. 같은 시각의 로그를 여러 노드에서 한 번에 모아
비교하면 공통 원인이 드러난다. 노드마다 다른 메시지가 나온다면 노드 개별 문제이고, 같은 시각에
같은 메시지가 나온다면 공통 설비를 의심한다.

```bash
# 문제가 난 노드들에서 같은 구간의 커널 로그를 한꺼번에 모은다
pdsh -w gpu[07-18] 'dmesg -T | grep -i -E "xid|error|down" | tail -5' | sort

# 스위치나 스토리지처럼 공통 설비가 원인이면 시각이 겹친다
pdsh -w gpu[07-18] 'journalctl -p err -S "02:00" -U "03:00" --no-pager | head -3' | dshbak -c
```

로그를 오래 남기는 것도 준비의 일부다. 기본 설정에서는 재부팅하면 커널 로그가 사라지므로,
장애 직후에 노드를 재부팅하면 증거가 함께 없어진다. `journald`를 디스크에 저장하도록 두고
보존 용량을 정해 둔다.

```bash
# /etc/systemd/journald.conf
# Storage=persistent
# SystemMaxUse=2G
journalctl --disk-usage
journalctl --list-boots | head           # 지난 부팅의 로그가 남아 있는지
```

## GPU 자원 관리

GPU 상태는 `nvidia-smi`로 본다. 사람이 읽는 화면보다 질의 형식이 자동화에 편하다.

```bash
nvidia-smi
nvidia-smi --query-gpu=index,name,memory.used,memory.total,utilization.gpu,temperature.gpu \
           --format=csv,noheader
nvidia-smi topo -m          # GPU 사이 연결 형태. NVLink 여부를 확인한다
```

사용률이 낮은데 학습이 느리면 GPU가 아니라 데이터 로더나 통신이 병목이다. 사용률과 메모리를
같이 보고 판단한다.

한 장을 여러 작업이 나눠 쓰게 하려면 분할 방식을 골라야 한다.

| 방식 | 격리 수준 | 쓰임 |
| --- | --- | --- |
| MIG | 하드웨어 분할. 메모리와 연산이 완전히 격리된다 | 추론 서비스, 다중 사용자 공유 |
| MPS | 프로세스 공유. 격리는 약하다 | 작은 커널을 많이 띄우는 워크로드 |
| 시분할 | 스케줄러가 번갈아 배정한다 | 개발과 실험 환경 |

Slurm에서는 GPU를 GRES로 다룬다. `--gres=gpu:2`처럼 요청하면 `CUDA_VISIBLE_DEVICES`가 자동으로
설정되어 다른 GPU가 보이지 않는다. 사용자가 이 변수를 직접 덮어쓰면 격리가 깨지므로 작업
스크립트에서 손대지 않게 안내한다.

## 모니터링

노드에 들어가서 보는 방식은 노드가 늘면 유지되지 않는다. 지표를 모아두고 대시보드로 본다.

수집기가 노드에서 지표를 뽑고, 시계열 DB가 저장하고, 대시보드가 보여준다.

![노드의 수집기가 지표를 내보내면 시계열 DB가 저장하고 대시보드와 경보로 나뉜다](img/monitoring-stack.svg) GPU 지표는 DCGM
Exporter가 맡는다.

| 지표 | 무엇을 알려주는가 |
| --- | --- |
| `DCGM_FI_DEV_GPU_UTIL` | GPU 사용률. 낮으면 병목이 GPU 밖에 있다 |
| `DCGM_FI_DEV_FB_USED` | GPU 메모리 사용량. OOM 예측에 쓴다 |
| `DCGM_FI_DEV_GPU_TEMP` | 온도. 스로틀링 판단의 근거다 |
| `DCGM_FI_DEV_POWER_USAGE` | 전력. 랙 단위 용량 계획에 쓴다 |
| `DCGM_FI_DEV_XID_ERRORS` | Xid 발생. 장애의 조기 신호다 |

무엇을 하나의 단위로 볼지도 정해야 한다. 노드 단위 지표만 있으면 "이 학습이 지금 잘 돌고
있는가"에 답하지 못한다. 클러스터에는 여러 층의 단위가 있고, 질문에 따라 보는 층이 다르다.

| 단위 | 답하는 질문 |
| --- | --- |
| GPU | 이 카드가 정상인가, 스로틀에 걸렸는가 |
| 노드 | 이 서버를 대기열에 넣어도 되는가 |
| 작업 | 이 학습이 자원을 제대로 쓰고 있는가 |
| 프로젝트나 팀 | 이 팀이 배정받은 몫을 얼마나 쓰는가 |
| 클러스터 | 지금 자원을 더 사야 하는가 |

같은 지표를 층마다 다르게 묶는다. GPU 사용률을 작업 단위로 모으면 그 학습의 효율이 되고,
팀 단위로 모으면 배정의 근거가 된다. 수집은 한 번 하고 집계를 여러 갈래로 두는 편이 단순하다.

경보는 적게 만든다. 사람이 즉시 행동해야 하는 것만 경보로 두고, 나머지는 대시보드에 둔다.
노드 다운, Xid 발생, 스토리지 사용률 90퍼센트 정도면 시작으로 충분하다.

## 네트워크 상태 점검

노드는 살아 있는데 작업만 느린 경우, 네트워크가 원인일 때가 많다. 링크 상태와 오류 카운터를
함께 본다.

```bash
ip -s link show eth0        # RX/TX errors, dropped 가 늘고 있는지
ethtool eth0 | grep -E "Speed|Duplex|Link detected"
ethtool -S eth0 | grep -iE "error|drop|discard"
```

`Speed`가 기대보다 낮으면 케이블이나 트랜시버, 스위치 포트 설정을 본다. 10G 포트가 1G로
협상되는 일이 드물지 않고, 이 상태로도 통신 자체는 되기 때문에 알아채기까지 시간이 걸린다.

노드 사이 실제 성능은 직접 재는 편이 빠르다.

```bash
# 한쪽에서 서버로 띄우고
iperf3 -s
# 다른 쪽에서 잰다
iperf3 -c gpu02 -P 4 -t 20
```

InfiniBand 구간은 `ib_write_bw`로 따로 잰다. 이더넷 수치가 정상이어도 IB 링크가 죽어 있으면
분산 학습만 느려진다.

InfiniBand 포트는 이더넷과 명령이 다르다. 포트 상태와 오류 카운터를 함께 본다.

```bash
ibstat                              # 포트가 Active/LinkUp 인지, Rate 가 규격대로인지
perfquery                           # 포트 오류 카운터. Symbol/Link 오류가 늘고 있는지
ibdiagnet                           # 팹 전체를 훑어 링크 오류와 속도 불일치를 모은다
```

`ibstat`의 `State`가 `Active`가 아니면 링크가 안 붙은 것이고, `Rate`가 규격보다 낮으면 협상에
실패한 것이다. NDR 400G 포트가 HDR 200G로 붙는 식의 절반 협상이 케이블이나 트랜시버 문제의
전형적 증상이다. 트랜시버를 재장착하거나 케이블을 바꿔 다시 협상시킨다.

`perfquery`의 `SymbolErrorCounter`나 `LinkErrorRecoveryCounter`가 시간에 따라 늘면 물리 계층이
약해지는 신호다. 카운터를 초기화하고 일정 시간 뒤 다시 재서 증가분을 본다.

```bash
perfquery -R                        # 카운터 초기화
sleep 300
perfquery                           # 5분 동안의 증가분
```

`ibdiagnet`은 팹 전체에서 속도가 낮게 붙은 링크와 오류가 쌓이는 링크를 한 번에 표시한다. 특정
포트만 반복해서 걸리면 그 포트의 케이블과 트랜시버를 교체 후보로 둔다. 케이블을 바꿔도 같은
슬롯에서 재발하면 카드나 스위치 포트를 본다.

## 작업 실패의 흔한 원인

같은 신고가 반복되면 원인도 대개 몇 가지로 좁혀진다.

| 증상 | 확인할 곳 | 대개의 원인 |
| --- | --- | --- |
| 아무 로그 없이 사라짐 | `dmesg`의 OOM 메시지 | 메모리 부족으로 커널이 죽였다 |
| `CUDA out of memory` | 배치 크기, 다른 프로세스 점유 | GPU 메모리 부족 |
| 시작하자마자 종료 | 스크립트의 경로와 모듈 | 공유 스토리지 미마운트, 모듈 미적재 |
| 특정 노드에서만 실패 | `dcgmi diag`, 드라이버 버전 | 그 노드의 하드웨어나 버전 불일치 |
| 무한 대기 | `squeue`의 REASON | 자원 부족이거나 정책 한도 |
| 통신 초기화 실패 | `NCCL_DEBUG=INFO` 로그 | 방화벽, 인터페이스 선택 오류 |

메모리 부족은 요청량을 늘리기 전에 실제 사용량을 먼저 본다. `sacct`의 `MaxRSS`가 요청량의
절반도 안 되는데 죽었다면 다른 원인이다.

```bash
sacct -j 12345 --format=JobID,JobName,State,ExitCode,MaxRSS,MaxVMSize,Elapsed
```

원인별로 로그에 남는 문자열과 확인 명령, 조치를 함께 두면 조사가 빨라진다.

| 원인 | 로그에 남는 문자열 | 확인 명령 | 조치 |
| --- | --- | --- | --- |
| 호스트 OOM | `Out of memory: Killed process` | `dmesg -T \| grep -i oom` | 요청 메모리를 늘리거나 배치를 줄인다 |
| GPU OOM | `CUDA out of memory` | 작업 로그, `nvidia-smi` | 배치 크기·해상도를 줄인다 |
| 시간 초과 | `DUE TO TIME LIMIT` | `sacct -j <번호>` State=TIMEOUT | `--time`을 늘리거나 체크포인트를 쓴다 |
| 노드 장애 | `NODE_FAIL` | `sinfo -R`, `dmesg` | 노드 드레인 후 진단 |
| 파일시스템 오류 | `Input/output error`, `Stale file handle` | `dmesg`, `mount` | 마운트와 스토리지 서버를 본다 |
| 권한 문제 | `Permission denied` | `ls -l`, `id` | 경로 소유권과 그룹을 맞춘다 |
| 이미지 문제 | `FATAL: could not open image` | `apptainer inspect` | 이미지 경로와 권한을 확인한다 |
| 포트 충돌 | `Address already in use` | `ss -tlnp` | 통신 포트를 바꾸거나 남은 프로세스를 정리한다 |

호스트 OOM과 GPU OOM은 자주 헷갈린다. 호스트 OOM은 커널이 `dmesg`에 남기고 프로세스가 아무
메시지 없이 사라지며, GPU OOM은 프레임워크가 `CUDA out of memory`를 출력하고 스택 추적을 남긴다.
남는 곳이 다르므로 둘을 가른 뒤 조치한다. 노드 장애로 죽은 작업은 사용자 잘못이 아니라, 자동
재시도(`--requeue`)를 켜 두면 성한 노드에서 다시 돌아 문의가 준다.

## 노드를 대기열에서 빼고 넣기

점검이나 수리를 하려면 그 노드에 새 작업이 들어가지 않게 막아야 한다. 실행 중인 작업을 죽이지
않고 비우는 절차가 있다.

```bash
# 새 작업만 막는다. 돌던 작업은 끝까지 돈다
scontrol update NodeName=gpu07 State=DRAIN Reason="dcgm diag 예정 $(date +%F)"

# 비었는지 확인한다
squeue -w gpu07

# 점검이 끝나면 되돌린다
scontrol update NodeName=gpu07 State=RESUME
```

`Reason`은 반드시 적는다. 며칠 뒤 드레인된 노드 목록을 봤을 때 왜 뺐는지 모르면 되돌릴 수도
없고 방치된다. 날짜와 담당자를 함께 넣는 편이 낫다.

```bash
sinfo -R --format="%50E %12U %19H %N"    # 사유, 사용자, 시각, 노드
```

여러 노드를 다룰 때는 범위 표기를 쓴다. 범위를 잘못 적어 전체 노드를 드레인하는 사고가 실제로
일어나므로, 실행 전에 대상을 먼저 출력해 확인한다.

```bash
scontrol show hostnames gpu[01-04]        # 무엇이 대상인지 먼저 본다
scontrol update NodeName=gpu[01-04] State=DRAIN Reason="펌웨어 교체"
```

## 용량을 언제 늘릴 것인가

노드를 더 사자는 판단은 느낌이 아니라 몇 가지 수치로 한다.

| 신호 | 무엇을 뜻하는가 |
| --- | --- |
| 대기 시간 중앙값이 오르는 추세 | 수요가 공급을 넘기 시작했다 |
| 할당률이 지속적으로 90% 이상 | 여유가 없다. 장애 하나에 대기열이 밀린다 |
| GPU 사용률은 낮은데 대기가 길다 | 자원이 아니라 파편화나 정책 문제다 |
| 특정 파티션만 밀린다 | 전체가 아니라 그 구역만 조정하면 된다 |

세 번째 신호가 중요하다. 할당률이 높은데 실제 GPU 사용률이 낮으면 노드를 사도 같은 일이
반복된다. 이때는 자원을 잡아만 두는 작업을 찾는 편이 빠르다. 모듈 06의 활용률 항목과 함께 본다.

```bash
sreport cluster Utilization Start=2026-07-01 End=2026-08-01
sreport user TopUsage Start=2026-07-01 End=2026-08-01 TopCount=10
```

증설 판단에 쓰는 지표는 임계값과 함께 둔다. 값 하나가 아니라 며칠 이상 이어지는 추세로 본다.

| 지표 | 임계값 예 | 뜻 |
| --- | --- | --- |
| 대기 시간 90분위 | 며칠 이상 24시간 초과 | 짧은 작업도 오래 기다린다 |
| 할당률 | 2주 평균 90퍼센트 이상 | 여유가 없다 |
| 거절된 요청 | 자원 부족 제출 실패가 증가 | 큰 작업이 아예 못 들어온다 |
| 특정 자원만 부족 | GPU는 남는데 CPU·메모리가 먼저 참 | 노드 종류가 안 맞는다 |

증설 전에 병목이 GPU인지부터 가른다. GPU는 남는데 CPU나 메모리, 스토리지가 먼저 차서 GPU를 못
잡는 경우가 있다. 이때는 GPU 노드를 더 사도 소용이 없고, CPU·메모리 비율이 다른 노드를 넣거나
요청 기본값을 조정하는 편이 맞다.

```bash
sacct -a -S 2026-07-01 --format=ReqCPUS,ReqMem,AllocGRES,Elapsed -X | head
sdiag                                # 스케줄러가 무엇 때문에 작업을 대기시키는지
```

증설이 답이 아닌 경우도 많다. 할당률은 높은데 사용률이 낮으면 자원을 잡아만 두는 작업이
원인이라, 우선순위·선점·최대 보유 시간 같은 정책으로 푸는 편이 빠르다. 특정 파티션만 밀리면
파티션 경계를 조정하거나 백필을 손본다. 새 노드는 도입까지 몇 주가 걸리므로, 정책으로 풀 수
있는지부터 확인한 뒤 결정한다.

## 사용자 문의를 줄이는 것들

같은 질문이 반복되면 문서나 기본값을 고칠 신호다. 문의 유형별로 대응이 다르다.

| 문의 | 대개의 원인 | 근본 대응 |
| --- | --- | --- |
| 작업이 안 돈다 | 요청이 노드 사양보다 크다 | 제출 예시와 노드 사양을 문서에 명시 |
| 어제는 됐는데 오늘 안 된다 | 환경 차이 | 작업 스크립트에 `module purge` 를 표준으로 |
| 갑자기 느려졌다 | 공유 스토리지 경합이나 노드 문제 | 대시보드를 사용자에게 열어 준다 |
| 내 차례가 언제인가 | 대기열 정책을 모른다 | `squeue --start` 안내와 정책 문서화 |

사용자가 스스로 확인할 수 있는 통로를 만들어 두면 문의가 줄고 조사도 빨라진다. 작업 상태와
노드 상태, 대기열 현황을 보여주는 대시보드 하나면 대부분 해결된다.

문서로 미리 막을 수 있는 것과 기본값으로 막을 수 있는 것을 구분한다. 문서는 읽지 않는 사람이
늘 있으므로, 자주 틀리는 값은 아예 기본값을 안전하게 잡아 둔다. 작업 제출 템플릿을 만들어
배포하면 사용자가 빈 스크립트를 처음부터 쓰지 않아도 된다.

```bash
#!/bin/bash
#SBATCH --job-name=train
#SBATCH --partition=gpu
#SBATCH --gres=gpu:1
#SBATCH --cpus-per-task=8
#SBATCH --mem=64G
#SBATCH --time=24:00:00
module purge
module load cuda/12.4 nccl/2.21
srun python train.py
```

이 템플릿 하나가 "GPU를 요청했는데 안 잡힌다", "메모리가 부족하다", "어제는 됐는데 오늘 안
된다" 같은 문의의 상당수를 없앤다. 여기에 자주 나오는 오류와 해결을 정리한 짧은 FAQ, 신규
사용자용 온보딩 문서, 상태를 스스로 보는 대시보드를 더하면 반복 문의가 눈에 띄게 준다. 문의가
들어올 때마다 그 원인을 문서나 기본값에 반영하면, 같은 질문이 두 번 오지 않는다.

## 정기 점검 항목

사람이 기억해서 돌리는 점검은 언젠가 빠진다. 주기를 정해 자동으로 돌리고 결과만 확인한다.

| 주기 | 항목 |
| --- | --- |
| 매시 | 노드 상태, 드레인된 노드 수, 스토리지 사용률 |
| 매일 | GPU 빠른 진단, ECC 카운터 증가분, 드라이버 버전 일치 |
| 매주 | 대기열 통계, 계정별 사용량, 백필 효과 |
| 매월 | 펌웨어와 드라이버 점검, 예비 부품 재고, 용량 추이 |

노드가 대기열에 들어가기 전에 통과해야 할 조건을 정해두면 문제 노드가 조용히 섞여 드는 것을
막을 수 있다. GPU 개수, 드라이버 버전, 마운트 상태, 빠른 진단 통과 정도면 시작으로 충분하다.

점검을 자동으로 돌리되 결과를 사람이 볼 수 있는 곳에 남긴다. 통과하면 조용하고 실패할 때만
알리는 방식이 쌓이지 않는다. 매시·매일 점검은 스케줄러의 배치 작업이나 cron으로 돌리고, 결과를
모니터링 시스템의 지표로 내보내 대시보드에서 추세를 본다.

```bash
# 노드가 대기열에 들어가기 전 통과 조건을 한 스크립트로 묶는다
gpu_count=$(nvidia-smi -L | wc -l)
[ "$gpu_count" -eq 8 ] || { echo "GPU 수 불일치: $gpu_count"; exit 1; }
nvidia-smi >/dev/null || { echo "드라이버 응답 없음"; exit 1; }
mountpoint -q /scratch || { echo "scratch 미마운트"; exit 1; }
dcgmi diag -r 1 >/dev/null || { echo "빠른 진단 실패"; exit 1; }
```

이 검사를 노드 부팅 후와 대기열 복귀 전에 돌리면, 마운트가 빠졌거나 GPU 한 장이 사라진 노드가
작업을 받는 사고를 막는다. 검사 항목은 장애를 겪을 때마다 늘린다. 한 번 사고가 난 원인은
다음부터 자동으로 걸러지도록 조건을 추가하는 편이 낫다. 매월 점검에는 펌웨어와 드라이버 버전을
전 노드에서 모아 비교하는 항목을 넣어, 한두 대만 뒤처진 상태를 찾아낸다.
