노드 한 대에 코어가 128개 있어도 프로그램이 저절로 128배 빨라지지는 않는다. 어디까지 나눌 수
있고 어디서 막히는지, 스레드를 어느 코어에 붙여야 하는지를 본다.

## 병렬화의 상한

프로그램에서 병렬로 돌릴 수 없는 구간이 조금이라도 있으면 전체 속도는 그 구간에 묶인다.
95퍼센트를 완벽히 병렬화해도 나머지 5퍼센트 때문에 최대 20배에서 멈춘다. 코어를 1000개
주더라도 마찬가지다.

| 병렬 가능 비율 | 코어 16개 | 코어 64개 | 코어 무한 |
| --- | ---: | ---: | ---: |
| 50% | 1.8배 | 2.0배 | 2배 |
| 90% | 6.4배 | 8.8배 | 10배 |
| 95% | 9.1배 | 15.4배 | 20배 |
| 99% | 13.9배 | 39.3배 | 100배 |

![병렬 가능 비율이 99퍼센트여도 코어 32개에서 24배에 그친다](img/scaling.svg)

여기서 나오는 결론은 두 가지다. 코어를 늘리기 전에 순차 구간을 먼저 줄여야 하고, 코어 수를
두 배로 늘렸을 때 성능이 두 배가 되지 않는 것은 정상이라는 점이다.

문제 크기를 함께 키우면 사정이 달라진다. 코어를 늘린 만큼 데이터도 늘리는 경우를 약한 확장이라
하고, 이쪽은 훨씬 잘 늘어난다. 대규모 학습에서 GPU를 늘리며 배치 크기를 함께 키우는 방식이
여기 해당한다.

코어를 두 배로 늘려도 두 배가 안 되는 이유는 병렬로 못 나누는 구간이 그대로 남기 때문이다. 이
직렬 구간은 눈에 잘 안 띄는 곳에 숨어 있다. 파일을 읽고 쓰는 입출력, 스레드를 띄우기 전의
메모리 할당, 각 스레드가 계산한 값을 하나로 합치는 취합, 공유 자료를 지키는 잠금이 대표적이다.
코어를 늘리면 병렬 구간의 시간만 줄고 이 직렬 구간의 시간은 그대로여서, 전체에서 직렬이
차지하는 비중이 점점 커진다.

확장이 어디서 꺾이는지는 재봐야 안다. 코어 수를 1, 2, 4, 8로 두 배씩 올리며 같은 입력으로
시간을 재고, 코어를 두 배로 했을 때 시간이 절반 가까이 주는 구간까지가 잘 늘어나는 범위다.
어느 지점부터 시간이 덜 줄거나 오히려 늘면 거기가 상한이고, 그 너머로 코어를 더 요청하면
클러스터 점유만 늘고 이득이 없다.

강한 확장과 약한 확장은 재는 목적이 다르다. 강한 확장은 문제 크기를 고정한 채 코어만 늘려 같은
일을 얼마나 빨리 끝내는지 본다. 정해진 데이터셋의 전처리를 앞당기려는 경우가 여기 해당하고,
암달의 법칙이 상한을 정한다. 약한 확장은 코어당 일감을 고정한 채 코어와 문제를 함께 늘려, 더
큰 문제를 같은 시간에 푸는지 본다. 노드를 늘리며 배치와 모델을 함께 키우는 대규모 학습이
약한 확장이고, 이쪽은 직렬 비중이 상대적으로 작아져 훨씬 멀리 늘어난다. 무엇을 재는지 정하지
않고 배속만 보면 같은 코드가 잘 늘어나는지 아닌지를 반대로 읽는다.

## 암달의 법칙

앞의 배속은 암달의 법칙에서 나온다. 전체 작업에서 병렬로 돌릴 수 있는 비율을 p라 하면, 코어
N개로 얻는 배속은 아래 식으로 정해진다.

```
speedup(N) = 1 / ( (1 - p) + p / N )
```

`1 - p`가 순차 구간이다. N을 아무리 키워도 `p / N`은 0으로 갈 뿐이라, 배속은 `1 / (1 - p)`를
넘지 못한다. p가 0.95면 상한이 20배, 0.99면 100배다.

| 병렬 비율 p | 코어 16개 | 코어 64개 | 코어 256개 | 코어 1024개 | 상한 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 75% | 3.4배 | 3.8배 | 4.0배 | 4.0배 | 4배 |
| 90% | 6.4배 | 8.8배 | 9.7배 | 9.9배 | 10배 |
| 95% | 9.1배 | 15.4배 | 18.6배 | 19.6배 | 20배 |
| 99% | 13.9배 | 39.3배 | 72.1배 | 91.2배 | 100배 |

같은 코드라도 p가 0.9인지 0.99인지에 따라 코어 256개에서 결과가 9.7배와 72.1배로 갈린다.
코어를 늘리기 전에 순차 구간을 줄이는 편이 이득이 큰 이유가 여기 있다. 순차 구간이 1퍼센트만
있어도 코어 256개의 4분의 3이 노는 셈이다.

구스타프슨의 법칙은 반대편을 본다. 암달은 문제 크기를 고정하지만, 코어가 늘면 더 큰 문제를
푸는 경우가 많다. 문제를 키우면 병렬 구간은 데이터에 비례해 늘고 직렬 구간인 초기화와 취합은
거의 그대로여서, 전체에서 병렬 비율 p가 올라간다. 그래서 코어당 일감을 유지하며 문제를 키우면
배속이 코어 수에 가깝게 붙는다. 대규모 학습에서 노드를 늘리며 배치를 키우는 방식이 이 곡선을
탄다.

```
# 문제를 코어에 맞춰 키울 때 (구스타프슨)
scaled_speedup(N) = N - s * (N - 1)      # s는 직렬 비율 (1 - p)
```

s가 0.02면 코어 64개에서 암달은 약 28배에 그치지만, 문제를 함께 키우는 구스타프슨 관점에서는
약 63배에 이른다. 같은 코드가 강한 확장에서는 막히고 약한 확장에서는 뻗는 이유가 여기 있다.

실제 코드의 p는 재서 역산한다. 코어 2개와 N개에서 같은 입력으로 시간을 재고 `T(n) = a + b/n`
꼴에 맞춘다. a는 직렬 시간, b는 1코어 기준 병렬 시간이다.

```
b = (T2 - TN) * 2N / (N - 2)
a = T2 - b / 2
p = b / (a + b)
```

코어 2개에서 100초, 64개에서 8초가 나오면 b는 약 190, a는 약 5로 나오고 p는 약 0.97이다.
p가 이 정도면 코어 256개의 상한이 약 34배여서, 그 이상 코어를 요청해도 시간이 줄지 않는다.
측정 두 점만으로 어디까지 늘려야 할지를 미리 가늠할 수 있다.

## 코어와 소켓과 하드웨어 스레드

스레드 수를 정하려면 노드의 물리 구조를 알아야 한다. 용어가 겹쳐 헷갈리기 쉬우므로 하나씩
짚는다.

- **코어** 명령을 실제로 실행하는 계산 단위다. 코어 하나가 한 번에 한 흐름의 연산을 처리한다.
- **소켓** 물리 CPU 칩 하나가 꽂히는 자리다. 노드 한 대에 소켓이 둘이면 CPU 칩이 두 개 있고,
  각 칩이 코어 수십 개를 담는다.
- **하드웨어 스레드** 코어 하나가 실행 흐름 두 개를 번갈아 처리하는 기능이다. 인텔은
  하이퍼스레딩이라 부른다. 한 흐름이 메모리를 기다리는 동안 다른 흐름을 돌려 빈 시간을 메운다.
- **물리 코어와 논리 코어** 하드웨어 스레드가 켜져 있으면 코어 하나가 논리 코어 둘로 나뉜다.
  물리 코어 64개짜리 노드가 OS에는 논리 코어 128개로 나타난다. 연산이 빽빽한 코드는 두 흐름이
  같은 계산 자원을 다투므로 물리 코어 수만큼만 스레드를 쓰는 편이 빠르다.

`lscpu` 출력에서 이 값들을 읽는다.

```bash
lscpu
# CPU(s):                128        논리 코어 총수 (OS가 보는 수)
# Thread(s) per core:    2          코어당 하드웨어 스레드. 2면 하이퍼스레딩 켜짐
# Core(s) per socket:    32         소켓당 물리 코어
# Socket(s):             2          소켓 수
# NUMA node(s):          2          메모리가 묶인 구역 수
```

물리 코어 수는 `Core(s) per socket × Socket(s)`로 계산한다. 이 예시는 32 곱하기 2로 물리
코어 64개, 논리 코어 128개다. 연산 위주 작업의 출발점은 논리 코어 128이 아니라 물리 코어 64다.

`NUMA node(s)`는 메모리 접근 거리가 갈리는 구역 수다. 소켓마다 붙은 메모리가 있어, 다른
소켓의 메모리를 읽으면 자기 소켓의 메모리보다 느리다. 스레드를 코어에 붙이는 이유가 이 거리
때문이다.

## GPU 클러스터에 CPU 병렬이 필요한 이유

GPU가 계산을 맡는데도 CPU 병렬이 필요한 이유는 GPU를 굶기지 않기 위해서다. 학습 한 스텝은
데이터를 읽고, 디코딩하고, 증강한 뒤 GPU에 올려 계산하는 순서로 돈다. 앞의 세 단계는 CPU가
한다. CPU가 배치를 제때 못 만들면 GPU가 다음 배치를 기다리며 놀고, 비싼 가속기의 활용률이
떨어진다.

그래서 데이터 로더에 CPU 코어를 충분히 배정해야 한다. PyTorch의 `DataLoader`는 `num_workers`
수만큼 프로세스를 띄워 배치를 미리 준비하는데, 이 워커가 CPU 코어를 쓴다. 코어가 모자라면
GPU가 기다리고, 코어를 과하게 잡으면 다른 작업이 밀린다.

`--cpus-per-task` 산정은 노드의 코어를 GPU 수로 나누는 데서 출발한다. GPU 8장 노드에 물리
코어가 64개라면 GPU 한 장당 8코어가 배정된다.

```bash
#SBATCH --nodes=1
#SBATCH --ntasks-per-node=8     # GPU 1장당 태스크(프로세스) 1개
#SBATCH --gres=gpu:8
#SBATCH --cpus-per-task=8       # 물리 코어 64 나누기 GPU 8 = 8
```

이 배정 안에서 데이터 로더 워커 수를 정한다. 태스크당 8코어라면 `num_workers`를 6에서 8
사이로 잡고, 남는 여유는 메인 프로세스와 시스템 몫으로 둔다. 워커를 코어 수보다 많이 띄우면
프로세스들이 서로 코어를 다투어 오히려 느려진다.

논리 코어 128개를 기준으로 나누고 싶을 수 있지만, 데이터 디코딩은 연산이 빽빽해 하이퍼스레딩
이득이 작다. 물리 코어 64를 기준으로 나누는 편이 안정적이다.

## 프로세스와 스레드

병렬화 수단은 크게 둘이다. 무엇을 고르느냐에 따라 메모리와 통신 비용이 달라진다.

| 방식 | 메모리 | 통신 | 적합한 곳 |
| --- | --- | --- | --- |
| 멀티프로세스 (MPI) | 각자 따로 | 명시적 메시지 | 노드를 넘는 병렬 |
| 멀티스레드 (OpenMP) | 공유 | 공유 변수 | 노드 안의 병렬 |

노드 안에서는 스레드가 유리하다. 메모리를 복제하지 않아 데이터셋이 큰 작업에서 차이가 크다.
노드를 넘어가면 메모리가 공유되지 않으므로 프로세스와 메시지가 필요하다.

파이썬은 사정이 다르다. GIL 때문에 스레드로는 CPU 병렬이 되지 않는다. `multiprocessing`으로
프로세스를 띄우거나, NumPy처럼 GIL을 놓는 라이브러리 안에서 병렬이 일어나게 해야 한다.

스레드는 같은 메모리를 공유하므로 데이터를 복제하지 않는다. 데이터셋 하나를 여러 스레드가 함께
읽는 작업에서 메모리가 절약된다. 대신 여러 스레드가 같은 변수를 동시에 고치면 결과가 깨지므로
동기화가 필요하고, 그 동기화가 비용이 된다.

프로세스는 각자 독립된 메모리를 가진다. 서로의 변수를 건드릴 수 없어 안전하지만, 데이터를
주고받으려면 명시적으로 메시지를 보내거나 복사해야 한다. 노드를 넘어가면 애초에 메모리를
공유할 방법이 없으므로 프로세스와 메시지가 유일한 선택지다.

고르는 기준은 두 가지다.

- **경계** 한 노드 안이면 스레드, 노드를 넘으면 프로세스다.
- **데이터 크기** 데이터가 커서 복제가 부담이면 스레드가 유리하다.

실전에서는 둘을 겹쳐 쓴다. 노드 사이는 프로세스로, 노드 안은 스레드로 나누는 하이브리드
구성이 대표적이다. 뒤의 하이브리드 절에서 이어 본다.

## OpenMP로 스레드 병렬

반복문 앞에 지시자 한 줄을 붙이면 컴파일러가 스레드로 나눈다.

```c
#pragma omp parallel for
for (int i = 0; i < n; i++) {
    y[i] = a * x[i] + y[i];
}
```

반복 사이에 의존성이 없어야 한다. 앞 반복의 결과를 뒤에서 쓰면 결과가 실행할 때마다 달라진다.
합계처럼 하나의 변수에 모으는 경우는 축약을 명시한다.

```c
double sum = 0.0;
#pragma omp parallel for reduction(+:sum)
for (int i = 0; i < n; i++) sum += x[i] * y[i];
```

반복마다 걸리는 시간이 들쭉날쭉하면 정적 분배로는 일부 스레드가 먼저 끝나고 논다. 이럴 때
동적 분배로 바꾼다.

```c
#pragma omp parallel for schedule(dynamic, 64)
```

청크를 너무 작게 잡으면 분배 자체의 비용이 커진다. 수십에서 수백 사이에서 재보고 정한다.

각 절은 변수를 스레드에 어떻게 나눌지 정한다. 잘못 쓰면 컴파일은 되지만 결과가 조용히 틀린다.

| 절 | 뜻 | 쓸 때 | 잘못 쓰면 |
| --- | --- | --- | --- |
| `shared(x)` | 모든 스레드가 같은 변수를 본다 | 읽기만 하는 입력 배열 | 여러 스레드가 동시에 쓰면 값이 깨진다 |
| `private(t)` | 스레드마다 별도 사본을 둔다 | 반복 안의 임시 변수 | 초기값이 없어 쓰레기값으로 시작한다 |
| `firstprivate(c)` | 사본을 두되 진입 전 값으로 채운다 | 루프 밖에서 정한 상수를 각자 쓸 때 | `private`로 두면 그 값이 사라진다 |
| `reduction(+:s)` | 스레드별로 모았다가 마지막에 합친다 | 합계, 최댓값 같은 누적 | 공유 변수로 두면 경쟁으로 값이 줄어든다 |

가장 흔한 사고는 누적 변수를 그냥 `shared`로 두는 것이다. 두 스레드가 같은 `sum`에 동시에
더하면 한쪽 갱신이 묻혀 매번 다른 값이 나온다. 반복 안에서만 쓰는 임시 변수를 `private`로
선언하지 않으면 스레드끼리 그 변수를 덮어써 결과가 어긋난다.

`schedule`은 반복을 스레드에 나누는 방식이다. `static`은 처음에 균등하게 잘라 분배 비용이 거의
없다. 반복마다 걸리는 시간이 고르면 이쪽이 가장 빠르다. `dynamic`은 스레드가 끝나는 대로 다음
청크를 집어 부하가 들쭉날쭉한 경우에 맞지만, 청크를 집을 때마다 조율 비용이 든다. `guided`는
큰 청크로 시작해 점점 줄여 둘의 절충이다. 반복 시간이 균등한데 `dynamic`을 쓰면 조율 비용만
늘어 느려지고, 반대로 들쭉날쭉한데 `static`을 쓰면 무거운 몫을 받은 스레드가 끝날 때까지 나머지가
논다.

컴파일과 실행은 컴파일러에 병렬 플래그를 켜는 데서 시작한다.

```bash
gcc -O2 -fopenmp axpy.c -o axpy      # GCC는 -fopenmp, Intel은 -qopenmp
OMP_NUM_THREADS=8 ./axpy             # 스레드 수는 환경 변수로 준다
```

플래그를 빼먹으면 `#pragma`가 주석으로 무시되어 한 스레드로 돈다. 병렬화한 코드가 안 빨라지면
먼저 이 플래그가 켜졌는지 확인한다.

## 스레드를 코어에 붙이기

기본 상태에서는 OS가 스레드를 옮겨 다니게 둔다. 캐시가 매번 식고 NUMA 노드를 넘나들면서
성능이 흔들린다. 붙여 두면 재현성도 함께 올라간다.

```bash
export OMP_NUM_THREADS=16
export OMP_PROC_BIND=close     # 스레드를 서로 가까이 붙인다
export OMP_PLACES=cores        # 배치 단위는 코어
```

`close`는 한 소켓에 몰아 붙여 캐시 공유가 유리하고, `spread`는 흩어 놓아 메모리 대역폭을 더
쓴다. 대역폭에 묶인 연산은 `spread`가 나은 경우가 있다.

![close는 스레드를 한 소켓에 모으고 spread는 소켓에 흩어 배치한다](img/thread-binding.svg)

메모리도 함께 묶어야 효과가 난다.

```bash
numactl --cpunodebind=0 --membind=0 ./app
```

리눅스는 메모리를 처음 만지는 스레드가 있는 노드에 페이지를 붙인다. 초기화를 한 스레드가
몰아서 하면 데이터 전체가 한 노드에 몰리고, 이후 다른 노드의 스레드는 계속 원격 접근을 한다.
초기화도 실제 계산과 같은 방식으로 병렬화해야 한다.

```c
#pragma omp parallel for
for (int i = 0; i < n; i++) x[i] = 0.0;   // 계산과 같은 분배로 초기화한다
```

## 하이브리드 MPI + OpenMP

노드 안은 스레드로, 노드 사이는 프로세스로 나누는 구성이다. 소켓마다 프로세스 하나를 두고
그 소켓의 코어 수만큼 스레드를 붙이는 배치가 무난한 출발점이다.

```bash
#SBATCH --nodes=4
#SBATCH --ntasks-per-node=2      # 소켓당 프로세스 1개
#SBATCH --cpus-per-task=64       # 소켓의 코어 수

export OMP_NUM_THREADS=$SLURM_CPUS_PER_TASK
export OMP_PROC_BIND=close
srun --cpu-bind=cores ./app
```

프로세스를 늘릴수록 통신량이 늘고, 스레드를 늘릴수록 동기화 비용과 NUMA 원격 접근이 는다.
둘 사이 균형은 코드마다 다르므로 몇 가지 조합을 재보고 고른다.

프로세스와 스레드의 곱이 노드의 물리 코어 수를 넘지 않아야 한다. 소켓이 둘이고 소켓당 코어가
64개인 노드라면, 소켓마다 프로세스 하나에 스레드 64개가 코어를 정확히 채운다. 프로세스를 소켓
경계에 맞추면 각 프로세스의 스레드가 한 소켓 안에 머물러 NUMA 원격 접근이 사라진다.

배치가 어긋나면 두 프로세스의 스레드가 같은 코어에 겹치거나, 한 프로세스가 두 소켓에 걸쳐
절반의 스레드가 원격 메모리를 읽는다. `--cpu-bind`와 `OMP_PLACES`로 경계를 맞춰야 하는 이유다.

| 구성 | 프로세스 배치 | 장점 | 단점 |
| --- | --- | --- | --- |
| 순수 MPI | 코어마다 프로세스 1개 | 단순하다 | 프로세스 수만큼 통신량과 메모리가 는다 |
| 순수 OpenMP | 노드에 프로세스 1개 | 통신이 없다 | 노드를 넘지 못한다 |
| 하이브리드 | 소켓마다 프로세스 1개 | 통신량과 NUMA 접근을 함께 줄인다 | 배치를 맞추기 까다롭다 |

어느 쪽이 빠른지는 코드가 통신에 묶였는지 메모리 대역폭에 묶였는지에 달렸다. 통신이 많으면
프로세스를 줄이고 스레드를 늘리고, 메모리 대역폭이 부족하면 반대로 간다.

## 배치가 제대로 됐는지 확인

설정을 넣었다고 적용되는 것은 아니다. 런타임이 무시하거나 스케줄러 설정과 충돌하는 경우가 있어
실제 배치를 눈으로 확인해야 한다.

```bash
export OMP_DISPLAY_ENV=verbose      # 시작할 때 적용된 설정을 찍는다
export OMP_DISPLAY_AFFINITY=true    # 스레드가 어느 코어에 묶였는지 찍는다
export OMP_AFFINITY_FORMAT="thread %0.3n bound to core %A on host %H"
```

Slurm에서는 할당 자체를 확인한다.

```bash
srun --cpu-bind=verbose,cores ./app 2>&1 | head    # 어느 마스크로 묶였는지
taskset -pc $$                                      # 현재 셸의 허용 코어
numastat -p <pid>                                   # 노드별 메모리 사용량
```

`numastat`에서 다른 노드의 값이 크면 원격 접근이 일어나는 중이다. 첫 접근 규칙 때문에 초기화
코드가 원인인 경우가 많다.

도구마다 보이는 것이 다르므로, 배치가 틀렸을 때 무엇이 보이는지 알아두면 원인을 빨리 좁힌다.

| 도구 | 명령 | 배치가 맞을 때 | 배치가 틀렸을 때 |
| --- | --- | --- | --- |
| hwloc | `hwloc-ps -t -c` | 스레드가 서로 다른 코어에 하나씩 | 여러 스레드가 같은 코어에 겹쳐 표시 |
| taskset | `taskset -cp <pid>` | 허용 코어가 소켓 하나로 좁다 | `0-127`처럼 전체가 열려 이동을 허용 |
| proc | `grep Cpus_allowed_list /proc/<pid>/status` | 좁은 코어 목록 | 노드 전체 범위 |
| numastat | `numastat -p <pid>` | 자기 노드 값만 크다 | 다른 노드 값이 함께 크다 |
| htop | `htop` | 쓰는 코어만 100퍼센트 | 부하가 여러 코어를 떠돌거나 절반만 참 |

```bash
hwloc-ps -t -c                                   # 스레드별 코어 점유를 한눈에
taskset -cp $(pgrep -n app)                       # 그 프로세스의 허용 코어 마스크
grep Cpus_allowed_list /proc/$(pgrep -n app)/status
numastat -p $(pgrep -n app)                       # 노드별 메모리 분포
```

`taskset`과 `Cpus_allowed_list`가 노드 전체를 가리키면 바인딩이 안 걸린 것이다. OS가 스레드를
아무 코어에나 옮길 수 있어, `htop`에서 부하가 코어 사이를 떠도는 모습으로 나타난다. `hwloc-ps`에서
두 스레드가 같은 코어에 찍히면 오버서브스크립션이고, `numastat`에서 원격 노드 값이 크면 첫 접근
규칙에 걸린 것이다. 세 도구가 같은 곳을 가리키면 초기화와 바인딩을 함께 손본다.

## 동기화 비용

스레드를 늘려도 안 빨라지는 두 번째 이유가 동기화다. 임계 구역과 배리어는 스레드 수에 따라
비용이 커진다.

```c
// 나쁜 예. 매 반복마다 락을 잡는다
#pragma omp parallel for
for (int i = 0; i < n; i++) {
    #pragma omp critical
    sum += x[i];
}

// 좋은 예. 각자 모았다가 마지막에 한 번 합친다
#pragma omp parallel for reduction(+:sum)
for (int i = 0; i < n; i++) sum += x[i];
```

앞의 코드는 스레드를 늘릴수록 느려진다. 락을 기다리는 시간이 계산 시간을 넘기기 때문이다.
축약은 스레드마다 지역 변수를 두고 마지막에 트리 형태로 합치므로 이 문제가 없다.

배리어도 마찬가지다. 반복문이 끝날 때마다 암묵적 배리어가 걸리는데, 다음 계산이 앞의 결과에
의존하지 않으면 없앨 수 있다.

```c
#pragma omp parallel
{
    #pragma omp for nowait          // 배리어를 없앤다
    for (int i = 0; i < n; i++) a[i] = f(i);

    #pragma omp for                 // 여기서는 필요하다
    for (int i = 0; i < n; i++) b[i] = g(a[i]);
}
```

## 거짓 공유를 눈으로 확인

논리적으로 겹치지 않는 변수라도 같은 캐시 라인(보통 64바이트)에 있으면 코어끼리 그 줄을
주고받는다. 결과는 맞지만 성능이 크게 떨어진다.

```c
// 나쁜 예. sums 원소들이 같은 캐시 라인에 몰린다
double sums[8];
#pragma omp parallel num_threads(8)
{
    int t = omp_get_thread_num();
    for (int i = t; i < n; i += 8) sums[t] += x[i];
}

// 좋은 예. 캐시 라인 크기로 띄운다
struct { double v; char pad[56]; } sums[8];
```

의심되면 캐시 관련 카운터로 확인한다.

```bash
perf stat -e cache-misses,cache-references,LLC-load-misses ./app
```

같은 계산인데 스레드를 늘렸을 때 캐시 미스가 급증하면 거짓 공유를 의심한다.

캐시는 바이트 하나가 아니라 캐시 라인 단위로 오간다. 한 라인이 보통 64바이트라, `double` 여덟
개가 한 라인에 들어간다. 코어는 자기가 쓰는 값을 캐시 라인째로 가져와 독점 상태로 바꾼 뒤
고친다. 다른 코어가 같은 라인의 다른 값을 고치려 하면, 값이 겹치지 않아도 그 코어가 라인을
독점으로 뺏어 온다. 두 코어가 번갈아 라인을 주고받으며 매 갱신마다 캐시가 무효화되고, 계산은
맞지만 메모리를 오가는 시간이 계산을 압도한다. 스레드별 누적 변수를 배열에 촘촘히 두면 이
현상이 그대로 재현된다.

`perf c2c`는 어느 캐시 라인이 코어 사이를 오가는지 짚어 준다.

```bash
perf c2c record ./app          # 캐시 라인 공유를 기록한다
perf c2c report                # HITM이 많은 라인과 그 변수를 보여준다
```

출력에서 `HITM`은 다른 코어의 변경된 캐시에서 값을 가져온 횟수다. 이 값이 큰 라인이 거짓 공유의
현장이고, 리포트가 그 라인에 걸린 변수와 소스 위치까지 짚어 준다. 고치는 방법은 각 스레드의
변수를 서로 다른 캐시 라인으로 밀어내는 것이다.

```c
// 전: 8개 누적 변수가 한두 라인에 몰려 코어끼리 라인을 뺏는다
double sums[8];

// 후: 64바이트로 정렬하고 라인 크기만큼 띄워 각자 다른 라인에 둔다
struct alignas(64) { double v; } sums[8];
```

띄우기 전에는 스레드 8개에서 오히려 1개보다 느린 일이 흔하다. 라인 하나를 여덟 코어가 돌려
쓰기 때문이다. 정렬로 라인을 분리하면 `perf c2c`의 HITM이 거의 사라지고, 스레드 수에 비례해
시간이 준다. 근본 해법은 애초에 스레드별 지역 변수에 모았다가 마지막에 합치는 축약이다.

## 작업 단위 병렬

반복문으로 나누기 어려운 구조, 예를 들어 재귀나 그래프 순회는 작업 단위로 나눈다.

```c
#pragma omp parallel
#pragma omp single
{
    #pragma omp task
    process(left);
    #pragma omp task
    process(right);
    #pragma omp taskwait
}
```

작업이 너무 잘게 쪼개지면 생성 비용이 계산을 넘는다. 일정 깊이 아래로는 순차로 처리하도록
잘라 주는 편이 낫다.

`task` 지시자는 만나는 순간 실행하지 않고 작업 큐에 넣는다. 노는 스레드가 큐에서 하나씩 꺼내
실행한다. 반복 횟수를 미리 알 수 없는 재귀나, 가지마다 길이가 다른 트리 순회에서 반복문
분배보다 균형이 잘 맞는다.

`single`은 작업을 만드는 일을 스레드 하나만 하게 막는다. 이 지시자가 없으면 모든 스레드가 같은
작업을 중복해서 만든다. `taskwait`은 만들어 둔 하위 작업이 모두 끝날 때까지 기다리는 지점이다.

잘게 쪼갤수록 부하 균형은 좋아지지만 작업 하나를 만들고 큐에 넣는 비용이 쌓인다. 일정 깊이
아래로는 작업을 만들지 않고 순차로 처리하도록 자르면 이 비용이 준다.

```c
void process(node *n, int depth) {
    if (n == NULL) return;
    if (depth > CUTOFF) {          // 깊으면 순차로 처리한다
        process_seq(n);
        return;
    }
    #pragma omp task
    process(n->left, depth + 1);
    process(n->right, depth + 1);  // 오른쪽은 현재 스레드가 이어서 한다
    #pragma omp taskwait
}
```

`CUTOFF` 깊이는 코드마다 다르므로 몇 값을 재보고 정한다. 얕으면 병렬이 부족하고 깊으면 작업
생성 비용이 계산을 넘는다.

## 스레드 수를 잘못 잡았을 때 증상

스레드 수가 코어 구조와 안 맞으면 나타나는 증상이 정해져 있다. 증상으로 원인을 좁힌 뒤 확인
명령으로 굳힌다.

| 증상 | 원인 | 확인 |
| --- | --- | --- |
| 스레드를 늘렸는데 급격히 느려진다 | 오버서브스크립션. 코어 수보다 스레드가 많다 | `nproc`와 스레드 수 비교, `htop`의 과부하 로드 |
| 코어 절반만 바쁘다 | 스레드 수가 물리 코어의 절반에 묶였다 | `htop`에서 유휴 코어 확인, `OMP_NUM_THREADS` 값 |
| 어느 지점부터 배속이 안 는다 | 순차 구간 한계나 메모리 대역폭 포화 | 코어별 시간 측정, `perf stat -d`의 캐시 미스 |
| 실행할 때마다 시간이 흔들린다 | 스레드가 코어에 안 묶여 이동한다 | `OMP_PROC_BIND` 미설정, `OMP_DISPLAY_AFFINITY`로 확인 |
| 논리 코어를 다 썼는데 더 느리다 | 하이퍼스레딩 흐름이 연산 자원을 다툰다 | 물리 코어 수로 낮춰 재측정 |

오버서브스크립션은 라이브러리가 각자 스레드를 띄울 때 잘 생긴다. MPI 프로세스 8개가 각각
64스레드를 띄우면 512스레드가 코어 64개를 다툰다. 확인 명령은 간단하다.

```bash
nproc                                  # 이 프로세스가 쓸 수 있는 코어 수
grep -c ^processor /proc/cpuinfo       # 논리 코어 총수
ps -eLf | wc -l                        # 지금 떠 있는 스레드 총수
```

떠 있는 스레드 총수가 코어 수를 크게 넘으면 어딘가에서 스레드가 중복으로 생기는 중이다.
`OMP_NUM_THREADS`와 라이브러리별 스레드 변수를 함께 확인한다.

## 런타임별 환경 변수

같은 OpenMP라도 컴파일러 런타임에 따라 변수 이름이 다르다. 혼용하면 한쪽만 적용되어 원인을
찾기 어려워진다.

| 목적 | 표준 | GNU | Intel |
| --- | --- | --- | --- |
| 스레드 수 | `OMP_NUM_THREADS` | 동일 | 동일 |
| 바인딩 | `OMP_PROC_BIND` | `GOMP_CPU_AFFINITY` | `KMP_AFFINITY` |
| 대기 정책 | `OMP_WAIT_POLICY` | 동일 | `KMP_BLOCKTIME` |
| 스택 크기 | `OMP_STACKSIZE` | 동일 | `KMP_STACKSIZE` |

`KMP_BLOCKTIME`은 스레드가 일이 없을 때 얼마나 기다리다 잠들지 정한다. 기본값이 크면 유휴
스레드가 CPU를 붙잡고 있어 다른 프로세스와 경합한다. MPI와 섞어 쓸 때는 줄이는 편이 낫다.

OpenMP 자체의 동작도 여러 변수로 갈린다. 이 변수들이 실제로 배치와 스케줄을 정한다.

| 목적 | 변수 | 값의 예 |
| --- | --- | --- |
| 스레드 수 | `OMP_NUM_THREADS` | `8` |
| 바인딩 방식 | `OMP_PROC_BIND` | `close`, `spread`, `true` |
| 배치 단위 | `OMP_PLACES` | `cores`, `threads`, `sockets` |
| 기본 스케줄 | `OMP_SCHEDULE` | `static`, `dynamic,64`, `guided` |

문제는 파이썬 과학 스택이 저마다 자기 스레드 풀을 따로 띄운다는 점이다. NumPy 뒤의 BLAS,
`numexpr`, PyTorch가 각각 코어 전체를 쓰려 든다. 변수를 하나만 잡고 나머지를 놓치면 그 라이브러리가
숨어서 스레드를 부풀린다.

| 라이브러리 | 스레드 제어 |
| --- | --- |
| OpenMP | `OMP_NUM_THREADS` |
| Intel MKL | `MKL_NUM_THREADS` |
| OpenBLAS | `OPENBLAS_NUM_THREADS` |
| NumExpr | `NUMEXPR_NUM_THREADS` |
| PyTorch | `torch.set_num_threads(n)` |

이 값들은 더해지지 않고 곱해진다. 데이터 로더가 `num_workers=8`로 워커 프로세스 8개를 띄우고,
워커마다 BLAS가 코어 64개짜리 풀을 열면 8 곱하기 64로 512스레드가 코어 64개를 다툰다. 전처리가
GPU 학습보다 느려지는 흔한 원인이 이 숨은 곱이다. 데이터 로더 워커 안에서는 BLAS 스레드를 1로
묶어 워커 수만큼만 병렬이 되게 한다.

```bash
# 워커가 각자 스레드를 부풀리지 못하게 진입 전에 1로 고정한다
export OMP_NUM_THREADS=1
export MKL_NUM_THREADS=1
export OPENBLAS_NUM_THREADS=1
export NUMEXPR_NUM_THREADS=1
```

```python
import torch
torch.set_num_threads(1)          # 데이터 로더 워커에서는 1로 둔다
```

메인 연산에서는 코어를 충분히 쓰고, 워커 안에서만 1로 누르는 식으로 층을 나눈다. 어느 쪽이든
곱이 물리 코어 수를 넘지 않게 맞추는 것이 요령이다.

## 자주 밟는 함정

**스레드 초과 할당**  라이브러리가 각자 스레드를 띄우면 코어 수보다 훨씬 많은 스레드가 생겨
서로를 방해한다. MPI 프로세스 8개가 각각 OpenMP 스레드 64개를 띄우면 512개가 된다. 데이터
로더나 전처리에서는 아예 1로 고정하는 편이 낫다.

```bash
export OMP_NUM_THREADS=1
export MKL_NUM_THREADS=1
export OPENBLAS_NUM_THREADS=1
export NUMEXPR_NUM_THREADS=1
```

**거짓 공유**  서로 다른 스레드가 같은 캐시 라인에 있는 다른 변수를 쓰면, 논리적으로는 겹치지
않는데도 캐시 라인이 계속 오간다. 스레드별 누적 변수를 배열 하나에 촘촘히 두면 이 현상이
생긴다. 각자 지역 변수에 모았다가 마지막에 합치면 사라진다.

**하이퍼스레딩**  논리 코어 수를 그대로 스레드 수로 쓰면 연산 위주 코드에서는 오히려 느려진다.
물리 코어 수로 시작해서 재보고 늘린다.

```bash
lscpu | grep -E "^CPU\(s\)|Thread|Core"
```

함정마다 증상과 확인 명령이 정해져 있다. 아래 표로 원인을 빠르게 좁힌다.

| 함정 | 증상 | 원인 | 확인 |
| --- | --- | --- | --- |
| 스레드 초과 할당 | 스레드를 늘렸는데 느려진다 | 라이브러리 스레드 수의 곱이 코어를 넘는다 | `ps -eLf`의 줄 수, 각 `*_NUM_THREADS` |
| 거짓 공유 | 스레드 늘리자 캐시 미스 급증 | 누적 변수가 한 캐시 라인에 몰렸다 | `perf c2c report`의 HITM |
| 하이퍼스레딩 과신 | 논리 코어를 다 쓰자 더 느리다 | 두 흐름이 연산 자원을 다툰다 | 물리 코어 수로 낮춰 재측정 |
| 바인딩 누락 | 실행 시간이 매번 흔들린다 | 스레드가 코어를 떠돈다 | `taskset -cp <pid>` |
| NUMA 원격 접근 | 스레드를 늘려도 정체 | 초기화가 한 노드에 몰렸다 | `numastat -p <pid>` |
| 잠금 과다 | 코어를 늘릴수록 느려진다 | 매 반복 임계 구역을 잡는다 | `perf record`에서 락 함수 비중 |

표의 앞 세 줄이 가장 흔하다. 스레드 초과 할당은 곱의 결과이므로 라이브러리별 스레드 변수를
모두 확인해야 잡힌다. 바인딩 누락과 NUMA 원격 접근은 배치를 눈으로 확인하는 절의 도구로
현장을 짚는다. 잠금 과다는 축약이나 스레드별 지역 변수로 바꾸면 사라진다.

## 얼마나 늘어나는지 재기

느낌으로 판단하지 말고 코어 수를 바꿔가며 같은 입력으로 재본다.

```bash
for t in 1 2 4 8 16 32 64; do
  OMP_NUM_THREADS=$t /usr/bin/time -f "$t threads: %e s" ./app
done
```

측정 자체가 흔들리면 결과를 믿기 어렵다. 몇 가지를 지켜야 값이 안정된다.

- **워밍업** 첫 실행은 캐시가 비어 있고 페이지가 아직 안 붙어 느리다. 처음 한두 번은 버리고
  그다음부터 잰다.
- **반복과 중앙값** 같은 설정을 다섯 번 이상 재고 평균이 아니라 중앙값을 쓴다. 중앙값은 가끔
  끼어드는 다른 작업의 영향을 덜 받는다.
- **주파수 고정** 터보 부스트가 켜져 있으면 클럭이 부하에 따라 오르내려 코어 수 비교가 흐트러진다.
  성능 거버너로 고정하고 잰다.
- **독점 노드** 다른 사람과 노드를 나눠 쓰면 측정이 오염된다. `--exclusive`로 노드를 통째로 잡는다.

```bash
sudo cpupower frequency-set -g performance      # 주파수를 고정한다
# Slurm에서는 제출 시 --exclusive 로 노드를 독점한다
```

잰 값은 표로 남겨야 비교가 된다. 코어 수, 시간, 1코어 대비 배속, 그리고 코어당 효율을 함께
적는다. 효율은 배속을 코어 수로 나눈 값이고, 이 값이 떨어지는 지점이 확장의 상한이다.

| 코어 | 시간(s) | 배속 | 효율 |
| ---: | ---: | ---: | ---: |
| 1 | 100.0 | 1.0배 | 100% |
| 8 | 13.5 | 7.4배 | 93% |
| 32 | 4.2 | 23.8배 | 74% |
| 64 | 3.1 | 32.3배 | 50% |

이 예시는 코어 32개까지는 효율이 70퍼센트를 넘다가 64개에서 절반으로 떨어진다. 코어 64개를
요청할 만한 이득이 없다는 뜻이므로 32개 근처가 이 코드의 실용 상한이다. 코어를 두 배로 늘렸을
때 시간이 절반 가까이 줄면 그 구간까지는 잘 늘어나는 것이고, 어느 지점부터 시간이 줄지 않거나
오히려 늘면 거기가 상한이다. 그 지점을 넘겨 자원을 요청하면 클러스터 전체의 활용률만
떨어뜨린다. 어디에서 시간을 쓰는지는 프로파일러로 본다.

```bash
perf stat -d ./app                       # 명령어 수, 캐시 미스, 분기 예측
perf record -g ./app && perf report      # 함수별 비중
```

캐시 미스 비율이 높으면 데이터 배치를, 명령어 수 대비 시간이 길면 메모리 대역폭을 의심한다.
