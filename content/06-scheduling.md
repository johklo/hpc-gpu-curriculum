대기열이 길어질수록 스케줄링 정책이 곧 성능이자 비용이 된다. 자원을 어떤 기준으로 나누는지,
그 결정이 대기 시간과 활용률에 어떻게 돌아오는지를 본다.

## 토폴로지 인지 배치

GPU 8장이 한 노드에 있다고 해서 서로 같은 거리에 있는 것은 아니다. NVLink로 직접 붙은 쌍이
있고, PCIe 스위치를 거쳐야 하는 쌍이 있다. 4장을 쓰는 작업에 어느 4장을 주느냐에 따라 집합
통신 성능이 달라진다.

```bash
nvidia-smi topo -m
```

출력에 찍히는 기호가 곧 거리다.

| 기호 | 의미 | 상대 성능 |
| --- | --- | --- |
| `NV#` | NVLink로 직접 연결. 숫자는 링크 수다 | 가장 빠르다 |
| `PIX` | 같은 PCIe 스위치 아래 | 빠르다 |
| `PXB` | PCIe 스위치 여러 개를 거친다 | 보통이다 |
| `SYS` | 소켓을 넘어 QPI/UPI를 거친다 | 가장 느리다 |

Slurm은 노드 안의 GPU 배치까지 이해하도록 설정할 수 있다. `gres.conf`에서 GPU마다 연결된
코어를 적어두면 스케줄러가 가까운 조합을 골라준다.

```ini
# gres.conf
Name=gpu File=/dev/nvidia0 Cores=0-15
Name=gpu File=/dev/nvidia1 Cores=0-15
Name=gpu File=/dev/nvidia4 Cores=64-79
```

노드 사이도 마찬가지다. `topology.conf`에 스위치 구성을 적으면 같은 리프 스위치 아래 노드를
우선 묶는다. 네트워크 홉이 줄어 allreduce 성능이 올라간다.

## 자원 파편화

활용률이 낮은 이유를 찾다 보면 자원이 없어서가 아니라 **쓸 수 있는 모양으로 남아 있지 않아서**인
경우가 많다. 작업이 들어오고 나가기를 반복하면 노드마다 GPU가 한두 장씩 흩어져 남는다. 전체로는
스무 장이 놀고 있는데 8장을 한 노드에서 요구하는 작업은 들어갈 자리가 없다.

```
호스트 1  [■■][□][■■■][□]      유휴 2장
호스트 2  [■■■][□][■■][□]      유휴 2장
호스트 3  [■][□][■■■■][□]      유휴 2장
          8장을 요구하는 작업은 어디에도 못 들어간다
```

대기열은 길어지는데 노드는 노는 상태가 이렇게 만들어진다. 할당률을 떨어뜨리는 요인 중에서
파편화가 가장 크다.

줄이는 방법은 셋이다.

- **빈팩 배치**. 노드를 골고루 채우는 대신 한 노드를 먼저 채운다. Kubernetes의 `MostAllocated`,
  Slurm의 `CR_Pack_Nodes`가 이 동작이다. 빈 노드가 통째로 남아 큰 작업이 들어갈 자리가 생긴다.
- **크기별 구역 분리**. 큰 작업만 받는 노드 묶음을 따로 둔다. 작은 작업이 그 구역을 잠식하지
  못하게 하면 큰 작업의 대기 시간이 안정된다. 대신 그 구역의 유휴는 감수한다.
- **정리 창구**. 짧은 작업만 받는 시간대를 두거나, 선점 가능한 낮은 우선순위 작업으로 조각을
  채운다. 큰 작업이 들어올 때 이들을 비우면 된다.

파편화가 얼마나 심한지는 유휴 GPU 수만 봐서는 모른다. **가장 큰 작업이 지금 들어갈 수 있는가**를
같이 봐야 한다. 노드별 유휴 장수의 분포를 보면 판단이 선다. 유휴 20장이 노드 3대에 흩어져 있는
것과 노드 3대가 통째로 비어 있는 것은 전혀 다른 상태다.

## 대규모 학습 예약

노드 수십 대를 며칠씩 쓰는 학습은 일반 대기열에 그냥 넣으면 곤란해진다. 자원이 모일 때까지
계속 밀리거나, 반대로 시작하는 순간 다른 모든 작업이 멈춘다.

예약은 이 문제를 시간 축으로 푼다. 큰 실험에 대해 언제부터 언제까지 어느 구역을 쓸지 미리
잡아 두고, 그 구간에는 다른 작업이 들어오지 못하게 한다.

```bash
# 12월 1일 12시부터 사흘간 노드 16대를 team-ml 계정에 잡아 둔다
scontrol create reservation starttime=2026-12-01T12:00:00 duration=3-00:00:00 \
  nodes=gpu[01-16] accounts=team-ml reservationname=bigrun-a

scontrol show reservation                    # 예약 현황
sbatch --reservation=bigrun-a train.sh       # 예약 구간에 제출한다
```

얻는 것은 세 가지다. 언제 시작하는지 사용자가 알 수 있고, 운영자는 그 앞뒤로 일정을 짤 수 있고,
예약 구간이 끝나면 자원이 돌아온다는 보장이 생긴다. 백필과 함께 쓰면 예약 시작 전까지 짧은
작업으로 빈 구간을 채울 수 있다.

예약을 남발하면 반대로 활용률이 떨어진다. 예약해 놓고 쓰지 않는 구간이 통째로 노는 탓이다.
시작 후 일정 시간 안에 작업이 들어오지 않으면 예약을 푸는 규칙을 함께 두는 편이 낫다.

## 갱 스케줄링과 백필

분산 학습 작업은 요청한 노드가 전부 동시에 있어야 시작할 수 있다. 8노드 중 7개만 주면 아무
진전이 없이 자원만 점유한다. 갱 스케줄링은 전부 확보되기 전에는 시작하지 않는 방식이다.

문제는 큰 작업이 자원을 기다리는 동안 노드가 놀게 된다는 점이다. 백필이 이 빈틈을 메운다.
앞선 작업의 예상 시작 시각을 계산해두고, 그 전에 끝날 수 있는 짧은 작업을 먼저 밀어 넣는다.

![대기 중인 큰 작업이 시작하기 전 빈 구간에 짧은 작업을 배치해 유휴를 줄인다](img/backfill.svg)

백필이 동작하려면 작업마다 실행 시간이 정확해야 한다. 모두가 최대 시간을 적으면 스케줄러가
빈틈을 계산할 수 없어 백필이 무력해진다. 사용자에게 실제에 가까운 `--time`을 적도록 안내하는
것이 활용률에 직접 영향을 준다.

```ini
# slurm.conf
SchedulerType=sched/backfill
SchedulerParameters=bf_window=4320,bf_resolution=300,bf_max_job_test=500
```

`bf_window`는 몇 분 앞까지 내다볼지, `bf_max_job_test`는 한 번에 몇 개를 검토할지 정한다.
값을 키우면 빈틈을 더 잘 찾지만 컨트롤러 부하가 늘어난다.

## 공정 배분과 우선순위

여러 팀이 한 클러스터를 쓰면 "많이 쓴 쪽이 잠시 뒤로 물러나는" 규칙이 필요하다. Slurm의
fairshare는 각 계정에 몫을 배정하고, 최근 사용량이 몫을 넘으면 우선순위를 낮춘다.

```ini
PriorityType=priority/multifactor
PriorityWeightFairshare=100000
PriorityWeightAge=10000
PriorityWeightPartition=10000
PriorityWeightJobSize=1000
PriorityDecayHalfLife=7-0        # 사용 이력은 7일 반감기로 잊는다
```

가중치의 절대값보다 비율이 중요하다. fairshare를 다른 요소보다 열 배 크게 두면 사용량 균형이
지배적으로 작동하고, age를 키우면 오래 기다린 작업이 앞서게 된다.

현재 상태는 다음 명령으로 본다.

```bash
sshare -a                        # 계정별 몫과 실제 사용량
sprio -l -u alice                # 대기 중인 작업의 우선순위 구성 요소
```

선점은 강한 도구다. 낮은 우선순위 작업을 중단시키고 자리를 비우게 하는데, 체크포인트가 없는
작업이 선점당하면 계산이 통째로 날아간다. 선점을 켤 때는 대상 파티션을 체크포인트가 있는
워크로드로 한정하는 편이 안전하다.

## GPU 메모리와 전력 인지

GPU를 장수로만 세면 실제 제약을 놓친다. 80GB 카드 한 장을 요구하는 작업과 24GB면 되는 작업을
같게 다루면 활용률이 떨어진다.

Slurm에서는 GRES 타입을 나눠 표현한다.

```ini
# gres.conf
Name=gpu Type=a100_80g File=/dev/nvidia[0-3]
Name=gpu Type=a100_40g File=/dev/nvidia[4-7]
```

```bash
sbatch --gres=gpu:a100_40g:2 job.sh    # 필요한 만큼만 요청한다
```

전력도 제약이 된다. 랙 단위 전력 한도가 있으면 모든 노드가 동시에 최대 전력으로 도는 구성을
피해야 한다. 클럭 상한을 걸어 노드당 소비를 낮추는 방법이 있다.

```bash
nvidia-smi -pl 350           # 전력 상한을 350W로 건다
nvidia-smi -q -d POWER       # 현재 상한과 실제 소비
```

전력 상한을 낮추면 성능도 낮아지지만, 비율은 선형이 아니다. 상한을 20퍼센트 낮췄을 때 성능
저하가 그보다 작다면 랙에 노드를 더 넣는 편이 전체 처리량에서 유리하다.

측정은 같은 작업을 상한만 바꿔 돌려 비교한다. 상한마다 스텝 시간을 재고 실제 소비 전력을 함께
남긴다.

```bash
for cap in 700 600 500 400; do
  srun -N1 --gres=gpu:8 bash -c "
    nvidia-smi -pl $cap >/dev/null
    python train.py --max-steps 200 --report-step-time" | tail -1
done
```

| 전력 상한 | 스텝 시간 | 성능 비율 | 전력 비율 | 같은 전력에서의 처리량 |
| ---: | ---: | ---: | ---: | ---: |
| 700W | 1.00초 | 100% | 100% | 1.00 |
| 600W | 1.06초 | 94% | 86% | 1.10 |
| 500W | 1.17초 | 85% | 71% | 1.19 |
| 400W | 1.42초 | 70% | 57% | 1.23 |

마지막 열이 판단 기준이다. 랙 전력이 상한이고 노드를 더 넣을 여지가 있다면 이 값이 큰 쪽이
이득이다. 반대로 노드 수가 고정이고 한 작업을 빨리 끝내는 것이 목적이면 상한을 낮출 이유가 없다.
클러스터가 전력에 묶였는지 자리에 묶였는지부터 정해야 답이 나온다.

메모리 요구량은 사용자가 스스로 알기 어렵다. 지난 실행에서 실제로 얼마를 썼는지 보여 주면
과다 요청이 줄어든다.

```bash
# 끝난 작업이 실제로 쓴 GPU 메모리 최댓값
sacct -j 12345 --format=JobID,ReqTRES%40,MaxRSS,MaxVMSize
dcgmi stats --job 12345 --verbose | grep -i "memory"
```

과다 요청은 활용률을 갉아먹는 가장 흔한 원인이다. 80GB 카드를 잡고 12GB만 쓰는 작업이 대기열의
절반이면, 카드를 늘리는 것보다 요청을 바로잡는 편이 훨씬 싸다. 사용자에게 벌을 주기보다 지난
실행의 실제 사용량을 작업 종료 메일이나 대시보드에 자동으로 보여 주는 쪽이 효과가 있다.

## Slurm과 Kubernetes를 함께 쓰기

학습은 Slurm으로, 추론 서비스는 Kubernetes로 운영하는 구성이 흔하다. 문제는 두 스케줄러가 같은
노드를 모르고 각자 배정할 때 생긴다. 같은 GPU를 둘 다 자기 것으로 알면 충돌한다.

현실에서 쓰는 방법은 셋이다.

| 방식 | 내용 | 적합한 상황 |
| --- | --- | --- |
| 물리 분리 | 노드 풀을 아예 나눈다 | 가장 단순하고 사고가 없다. 활용률은 손해다 |
| 시간 분리 | 낮에는 추론, 밤에는 학습으로 노드를 옮긴다 | 수요 패턴이 뚜렷할 때 |
| 단일 스케줄러 | 한쪽으로 통일하고 다른 워크로드를 얹는다 | 운영 인력이 한 스택에 익숙할 때 |

동적으로 노드를 옮기는 구성은 매력적이지만 상태 전이 중 실패를 다루기가 까다롭다. 처음에는
물리 분리로 시작하고, 활용률 측정치가 분리 비용을 넘어설 때 옮기는 편이 안전하다.

분리 비용은 계산할 수 있다. 노드를 나누면 각 풀의 대기열이 짧아지는 대신, 한쪽이 놀 때 다른
쪽이 그 자원을 쓰지 못한다. 하루 단위로 두 풀의 유휴 GPU 시간을 각각 재고, 그 값이 서로
어긋나는 시간대가 있는지 본다. 학습 수요가 밤에 몰리고 추론 수요가 낮에 몰린다면 옮길 값어치가
있다. 두 수요의 성수기가 겹치면 옮겨도 얻는 것이 없고 이동 중 유휴 시간만 늘어난다.

```bash
# Slurm 풀의 유휴 GPU 시간을 하루 단위로 뽑는다
sreport cluster utilization start=2026-08-01 end=2026-08-08 -t hours

# Kubernetes 풀의 미할당 GPU 수를 같은 기간에 대해 본다
kubectl get nodes -l pool=inference -o json | \
  python -c "import json,sys; d=json.load(sys.stdin);
print(sum(int(n['status']['allocatable'].get('nvidia.com/gpu',0)) for n in d['items']))"
```

노드를 어떻게 나누고 무엇을 함께 쓰는지, 옮기는 절차를 어떻게 짜는지는 모듈 07의 공존 항목에
정리해 두었다.

## 학습과 추론을 함께 돌릴 때

같은 GPU를 쓰지만 학습과 추론은 요구가 정반대다. 이 차이를 모르고 한 대기열에 섞으면 둘 다
나빠진다.

| 항목 | 학습 | 추론 |
| --- | --- | --- |
| 수명 | 몇 시간에서 며칠, 끝이 있다 | 상시 떠 있다, 끝이 없다 |
| 지연 요구 | 스텝 지연은 상관없고 처리량이 목표 | 요청당 응답 지연이 목표 |
| 자원 형태 | 여러 GPU를 한꺼번에, 통신이 촘촘 | 대개 소수 GPU, 요청 단위로 독립 |
| 부하 | 시작하면 꾸준히 높다 | 트래픽 따라 오르내린다 |
| 실패 처리 | 체크포인트에서 재시작 | 재시도하거나 다른 복제본으로 |

문제는 자원을 채우는 방향이 서로 반대라는 데서 나온다. 학습은 처리량이 목표라 GPU를 최대한
채워야 이득이고, 노는 시간이 곧 손해다. 추론은 응답 지연이 목표라 트래픽이 튈 여유를 늘 남겨
둬야 한다. 사용률 90%로 돌던 추론 서비스에 요청이 몰리면 큐가 쌓여 지연이 무너진다. 한쪽은
채우라 하고 다른 쪽은 비우라 하니, 한 자원 풀에서 두 목표를 같이 만족시킬 수 없다.

섞을 때 생기는 구체적 문제도 있다. 학습 작업이 GPU 메모리를 거의 다 잡으면 추론 복제본이 같은
카드에 못 들어간다. 학습의 집합 통신이 NVLink를 포화시키면 같은 노드의 추론 응답 지연이 튄다.
반대로 추론 트래픽이 몰려 카드를 오래 쥐면 학습 스텝이 밀린다. 서로의 꼬리 지연을 키우는 관계다.

분리 기준은 지연 보장이 필요한지로 가른다. 응답 지연에 약속(SLO)이 걸린 추론은 전용 자원에 두고
여유를 남긴다. 지연 약속이 없는 배치 추론이나 야간 대량 채점은 학습과 같은 풀에 넣어도 된다.

```bash
# 추론은 지연 여유를 남기려 노드당 복제본 수를 묶는다
kubectl scale deploy/serving --replicas=6
# 학습은 남은 노드를 채워 쓰도록 빈팩으로 배치한다
sbatch --gres=gpu:8 --constraint=train_pool train.sh
```

시간대별로 자원을 옮기는 정책이 흔한 절충이다. 추론 트래픽이 낮에 몰리고 학습 수요가 밤에 몰리면,
밤에는 추론 복제본을 줄이고 그 노드를 학습 풀로 돌린다.

```bash
# 밤 시간대에 추론을 줄이고 노드를 학습 파티션으로 넘기는 크론
0 22 * * * kubectl scale deploy/serving --replicas=2 && \
           scontrol update nodename=gpu[09-16] state=resume
0 8  * * * scontrol update nodename=gpu[09-16] state=drain reason=serving && \
           kubectl scale deploy/serving --replicas=6
```

이 방식의 한계는 셋이다. 트래픽 패턴이 뚜렷해야 하고, 옮기는 순간 상태 전이 중 실패를 다뤄야
하며, 넘기는 노드에서 돌던 작업을 안전하게 비워야 한다. 학습이 체크포인트 없이 돌고 있으면 노드를
회수하는 순간 계산이 날아간다. 트래픽이 예측을 벗어나 낮에도 학습 수요가 크면 옮길 값어치가
사라지고 전이 비용만 남는다. 두 수요의 성수기가 겹치는 클러스터라면 시간 이동이 아니라 물리
분리가 낫다.

## 자원을 자동으로 늘리고 줄이기

대기열이 길면 노드를 늘리고, 놀면 줄이는 것이 오토스케일링이다. CPU 웹 서비스에서는 흔한
방식이지만 GPU 워크로드에서는 어렵다. 늘리는 데 걸리는 시간과 줄일 때 잃는 것이 둘 다 크다.

늘리는 쪽이 느린 이유가 여러 겹이다.

| 단계 | 걸리는 시간 | 왜 |
| --- | --- | --- |
| 노드 준비 | 수 분 | 클라우드 인스턴스 생성과 부팅 |
| 드라이버 초기화 | 수십 초에서 수 분 | GPU 드라이버·fabric manager 기동 |
| 이미지 내려받기 | 수 분에서 수십 분 | 학습 이미지가 수 GB에서 수십 GB |
| 상태 준비 | 경우에 따라 | 데이터셋 마운트·워밍업 |

새 노드 하나가 실제 일을 받기까지 십수 분이 걸리기도 한다. 대기열이 튀는 순간에 맞춰 늘려도
노드가 붙을 즈음이면 이미 대기가 빠져 있거나, 반대로 더 쌓여 있다.

줄이는 쪽은 상태를 가진 학습 작업 때문에 어렵다. 웹 서버는 요청이 끝나면 언제 꺼도 되지만, 학습은
며칠째 돌던 상태가 GPU 메모리에 있어 그냥 끄면 계산이 날아간다. 축소는 돌던 작업을 어떻게
다루느냐가 핵심이다. 체크포인트가 있으면 저장하고 회수하고, 없으면 작업이 끝날 때까지 그 노드는
축소 대상에서 뺀다. 대개 유휴 노드만 골라 끄고, 작업이 도는 노드에는 새 작업 배정을 막는(cordon)
쪽으로 뺀다.

```bash
# 도는 작업이 없는 노드만 축소 후보로 표시한다
kubectl cordon gpu-node-42              # 새 배정을 막는다
kubectl drain gpu-node-42 --ignore-daemonsets --grace-period=120
# Slurm은 작업이 빠진 뒤 전원을 내리는 상태로 돌린다
scontrol update nodename=gpu-node-42 state=power_down
```

확장 판단의 지표는 두 갈래다. 대기열 길이 기반은 밀린 작업 수와 그 작업이 요구하는 GPU 수를 보고
늘린다. 앞을 내다보기 좋지만 짧게 튀는 대기에 반응하면 노드를 켰다 끄기를 반복한다. 사용률 기반은
지금 GPU가 얼마나 도는지를 보고 줄인다. 낭비를 잡기 좋지만 이미 밀린 뒤에야 늘려 늦다. 현실에서는
늘릴 때는 대기열, 줄일 때는 사용률을 보는 식으로 섞어 쓴다.

```bash
# 대기 중인 작업이 요구하는 GPU 총량을 뽑아 확장 판단에 쓴다
squeue -t pending -h -o "%b" | grep -oP 'gpu:\K[0-9]+' | paste -sd+ | bc
# 유휴 상태가 이어진 노드를 축소 후보로 센다
sinfo -N -h -t idle -o "%N %t"
```

축소는 늘 쿨다운(cooldown)을 둔다. 늘린 직후에는 일정 시간 축소를 막아, 노드를 붙이자마자 다시
떼는 진동을 없앤다. 대기열 기반 확장에도 최소 유지 시간을 걸어 짧은 스파이크에 반응하지 않게 한다.

클라우드 버스팅은 온프레미스가 꽉 찼을 때 클라우드로 넘치게 하는 방식인데, 데이터 지역성이 발목을
잡는다. 학습 데이터가 사내 스토리지에 있으면 클라우드 노드가 매 스텝 데이터를 원격으로 당겨 와
네트워크가 병목이 되고, 붙는 대역폭이 GPU 속도를 못 따라가 값비싼 클라우드 GPU가 논다. 버스팅으로
넘길 작업은 데이터를 미리 클라우드 쪽으로 복제해 두거나, 데이터 이동이 적은 작업으로 고르는 편이
낫다. 이동 비용과 클라우드 GPU 단가를 견줘, 넘겨서 이득인 작업만 넘긴다.

## 여러 종류의 가속기가 섞인 클러스터

클러스터를 여러 해에 걸쳐 늘리면 세대가 다른 GPU가 섞인다. A100 노드에 H100 노드가 더해지고,
나중에는 GPU와 NPU가 한 대기열에 든다. 이때 아무 카드나 잡아 주면 성능이 튄다.

분산 학습에서 세대를 섞으면 안 되는 이유는 집합 통신이 가장 느린 랭크를 기다리기 때문이다. H100
네 장에 A100 네 장을 붙여 여덟 장으로 학습하면, 매 스텝 배리어에서 H100이 A100을 기다려 전체가
A100 속도로 떨어진다. 빠른 카드의 값을 못 쓰고 느린 카드에 맞춰지니, 섞는 순간 비싼 H100이 A100처럼
도는 셈이다. 그래서 한 학습 작업 안의 카드는 같은 종류로 묶어야 한다.

Slurm에서는 GRES 타입으로 종류를 나눠 표현하고, 요청할 때 타입을 못 박아 같은 종류만 잡게 한다.

```ini
# gres.conf, 세대를 타입으로 구분한다 (노드마다 해당 카드만 적는다)
Name=gpu Type=h100 File=/dev/nvidia[0-7]
Name=gpu Type=a100 File=/dev/nvidia[0-7]
```

```bash
sbatch --gres=gpu:h100:8 train.sh       # H100 여덟 장만 잡는다
sbatch --gres=gpu:a100:8 train.sh       # A100 여덟 장만 잡는다
# 타입을 안 적으면 섞일 수 있으니 작업 템플릿에서 늘 못 박는다
```

한 작업이 한 종류만 잡아도, 그 작업이 여러 노드에 걸칠 때 노드 간 세대가 섞이면 같은 문제가 난다.
노드 자체에 특성(feature)을 붙이고 제약(constraint)으로 같은 특성 노드만 고르게 한다.

```ini
# slurm.conf, 노드에 세대 특성을 붙인다
NodeName=gpu[01-08] Gres=gpu:h100:8 Feature=h100,nvlink4
NodeName=gpu[09-16] Gres=gpu:a100:8 Feature=a100,nvlink3
```

```bash
sbatch --constraint=h100 --nodes=4 train.sh    # H100 노드에서만 4대를 잡는다
```

세대별로 파티션을 나눌지, 한 파티션에 두고 제약으로 풀지는 규모와 운영 손으로 정한다.

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 파티션 분리 | 경계가 뚜렷하고 사용자가 고르기 쉽다 | 한쪽이 놀아도 다른 쪽이 못 쓴다 |
| 단일 파티션 + 제약 | 자원을 합쳐 두고 유연하게 쓴다 | 사용자가 제약을 빠뜨리면 섞인다 |

세대가 둘뿐이고 사용자가 어느 카드를 쓰는지 뚜렷이 알아야 하면 파티션을 나누는 편이 헷갈림이
적다. 세대가 여럿이고 조합이 자주 바뀌면 제약으로 푸는 편이 자원을 덜 놀린다. 어느 쪽이든 작업
템플릿에 타입과 제약을 기본으로 박아, 사용자가 빠뜨려 섞이는 사고를 코드로 막는다. GPU와 NPU가
섞인 클러스터는 프레임워크 자체가 다른 경우가 많아, 아예 다른 대기열로 갈라 두는 편이 낫다.

## 대기열을 나누는 기준

파티션을 어떻게 자를지가 사용자 경험을 크게 바꾼다. 하나로 두면 짧은 작업이 긴 작업 뒤에서
하염없이 기다리고, 너무 잘게 나누면 어느 쪽은 놀고 어느 쪽은 밀린다.

| 기준 | 예 | 얻는 것 |
| --- | --- | --- |
| 실행 시간 | short 4시간, long 72시간 | 짧은 작업의 응답이 빨라진다 |
| 하드웨어 | a100, h100, cpu-only | 필요한 자원만 정확히 요청하게 된다 |
| 조직 | team-a, team-b, shared | 팀별 보장량을 만들 수 있다 |
| 성격 | interactive, batch | 디버깅용 세션이 학습 뒤에 밀리지 않는다 |

파티션은 겹쳐도 된다. 같은 노드를 여러 파티션에 넣고 우선순위와 시간 한도를 다르게 주면,
평소에는 공유하다가 필요할 때 특정 팀이 앞서게 만들 수 있다.

```ini
PartitionName=interactive Nodes=gpu[01-02] MaxTime=02:00:00 Priority=100
PartitionName=short  Nodes=gpu[01-08] MaxTime=04:00:00 Priority=50
PartitionName=long   Nodes=gpu[01-16] MaxTime=72:00:00 Priority=10
```

## 활용률을 읽는 법

활용률이 높다고 좋은 상태는 아니다. 100퍼센트에 붙어 있으면 대기열이 계속 쌓인다는 뜻이고,
낮으면 자원이 논다. 무엇을 재는지도 구분해야 한다.

- 할당률은 스케줄러가 노드를 작업에 배정한 비율이다. 그 작업이 실제로 계산하는지는 모른다.
- GPU 사용률은 커널이 돌던 시간의 비율이다. 배정만 받고 노는 작업을 잡아낸다.
- 대기 시간은 사용자가 체감하는 값이다. 활용률과 반대 방향으로 움직인다.

세 값을 같이 놓아야 판단이 선다. 할당률이 90퍼센트인데 GPU 사용률이 30퍼센트라면 자원을
잡아만 두고 쓰지 않는 작업이 있다는 뜻이고, 이때는 노드를 늘리는 대신 그 작업을 찾는 편이
빠르다.

```bash
sacct -a -S 2026-01-01 -E now --format=JobID,Account,AllocGRES,Elapsed,State -X | head
sreport cluster Utilization Start=2026-01-01 End=now
```

배정만 받고 노는 작업은 두 값을 맞춰 보면 찾아진다. 작업 번호별로 잡은 GPU 수와 그 GPU들의
실제 사용률을 같이 놓는다.

```bash
# 지금 도는 작업이 잡은 GPU 수
squeue -t running -o "%i %u %b %N" -h

# 그 노드들의 GPU 사용률
srun -w "$(squeue -t running -h -j 12345 -o %N)" --overlap \
     nvidia-smi --query-gpu=index,utilization.gpu --format=csv,noheader
```

몇 시간째 사용률이 한 자릿수인 작업은 대개 셋 중 하나다. 대화형 세션을 열어 두고 자리를 비웠거나,
디버거 앞에서 멈춰 있거나, 데이터를 기다리고 있다. 앞의 둘은 정책으로 줄인다. 대화형 세션에
짧은 시간 제한을 걸고, 유휴 상태가 일정 시간 이어지면 알림을 보낸다.

목표값은 워크로드 성격에 따라 다르다. 하나의 숫자를 모든 파티션에 들이대면 잘못된 결정을 한다.

| 파티션 성격 | 적당한 할당률 | 이유 |
| --- | ---: | --- |
| 대규모 학습 전용 | 85~95% | 큰 작업이 들어갈 빈자리를 남겨 둬야 한다 |
| 일반 배치 | 90~98% | 백필로 틈을 메울 수 있다 |
| 대화형과 디버그 | 40~60% | 기다리지 않고 바로 잡히는 것이 목적이다 |
| 추론 서비스 | 50~70% | 트래픽이 튈 여유를 둬야 한다 |

대화형 파티션의 낮은 활용률을 낭비로 보고 없애면 사용자가 배치 파티션에서 대화형 세션을 열기
시작한다. 그러면 큰 작업이 들어갈 자리가 사라지고 전체 처리량이 떨어진다. 활용률은 파티션마다
따로 읽는다.

## 정책을 바꿀 때

스케줄링 정책을 한 번에 크게 바꾸면 무엇 때문에 달라졌는지 알 수 없게 된다. 하나씩 바꾸고
효과를 확인한다.

바꾸기 전 값은 기록해 둔다. `scontrol show config` 출력을 저장해 두면 되돌릴 근거가 된다.
변경 뒤에는 대기 시간 분포와 활용률을 같은 기간으로 비교한다. 평균만 보면 소수의 긴 대기가
묻히므로 중앙값과 상위 백분위를 함께 본다.

사용자에게 알리는 것도 정책의 일부다. 우선순위 규칙이 바뀌면 같은 작업이 어제와 다른 시각에
시작하는데, 공지 없이 그러면 장애로 오해받는다.

바꾸기 전에 지금 값을 남기고, 무엇을 보고 판단할지 먼저 정한다.

```bash
scontrol show config > /var/backups/slurm-config-$(date +%F).txt
sacctmgr dump cluster > /var/backups/slurm-assoc-$(date +%F).cfg

# 최근 2주 대기 시간 분포. 평균이 아니라 분포를 본다
sacct -a -S now-14days -X -o JobID,Partition,Submit,Start,Elapsed,State \
      --parsable2 > /tmp/jobs.csv
```

```python
import csv, statistics
from datetime import datetime

waits = []
with open("/tmp/jobs.csv") as f:
    for row in csv.DictReader(f, delimiter="|"):
        if row["Start"] in ("Unknown", "None", ""):
            continue
        fmt = "%Y-%m-%dT%H:%M:%S"
        waits.append((datetime.strptime(row["Start"], fmt)
                      - datetime.strptime(row["Submit"], fmt)).total_seconds() / 60)

waits.sort()
print(f"중앙값 {statistics.median(waits):.0f}분  "
      f"90퍼센타일 {waits[int(len(waits) * 0.9)]:.0f}분  "
      f"99퍼센타일 {waits[int(len(waits) * 0.99)]:.0f}분")
```

평균만 보면 소수의 긴 대기가 묻힌다. 불만은 평균이 아니라 상위 백분위에서 나온다. 중앙값이
줄었는데 99퍼센타일이 늘었다면 그 정책은 다수를 조금 낫게 만들고 소수를 크게 나쁘게 만든 것이다.

| 바꾸는 것 | 효과가 도는 데 걸리는 시간 | 함께 볼 지표 |
| --- | --- | --- |
| 파티션 시간 제한 | 즉시 | 백필로 들어간 작업 수, 대기 시간 분포 |
| fairshare 반감기 | 며칠 | 계정별 사용량 편차 |
| 우선순위 가중치 | 대기열이 한 바퀴 도는 시간 | 대기 시간 상위 백분위 |
| 선점 정책 | 즉시 | 선점당한 작업 수와 그중 재시작 실패 수 |
| QoS 동시 실행 한도 | 즉시 | 특정 사용자의 대기 작업 수 |

한 번에 하나만 바꾸고 최소 한 주는 둔다. 대기열은 주 단위로 패턴이 도는 경우가 많아 하루
이틀 값으로 판단하면 요일 효과를 정책 효과로 착각한다. 되돌릴 조건도 미리 정해 둔다. 99퍼센타일
대기가 어느 값을 넘으면 되돌린다는 식으로 숫자를 적어 두면 논쟁이 줄어든다.
