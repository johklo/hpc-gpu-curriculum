GPU 클러스터는 사는 순간이 아니라 돌리는 내내 돈이 나간다. 한 장이 시간당 얼마인지 계산하는
방법, 사서 쓸지 빌려 쓸지 정하는 기준, 이미 산 자원을 덜 낭비하는 방법을 정리한다.

## GPU 한 시간의 원가

자원 요청을 줄여 달라고 말하려면 숫자가 있어야 한다. GPU 한 장의 시간당 원가는 구매 비용만으로
나오지 않는다.

![장비 감가가 3분의 2를 차지하고 전력과 냉각과 운영이 나머지를 채운다](img/cost-stack.svg)

| 항목 | 잡는 법 | 8장 노드 한 대 기준 예시 |
| --- | --- | ---: |
| 장비 감가 | 구매가를 상각 기간으로 나눈다 | 3억 원을 4년으로 나눠 연 7,500만 원 |
| 전력 | 소비 전력 곱하기 가동 시간 곱하기 단가 | 10 kW, 연 8,760시간, kWh당 120원이면 연 1,050만 원 |
| 냉각 | 전력의 30에서 50퍼센트를 더 잡는다 | 연 400만 원 |
| 상면과 랙 | 랙 단위 임대료를 노드 수로 나눈다 | 연 300만 원 |
| 네트워크 | 스위치와 케이블 감가를 노드 수로 나눈다 | 연 500만 원 |
| 스토리지 | 공유 스토리지 감가를 노드 수로 나눈다 | 연 600만 원 |
| 운영 인력 | 인건비를 관리하는 노드 수로 나눈다 | 연 800만 원 |

합치면 연 1억 1,150만 원이고 노드 한 대에 GPU가 8장이므로 장당 연 1,394만 원이다. 8,760시간으로
나누면 **시간당 약 1,590원**이다. 이 값이 가동률 100퍼센트를 가정한 값이라는 점이 중요하다.
실제 가동률이 60퍼센트라면 실제로 쓴 한 시간의 원가는 2,650원으로 올라간다.

```python
# 가동률이 원가를 어떻게 바꾸는지
annual = 111_500_000        # 노드 한 대의 연간 총비용
gpus, hours = 8, 8_760

for util in (0.4, 0.6, 0.8, 0.95):
    cost = annual / gpus / (hours * util)
    print(f"가동률 {util:.0%}  실사용 시간당 {cost:,.0f}원")
```

가동률을 60퍼센트에서 80퍼센트로 올리는 일은 GPU를 25퍼센트 더 사는 것과 같은 효과를 낸다.
장비를 늘리기 전에 활용률부터 보라는 말이 여기서 나온다.

## 사서 쓸 것인가 빌려 쓸 것인가

같은 GPU를 클라우드에서 빌리면 시간당 단가는 자체 구축보다 몇 배 높다. 그런데도 빌리는 쪽이
싼 경우가 있다. 기준은 가동률과 기간이다.

| 조건 | 유리한 쪽 |
| --- | --- |
| 24시간 내내 돌릴 일이 있고 3년 이상 쓴다 | 자체 구축 |
| 수요가 몇 달에 한 번 몰린다 | 빌린다 |
| 어떤 GPU가 필요한지 아직 모른다 | 빌려서 재 본다 |
| 데이터를 밖으로 내보낼 수 없다 | 자체 구축 |
| 운영할 사람이 없다 | 빌린다. 관리형이면 더 그렇다 |
| 몇 주짜리 실험이 불규칙하게 생긴다 | 기본은 자체, 넘치는 만큼만 빌린다 |

손익분기는 계산된다. 자체 구축의 실사용 시간당 원가가 2,650원이고 클라우드가 시간당 6,000원
이라면, 클라우드를 연 몇 시간 쓸 때까지 싼지 나온다.

```python
own_annual = 111_500_000 / 8        # GPU 한 장의 연간 자체 비용
cloud_hourly = 6_000
breakeven = own_annual / cloud_hourly
print(f"연 {breakeven:,.0f}시간 미만이면 빌리는 쪽이 싸다")
print(f"가동률로는 {breakeven / 8760:.0%}")
```

연 2,323시간, 가동률 27퍼센트가 갈림선이다. 이보다 적게 쓸 자원이면 사지 않는 편이 낫다.
자체 구축을 정당화하려면 최소한 이 선을 넘게 쓸 계획이 있어야 한다.

계산에서 빠뜨리기 쉬운 항목이 몇 가지 있다. 자체 구축 쪽에서는 도입까지 걸리는 기간과 그동안
일을 못 하는 손실, 그리고 장비를 다 채우기 전까지의 낮은 가동률이 빠진다. 빌리는 쪽에서는
데이터를 넣고 빼는 요금과 스토리지 상시 비용이 빠진다. 계산이 GPU 시간 단가로만 이루어지면
양쪽 다 실제보다 싸 보인다.

| 자주 빠지는 항목 | 어느 쪽 | 크기 |
| --- | --- | --- |
| 도입 기간 동안의 기회 손실 | 자체 | 발주에서 가동까지 3개월에서 9개월 |
| 초기 저가동 구간 | 자체 | 첫 분기 가동률이 절반 아래인 경우가 흔하다 |
| 데이터 내보내기 요금 | 클라우드 | 학습 결과와 로그를 가져올 때마다 든다 |
| 상시 스토리지 | 클라우드 | 계산을 안 해도 데이터가 있으면 계속 나간다 |
| 유휴 예약 자원 | 클라우드 | 약정을 크게 잡으면 안 쓰는 자리를 산다 |
| 운영 인력 학습 기간 | 양쪽 | 첫 6개월은 사람이 익히는 비용이 든다 |

## 조달에서 걸리는 것들

GPU는 돈이 있다고 바로 오지 않는다. 계획에 반드시 기간을 넣어야 한다.

| 단계 | 걸리는 시간 | 걸리는 지점 |
| --- | --- | --- |
| 사양 확정과 견적 | 2주에서 6주 | 어떤 세대를 살지, 네트워크를 어디까지 갖출지 |
| 발주와 물량 배정 | 1개월에서 6개월 | 수요가 몰리면 배정 자체가 대기다 |
| 입고와 상면 준비 | 2주에서 2개월 | 전력과 냉각 공사가 장비보다 오래 걸리기도 한다 |
| 설치와 반입 검사 | 2주에서 1개월 | 초기 불량 교체가 여기서 나온다 |
| 가동 | | 발주에서 여기까지 3개월에서 9개월 |

기간이 이렇게 길기 때문에 필요해진 뒤에 발주하면 이미 늦다. 학습 계획에서 필요한 규모를
역산해 미리 잡아야 한다. 반대로 너무 미리 잡으면 세대가 바뀌어 손해를 본다.

전력과 냉각이 장비보다 먼저 상한이 되는 경우가 많다. GPU 노드 한 대가 10 kW를 쓰면 랙 하나에
서너 대밖에 못 넣는다. 기존 전산실은 랙당 5에서 10 kW를 가정해 지어진 곳이 많아, 장비는 살 수
있어도 넣을 자리가 없는 상황이 생긴다. 구매 검토와 동시에 확인할 것이 있다.

- 랙당 공급 가능한 전력과 현재 사용량
- 냉각 방식과 배기 온도 한계. 공랭으로 감당되는 밀도인지
- 바닥 하중. GPU 노드는 무겁다
- 배전반 여유와 증설 공사 기간
- 네트워크 포트 수. GPU 노드 한 대가 여러 포트를 쓴다

계약할 때 미리 정해 둘 것도 있다. 초기 불량 교체 기간, 예비 부품 보유 수량, 장애 대응 시간,
드라이버와 펌웨어 지원 기간이 여기 해당한다. 반입 검사에서 불량이 나왔을 때 어떻게 처리할지가
계약서에 없으면 협의에 몇 주가 든다.

## 클라우드에서 GPU를 확보하는 방식

같은 GPU라도 어떤 계약으로 잡느냐에 따라 단가와 안정성이 달라진다.

| 방식 | 단가 | 중간에 회수되는가 | 맞는 워크로드 |
| --- | --- | --- | --- |
| 온디맨드 | 기준가 | 없다 | 짧고 급한 작업 |
| 예약 · 약정 | 기준가의 40에서 60퍼센트 | 없다 | 상시 도는 기반 부하 |
| 스팟 · 선점형 | 기준가의 20에서 40퍼센트 | 있다. 몇 분 전에 통보 | 체크포인트가 있는 학습 |
| 전용 용량 예약 | 기준가 이상 | 없다. 자리를 미리 잡는다 | 시작 시각이 정해진 대형 학습 |

스팟은 학습에 쓸 수 있다. 조건은 하나다. 회수 통보를 받고 체크포인트를 남길 수 있어야 한다.
통보에서 종료까지 주어지는 시간은 대개 2분 안팎이라, 그 안에 저장이 끝나야 한다.

```python
import signal, sys

def on_reclaim(signum, frame):
    save_checkpoint(step, async_write=False)   # 2분 안에 끝나야 한다
    sys.exit(0)

signal.signal(signal.SIGTERM, on_reclaim)
```

체크포인트 저장에 49초가 걸리는 작업이라면 통보 시간 안에 들어간다. 5분이 걸린다면 스팟에
올리면 안 된다. 저장 시간이 스팟 사용 가능 여부를 정한다.

기반 부하는 약정으로 깔고, 그 위를 스팟으로 덮고, 급한 것만 온디맨드로 받는 구성이 대체로
싸다. 약정 비율은 지난 1년의 최저 사용량 근처로 잡는다. 그보다 많이 약정하면 안 쓰는 자리를
사는 셈이 된다.

```bash
# 지난 1년 중 매달 최저 동시 사용 GPU 수를 뽑아 약정 규모의 근거로 쓴다
sacct -a -S now-365days -X -o Start,End,AllocTRES --parsable2 \
  | python analyze_concurrency.py --percentile 10
```

## 낭비를 찾아내는 지표

비용을 줄이는 가장 싼 방법은 이미 산 자원을 덜 놀리는 것이다. 낭비는 몇 가지 모양으로 나타나고
각각 다른 지표에 걸린다.

| 낭비의 모양 | 걸리는 지표 | 대응 |
| --- | --- | --- |
| 자리를 잡고 놀린다 | 할당률은 높은데 GPU 사용률이 낮다 | 유휴 작업을 찾아 알리고 정책으로 제한한다 |
| 필요보다 크게 요청한다 | 요청 메모리 대비 실사용 메모리 | 지난 실행의 실사용량을 보여 준다 |
| 대화형 세션을 켜 두고 나간다 | 사용률 한 자릿수가 몇 시간 이어진다 | 시간 제한과 유휴 종료 |
| 실패한 작업을 반복 제출한다 | 같은 사용자의 짧은 실패 작업이 반복된다 | 실패 원인을 알려 준다 |
| 체크포인트가 쌓인다 | 스토리지 사용량이 단조 증가한다 | 보존 개수 정책 |
| 세대가 낡은 노드가 남아 있다 | 노드별 처리량 대비 전력 | 교체 시점 계산 |

유휴 작업 하나를 찾아 정리하는 값어치도 계산할 수 있다. GPU 8장을 12시간 놀린 작업 하나는
시간당 2,650원 기준으로 25만 4천 원이다. 이런 작업이 한 달에 스무 건이면 연 6,100만 원이다.
노드 한 대 값의 절반이 넘는다.

```bash
# 사용률이 5% 아래로 30분 넘게 이어진 작업을 뽑는다
cat <<'PROMQL'
avg_over_time(DCGM_FI_DEV_GPU_UTIL[30m]) < 5
  and on(hostname) slurm_job_running > 0
PROMQL
```

찾아낸 뒤의 처리는 단계를 둔다. 바로 죽이면 사용자가 우회하는 방법을 배운다.

- 30분 유휴가 확인되면 사용자에게 알린다. 작업 번호와 사용률을 함께 보낸다.
- 2시간이 이어지면 다시 알리고 관리자에게도 보낸다.
- 대화형 파티션에 한해 4시간 유휴면 종료한다. 배치 작업은 자동 종료하지 않는다.

배치 작업을 자동 종료하지 않는 이유는 사용률이 낮아도 정당한 경우가 있어서다. 체크포인트를
쓰는 중이거나, 데이터 전처리 구간이거나, 평가를 도는 중일 수 있다. 대화형 세션은 사람이 자리를
비운 것이 거의 확실하므로 다르게 다룬다.

과다 요청은 요청과 실사용의 비율로 잡는다. 지난 30일 작업을 모아 비율 분포를 보면 어느 팀이
얼마나 크게 잡는지 드러난다.

```bash
sacct -a -S now-30days -X --parsable2 \
      -o JobID,User,Account,ReqTRES,MaxRSS,Elapsed,State \
  | awk -F'|' '$7=="COMPLETED"' > /tmp/usage.psv
```

비율이 3배를 넘는 작업이 많은 팀에는 지난 실행의 실제 사용량을 자동으로 보내 준다. 대개는
몰라서 크게 잡는 것이지 일부러 그러는 것이 아니다.

## 낡은 노드를 언제 바꿀 것인가

GPU는 고장 나기 전에 경제적으로 먼저 수명이 끝난다. 새 세대가 같은 전력으로 몇 배를 하기
때문이다. 교체 판단은 처리량당 전력으로 한다.

| 세대 | 학습 처리량(상대) | 노드 소비 전력 | 처리량당 전력(상대) |
| --- | ---: | ---: | ---: |
| 이전 세대 | 1.0 | 6.5 kW | 1.00 |
| 현 세대 | 2.8 | 10.2 kW | 0.56 |
| 차기 세대 | 4.5 | 13.0 kW | 0.44 |

전력 단가와 상면 비용이 높은 곳일수록 교체 시점이 앞당겨진다. 랙 전력이 상한이라면 더 그렇다.
같은 랙에 넣을 수 있는 노드 수가 정해져 있으므로, 노드당 처리량이 곧 랙당 처리량이 된다.

낡은 노드를 버리지 않고 쓰는 방법도 있다. 대화형 개발, 소규모 파인튜닝, 데이터 전처리, 추론
같은 작업은 최신 세대가 필요하지 않다. 별도 파티션으로 내려 두고 대형 학습만 새 노드로 받는
구성이 흔하다. 다만 노드 종류가 늘면 운영 부담도 늘어난다는 점을 계산에 넣어야 한다.

교체를 미루는 비용도 계산된다. 이전 세대 노드가 같은 일을 하는 데 전력을 1.8배 쓴다면, 그
차액이 새 노드 값을 넘는 시점이 나온다.

```python
old_kw, new_kw = 6.5, 10.2          # 노드당 소비 전력
old_tp, new_tp = 1.0, 2.8           # 상대 처리량
price_kwh, node_price = 120, 300_000_000

# 같은 처리량을 내는 데 드는 연간 전력비를 견준다
old_cost = (old_kw / old_tp) * 8760 * price_kwh
new_cost = (new_kw / new_tp) * 8760 * price_kwh
saving = old_cost - new_cost
print(f"연간 전력비 절감 {saving:,.0f}원, 회수까지 {node_price / saving:.1f}년")
```

전력비만으로 4년 안에 회수되지 않는 경우가 대부분이다. 교체를 정당화하는 것은 대개 전력이
아니라 랙 자리와 처리 속도다. 랙 전력이 상한이라 노드를 더 못 넣는 상황이거나, 학습 한 번에
걸리는 시간이 사업 일정에 걸릴 때 교체가 값어치를 한다.

| 교체를 미룰 만한 조건 | 교체를 앞당길 조건 |
| --- | --- |
| 랙과 전력에 여유가 있다 | 랙 전력이 이미 상한이다 |
| 워크로드가 작은 모델 위주다 | 새 세대에서만 되는 정밀도나 용량이 필요하다 |
| 가동률이 낮다 | 가동률이 높아 대기열이 길다 |
| 유지보수 계약이 남아 있다 | 지원이 끝나 부품 조달이 어렵다 |

## 사용량을 보여 주고 나누기

여러 팀이 같은 클러스터를 쓰면 누가 얼마를 썼는지 보여 주는 것만으로 행동이 바뀐다. 요금을
실제로 걷지 않더라도 마찬가지다.

```bash
# 계정별 GPU 시간을 뽑는다. 청구서의 기초가 된다
sreport cluster AccountUtilizationByUser start=2026-07-01 end=2026-08-01 \
        -t hours --tres=gres/gpu

# 작업별로 요청 대비 실사용을 뽑아 과다 요청을 드러낸다
sacct -a -S 2026-07-01 -X --parsable2 \
      -o Account,User,JobID,ReqTRES,Elapsed,State
```

보여 주는 방식은 세 단계로 올린다.

- **보여 주기만 한다.** 월별 사용량과 원가 환산액을 팀에 전달한다. 강제는 없다. 이것만으로도
  과다 요청이 줄어든다.
- **몫을 정한다.** 팀별 GPU 시간 한도를 두고 넘으면 우선순위를 낮춘다. 공정 배분이 이 일을
  한다. 자원을 뺏지는 않는다.
- **실제로 청구한다.** 내부 정산까지 간다. 관리 비용이 크므로 조직이 그 값어치를 필요로 할
  때만 간다.

세 번째로 바로 뛰면 사용자가 자원을 숨기고 잡아 두는 행동을 배운다. 첫 단계에서 얻는 효과가
생각보다 크므로 순서대로 올린다.

무엇을 기준으로 나눌지도 정해야 한다. GPU 시간만 세면 메모리를 크게 잡고 GPU를 적게 쓰는
작업이 공짜가 된다. 자원 종류마다 가중치를 두고 하나의 값으로 합치는 방식이 흔하다.

| 자원 | 가중치 예시 | 근거 |
| --- | ---: | --- |
| GPU 시간 | 1.00 | 원가의 대부분을 차지한다 |
| CPU 코어 시간 | 0.01 | GPU 노드의 부속 자원이다 |
| 호스트 메모리 GB 시간 | 0.002 | 코어와 함께 잡히는 경우가 많다 |
| 공유 스토리지 TB 월 | 0.05 | 상시 점유라 시간이 아니라 기간으로 센다 |

가중치는 앞에서 계산한 원가 비율에서 뽑는다. 임의로 정하면 사용자가 납득하지 않는다. 계산
근거를 문서로 공개해 두면 조정 요청이 논쟁 대신 계산으로 바뀐다.

집계 주기는 월 단위가 무난하다. 주 단위는 잡음이 많고, 분기 단위는 행동이 바뀌기 전에 시간이
너무 흐른다. 월별 추이를 함께 보여 주면 자기 팀이 늘고 있는지 줄고 있는지 알 수 있다.

## 관리형과 직접 운영 사이

GPU를 서비스로 받는 선택지도 있다. 클러스터를 직접 세우지 않고 스케줄러와 관측까지 딸린
환경을 빌린다.

| 형태 | 무엇까지 남이 하나 | 남는 일 |
| --- | --- | --- |
| 장비 임대 | 하드웨어와 상면 | 운영체제부터 전부 |
| 관리형 클러스터 | 스케줄러와 드라이버까지 | 사용자 관리, 작업 정책 |
| 관리형 학습 플랫폼 | 작업 제출 인터페이스까지 | 코드와 데이터 |

관리형으로 갈수록 단가는 오르고 운영 인력은 준다. 인력 한 명의 연간 비용을 원가 계산에 넣으면
작은 클러스터에서는 관리형이 싼 경우가 자주 나온다. 노드가 수십 대를 넘어가면 반대가 된다.

섞어 쓰는 구성도 흔하다. 기반은 자체 클러스터로 두고, 데이터를 밖으로 낼 수 있는 작업만
외부로 보낸다. 이때 걸림돌은 대개 계산이 아니라 데이터다. 수백 TB를 옮기는 시간과 전송 비용이
계산 비용보다 클 수 있으므로, 옮길 데이터의 크기부터 확인하고 판단한다.

| 확인할 것 | 왜 |
| --- | --- |
| 옮길 데이터 크기와 전송 대역폭 | 전송에 며칠이 걸리면 탄력성이 사라진다 |
| 내보내기 요금 | 결과를 다시 가져올 때 드는 비용이 숨어 있다 |
| 데이터 반출 규정 | 기술 문제가 아니라 규정에서 막히는 경우가 많다 |
| 체크포인트 호환 | 양쪽에서 같은 체크포인트를 읽어야 오갈 수 있다 |
