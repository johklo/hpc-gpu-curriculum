자주 나오지만 정의가 흐릿한 채로 쓰이는 말을 모았다. 순서대로 읽기보다 막힐 때 찾아보는
용도다. 같은 말이 벤더마다 다르게 쓰이는 경우에는 그 차이도 적었다.

## 처음 보는 사람을 위한 최소 지도

학습 한 번이 도는 과정을 층으로 늘어놓으면 나머지 용어가 어디에 붙는지 보인다.

| 층 | 하는 일 | 여기서 나오는 말 |
| --- | --- | --- |
| 사용자 | 실행할 내용과 필요한 자원을 적어 제출한다 | 작업, 배치 스크립트, 대기열 |
| 스케줄러 | 언제 어느 노드에서 돌릴지 정한다 | Slurm, 파티션, 갱 스케줄링, 백필, fairshare |
| 노드 | 실제로 프로세스를 띄운다 | 랭크, CPU 코어, NUMA |
| 가속기 | 행렬 계산을 맡는다 | GPU, HBM, MIG, 사용률, MFU |
| 노드 간 연결 | 랭크끼리 값을 주고받는다 | InfiniBand, NCCL, 집합 통신, all-reduce |
| 스토리지 | 데이터와 체크포인트를 읽고 쓴다 | Lustre, OST, MDT, 스트라이핑 |

성능 이야기는 결국 셋 중 하나다. 계산이 느리거나, 값을 주고받느라 기다리거나, 데이터가 제때
오지 않는다. 어느 쪽인지부터 가리면 볼 지표가 정해진다.

숫자를 읽을 때 단위를 자주 혼동한다. 특히 네트워크는 비트, 저장과 메모리는 바이트를 쓴다.

| 표기 | 읽는 법 | 바꿔 보면 |
| --- | --- | --- |
| 200 Gb/s | 초당 200기가비트. 네트워크 표기다 | 8로 나눠 25 GB/s. 실효는 20 GB/s 안팎 |
| 25 GB/s | 초당 25기가바이트. 저장과 메모리 표기다 | 8을 곱해 200 Gb/s |
| 32 GT/s | 초당 32기가전송. PCIe 표기다 | 레인 수와 인코딩을 곱해야 바이트가 된다 |
| 989 TFLOP/s | 초당 989조 번의 부동소수점 연산 | 정밀도를 확인해야 한다. bf16과 fp8은 값이 다르다 |
| 80 GB | 메모리 용량 | 파라미터 하나에 2바이트면 400억 개가 들어간다 |

비슷해 보이지만 다른 짝도 미리 갈라 둔다.

| 헷갈리는 짝 | 차이 |
| --- | --- |
| 대역폭과 지연 | 한 번에 얼마나 보내느냐와 한 번 보내는 데 얼마나 걸리느냐 |
| GPU 사용률과 MFU | 커널이 돌고 있었느냐와 연산 유닛을 얼마나 채웠느냐 |
| 노드와 랭크 | 물리 서버 한 대와 그 위에서 도는 프로세스 하나 |
| 작업과 태스크 | 제출 단위 하나와 그 안에서 실제로 뜨는 프로세스 하나 |
| 용량과 대역폭 | 얼마나 담느냐와 얼마나 빨리 오가느냐. 스토리지는 이 둘을 따로 늘린다 |

## 가속기와 메모리

값이 어디에 있느냐가 속도를 정한다. 아래로 갈수록 넓고 느리다.

![레지스터에서 공유 스토리지까지 용량은 커지고 속도는 느려진다](img/memory-hierarchy.svg)

**Accelerator**  CPU가 잘 못하는 계산을 대신 맡는 장치를 통칭한다. GPU가 대표적이고 TPU,
NPU, FPGA도 여기 들어간다. CPU는 분기가 많은 순차 처리에 강하고 가속기는 같은 연산을 대량으로
반복하는 데 강하다. 행렬 곱이 딥러닝의 대부분을 차지하기 때문에 가속기가 이 분야를 가져갔다.

**HBM**  가속기 패키지 안에 쌓아 올린 메모리다. 일반 DDR을 기판에 늘어놓는 대신 실리콘을
수직으로 적층해 폭을 극단적으로 넓혔다. H100의 HBM3는 초당 3TB 안팎을 낸다. DDR5 채널 하나가
초당 수십 GB인 것과 비교하면 두 자릿수 차이다.

용량은 반대로 작다. 80GB나 141GB에서 끊기기 때문에 모델이 커지면 곧바로 벽에 부딪힌다.
GPU 메모리 부족은 대개 대역폭이 아니라 이 용량 때문에 생긴다.

**메모리 대역폭 한계**  연산 유닛이 놀고 있는데 성능이 안 나오면 대개 메모리에서 데이터를
못 받아오는 상태다. 연산량을 메모리 접근량으로 나눈 값을 산술 강도라 하고, 이 값이 낮은 연산은
아무리 좋은 가속기를 써도 대역폭에 묶인다. 요소별 덧셈이나 정규화가 여기 해당한다.

**ECC**  메모리 오류를 정정하는 기능이다. 1비트 오류는 고쳐서 넘어가고 2비트 오류는 고치지
못한 채 보고한다. 후자가 Xid 48로 나타난다. ECC를 끄면 가용 메모리가 조금 늘지만 학습 중
값이 조용히 틀어질 수 있어 계산 노드에서는 켜 둔다.

```bash
nvidia-smi --query-gpu=name,memory.total,memory.used --format=csv   # 용량과 사용량
nvidia-smi -q -d ECC | grep -A3 "Volatile"                          # ECC 오류 누적
```

## 연결과 통신

**PCIe**  CPU와 장치를 잇는 범용 버스다. 세대와 폭으로 속도가 정해지며 Gen5 x16이 양방향
합쳐 초당 128GB 수준이다. GPU 사이 통신을 PCIe로만 하면 NVLink 대비 몇 배 느리다.

**NVLink**  NVIDIA GPU끼리 직접 잇는 전용 링크다. PCIe를 거치지 않아 지연이 낮고 대역폭이
훨씬 크다. 링크 수만큼 대역이 늘어나며, `nvidia-smi topo -m`에서 `NV#`로 표시된다.

**NVSwitch**  NVLink를 스위칭해 노드 안의 모든 GPU가 서로 같은 대역으로 통신하게 만드는
칩이다. 이것이 없으면 GPU 쌍마다 거리가 달라져 어떤 조합을 받느냐에 따라 성능이 달라진다.

**InfiniBand**  노드 사이를 잇는 저지연 네트워크다. 이더넷과 달리 커널을 거치지 않고 애플리케이션
메모리에서 곧바로 전송하는 RDMA를 쓴다. 집합 통신 지연이 분산 학습 속도를 좌우하기 때문에
대규모 학습 클러스터의 기본 선택지다.

**RoCE**  이더넷 위에서 RDMA를 구현한 방식이다. 기존 이더넷 장비를 쓸 수 있는 대신 무손실
설정을 제대로 잡아야 한다. 흐름 제어가 어긋나면 성능이 InfiniBand보다 크게 떨어진다.

**GPUDirect RDMA**  네트워크 카드가 GPU 메모리에 직접 접근하게 하는 기능이다. CPU 메모리를
거치는 복사가 사라져 지연이 준다. 다만 NIC과 GPU가 같은 PCIe 스위치 아래 있어야 효과가 크다.

**NCCL**  NVIDIA의 집합 통신 라이브러리다. allreduce, allgather 같은 연산을 NVLink와
InfiniBand를 알아서 조합해 처리한다. `NCCL_DEBUG=INFO`를 켜면 어떤 경로를 골랐는지 로그에 남고,
여기서 `NET/Socket`이 보이면 RDMA를 못 쓰고 TCP로 돌고 있다는 뜻이다.

**집합 통신**  전체 프로세스가 함께 참여하는 통신이다. 데이터 병렬 학습에서 그래디언트를
평균 내는 allreduce가 대표적이고, 링이나 트리 형태로 구현한다. 프로세스 하나가 늦으면 전체가
기다리므로 가장 느린 노드가 속도를 정한다.

```bash
nvidia-smi topo -m              # GPU와 NIC이 어떤 링크로 붙어 있는지 표로 본다
ibstat                          # InfiniBand 포트 상태와 속도
lspci -vv | grep -i "LnkSta"    # PCIe 링크가 실제로 몇 세대 몇 레인으로 붙었는지
```

`nvidia-smi topo -m`의 표기가 곧 비용 순서다. `NV#`가 NVLink이고 숫자가 링크 수다. `PIX`는
같은 PCIe 스위치 아래, `NODE`는 같은 소켓 안, `SYS`는 소켓을 넘는 경로다. 오른쪽으로 갈수록
느리다.

## GPU 분할과 공유

**MIG**  GPU 한 장을 하드웨어에서 여러 인스턴스로 쪼갠다. 인스턴스마다 연산 유닛과 메모리가
물리적으로 나뉘어 한쪽 작업이 다른 쪽에 영향을 주지 않는다. 격리가 필요한 추론 서비스나
다중 사용자 환경에 맞는다. 나눈 뒤에는 개별 인스턴스가 작아지므로 큰 학습에는 쓰지 않는다.

**MPS**  여러 프로세스의 CUDA 커널을 하나의 컨텍스트에서 함께 돌린다. 컨텍스트 전환 비용이
줄어 작은 커널을 많이 던지는 워크로드에서 처리량이 오른다. 격리는 약해서 한 프로세스가
메모리를 다 쓰면 다른 쪽도 함께 실패한다.

**시분할**  스케줄러가 GPU를 번갈아 배정한다. 구현이 간단하고 어디서나 되지만 컨텍스트 전환
비용이 있고 지연이 튄다. 개발이나 실험 환경에 적당하다.

**vGPU**  하이퍼바이저 층에서 GPU를 가상 머신에 나눠 준다. VDI나 가상화 기반 환경에서 쓰며
별도 라이선스가 필요하다.

넷은 격리 수준과 쓰는 자리가 다르다.

| 방식 | 나누는 층 | 격리 | 메모리 | 맞는 자리 |
| --- | --- | --- | --- | --- |
| MIG | 하드웨어 | 강하다. 서로 영향이 없다 | 인스턴스별로 고정 | 다중 사용자 추론, 교육용 |
| MPS | 드라이버 | 약하다. 한쪽이 죽으면 함께 죽는다 | 공유. 한쪽이 다 쓸 수 있다 | 작은 커널을 많이 던지는 추론 |
| 시분할 | 스케줄러 | 중간. 메모리는 공유다 | 공유 | 개발과 실험 |
| vGPU | 하이퍼바이저 | 강하다 | 프로파일별로 고정 | 가상 데스크톱 |

학습에는 넷 다 쓰지 않는다. 큰 학습은 GPU 한 장을 통째로 쓰고 여러 장을 묶는 방향이라
나누는 것과 반대다. 나눠 쓰는 논의는 추론과 개발 환경에서 나온다.

```bash
nvidia-smi -i 0 -mig 1                      # 0번 GPU 를 MIG 모드로 바꾼다. 재부팅이 필요할 수 있다
nvidia-smi mig -lgip                        # 만들 수 있는 인스턴스 종류
nvidia-smi mig -cgi 9,9,9 -C                # 인스턴스를 만들고 컴퓨트 인스턴스까지 붙인다
nvidia-smi -L                               # 나뉜 결과. UUID 가 MIG- 로 시작한다
```

MIG로 나눈 뒤에는 GPU 번호가 아니라 MIG UUID로 지정해야 한다. `CUDA_VISIBLE_DEVICES=0`이
동작하지 않아 당황하는 일이 흔하다.

## 개발과 분석 도구

**nvcc**  CUDA 코드를 컴파일한다. 호스트 코드는 시스템 컴파일러에 넘기고 장치 코드만 직접
처리한다. `-arch=sm_90` 처럼 대상 아키텍처를 지정하는데, 값이 실제 GPU보다 낮으면 새 기능을
못 쓰고 높으면 실행이 안 된다.

**PTX와 SASS**  PTX는 중간 표현이고 SASS는 실제 기계어다. 이미지에 PTX만 들어 있으면 처음
실행할 때 드라이버가 변환하느라 시간이 걸린다. 여러 세대를 지원하려면 세대별 SASS를 함께
넣는다.

**HIP와 ROCm**  AMD GPU용 스택이다. HIP은 CUDA와 문법이 거의 같아 변환 도구로 옮길 수 있다.
실제로는 라이브러리 대응과 성능 조정에 손이 많이 간다. 커널 코드보다 주변 생태계가 이식의
난이도를 정한다.

**OpenACC와 OpenMP offload**  지시문을 붙여 반복문을 가속기로 넘긴다. 기존 C나 Fortran 코드를
크게 안 고치고 옮길 때 쓴다. 손으로 쓴 CUDA만큼 나오지는 않지만 과학 계산 코드에서 값어치가
있다.

**nsys**  CPU와 GPU에 걸친 타임라인을 본다. 어느 구간에서 GPU가 노는지, 통신과 계산이 겹치는지
확인한다. 병목의 위치를 모를 때 여기서 시작한다.

**ncu**  커널 하나를 뜯어본다. 메모리 대역폭에 묶였는지 연산에 묶였는지, 점유율이 얼마인지
알려 준다. 느린 커널을 이미 특정한 뒤에 쓴다.

**compute-sanitizer**  메모리 접근 오류와 경쟁 상태를 잡는다. 결과가 가끔 틀리거나 이유 없이
죽을 때 쓴다. 느려지므로 작은 입력으로 돌린다.

**cuda-gdb**  장치 코드를 단계 실행한다. 커널 안에서 죽는 원인을 찾을 때 쓴다.

```bash
nsys profile -o run --trace=cuda,nvtx,osrt python train.py   # 전체 타임라인
ncu --set full -k my_kernel -o kern ./app                    # 커널 한 개 분해
compute-sanitizer --tool memcheck ./app                      # 잘못된 메모리 접근
cuda-gdb --args python train.py                              # 장치 코드 디버깅
```

`nvprof`는 옛 도구이고 Volta 이후 세대에서는 `nsys`와 `ncu`가 대신한다. 오래된 문서를 볼 때
이름만 확인하면 된다.

## 플랫폼과 모델 운영

**MLOps**  모델을 만들고 배포하고 유지하는 과정을 자동화하는 방식을 통칭한다. 데이터 준비,
학습, 평가, 배포, 감시가 한 줄로 이어지는 것을 목표로 한다. 인프라 쪽에서 보면 학습 작업과
서빙 워크로드를 어떤 자원 위에 어떻게 올릴지가 접점이다.

**AIOps**  반대 방향이다. 운영 데이터에 기계학습을 써서 이상을 찾거나 원인을 좁힌다. 지표가
많아 사람이 다 못 볼 때 후보를 줄여 주는 용도다. 판단을 대신하지는 못한다.

**실험 추적**  하이퍼파라미터, 코드 버전, 데이터 버전, 결과 지표를 실행마다 기록한다. 기록이
없으면 좋았던 실험을 다시 만들지 못한다. 작업 번호와 커밋 해시를 함께 남기는 것이 최소선이다.

**모델 레지스트리**  학습이 끝난 모델을 버전과 함께 보관하고, 어떤 데이터와 코드로 만들었는지
연결해 둔다. 배포된 모델이 어느 실행에서 나왔는지 되짚을 수 있어야 문제가 생겼을 때 원인을
찾는다.

**모델 버전 관리**  가중치 파일은 크고 자주 바뀌므로 일반 소스 관리에 그대로 넣지 않는다.
객체 스토리지에 두고 해시로 참조하는 방식이 흔하다. 코드 저장소에는 참조만 남긴다.

**서빙 엔진**  학습한 모델을 요청에 응답하는 형태로 올린다. 여러 요청을 묶어 한 번에 계산하는
배치 기능과, 여러 모델을 한 GPU에 올리는 기능이 성능을 좌우한다.

**모델 저장소 플랫폼**  팀이 모델과 데이터셋을 공유하는 웹 환경이다. 접근 권한과 라이선스
관리가 실제 운영에서 중요한 부분이 된다.

## 이기종과 배치

**NPU**  신경망 연산에 특화한 가속기다. 전력당 성능이 좋은 대신 지원하는 연산과 프레임워크가
제한된다. 추론에 먼저 들어오는 경우가 많다.

**DPU**  네트워크와 스토리지 처리를 CPU에서 덜어 가는 장치다. 호스트 CPU를 계산에 더 쓰게 하고
가상화와 보안 기능을 하드웨어로 내린다.

**이기종 클러스터**  종류나 세대가 다른 가속기가 섞인 클러스터다. 분산 학습에서는 가장 느린
랭크가 전체 속도를 정하므로 한 작업 안에서 섞지 않는다. 스케줄러에서 종류별로 자원 유형을
나누고 요청할 때 지정하게 한다.

**GPUaaS**  GPU를 서비스처럼 받아 쓰는 형태다. 장비를 사지 않고 필요할 때 계산 자원을 빌린다.
운영 부담이 줄지만 데이터를 옮기는 비용과 규정이 걸림돌이 된다.

**하이브리드 배치**  자체 클러스터를 기반으로 두고 넘치는 수요만 외부로 보낸다. 두 곳에서 같은
이미지와 같은 체크포인트를 읽을 수 있어야 실제로 오갈 수 있다.

**자원 유형**  스케줄러가 GPU를 셀 때 장수만 세면 세대 차이를 놓친다. 종류마다 이름을 붙여
구분하면 요청할 때 지정할 수 있다. Slurm은 GRES 타입으로, Kubernetes는 노드 라벨로 나눈다.

**노드 라벨과 테인트**  라벨은 노드에 붙이는 표식이고 테인트는 조건을 만족하지 않는 파드를
밀어내는 표식이다. 라벨만 쓰면 지정하지 않은 파드가 GPU 노드에 올라오므로 둘을 같이 쓴다.

**데이터 지역성**  계산을 데이터가 있는 곳으로 보내는 원칙이다. 수백 TB를 옮기는 시간이 계산
시간보다 길면 자원이 남아도 그쪽으로 보낼 수 없다. 이기종이나 하이브리드 구성에서 실제로
발목을 잡는 것은 대개 계산 자원이 아니라 이 문제다.

**세대 혼용**  분산 학습 한 작업 안에 다른 세대를 섞으면 가장 느린 랭크가 전체 속도를 정한다.
빠른 카드가 기다리느라 노는 셈이라 총 처리량이 오히려 준다. 파티션을 나누거나 요청에 제약을
걸어 한 작업이 한 종류만 잡게 한다.

```bash
sinfo -o "%P %G %D %t"                        # 파티션별 GRES 종류와 노드 수
sbatch --gres=gpu:h100:8 --constraint=h100 job.sh   # 한 종류만 잡는다
kubectl get nodes -L nvidia.com/gpu.product   # 노드마다 어떤 카드가 붙었는지
```

## 스케줄링

**갱 스케줄링**  작업이 요구한 자원 전부가 확보될 때까지 시작하지 않는 방식이다. 분산 학습처럼
프로세스가 서로를 기다리는 작업은 일부만 배치되면 진전 없이 자원만 잡는다.

**백필**  앞선 작업이 시작할 시각을 계산해두고, 그 전에 끝날 수 있는 짧은 작업을 빈 구간에
먼저 넣는다. 작업마다 적어 낸 실행 시간이 정확해야 동작하며, 모두가 최대치를 적으면 무력해진다.

**fairshare**  계정마다 몫을 정하고 최근 사용량이 몫을 넘으면 우선순위를 낮춘다. 사용 이력은
반감기를 두고 잊는다. 절대 사용량이 아니라 몫 대비 비율로 판단한다.

**선점**  낮은 우선순위 작업을 중단시키고 자리를 비운다. 체크포인트가 없는 작업이 선점당하면
계산이 통째로 사라지므로 대상 파티션을 한정해 쓴다.

**어피니티와 안티 어피니티**  특정 조건의 노드에 붙이거나 떨어뜨리는 배치 규칙이다. 같은 학습
작업의 프로세스를 같은 리프 스위치 아래 모으면 통신이 빨라지고, 복제본을 서로 다른 랙에 흩으면
장애 영향이 준다. 목적이 반대라 한쪽을 얻으면 다른 쪽을 잃는다.

**빈팩과 스프레드**  빈팩은 노드를 채워 나가며 배치해 빈 노드를 남긴다. 큰 작업이 들어올
자리를 만들어 준다. 스프레드는 고르게 흩어 개별 작업의 자원 경합을 줄인다.

**QoS**  작업에 붙이는 정책 묶음이다. 우선순위, 동시 실행 한도, 최대 시간, 선점 가능 여부를
함께 정의한다. 팀별로 다른 규칙을 주고 싶을 때 파티션보다 유연하다.

```bash
sinfo -o "%P %a %l %D %t"       # 파티션별 상태와 시간 제한
squeue -o "%i %u %P %q %T %R"   # 작업별 QoS 와 대기 사유
sacctmgr show qos format=name,priority,maxwall,maxjobsperuser
sshare -a                       # 계정별 fairshare 몫과 최근 사용량
```

## 성능과 측정

**FLOPS**  초당 부동소수점 연산 횟수다. 카탈로그 값은 이론 최대치이고 실제로는 그 절반도
어렵다. 정밀도에 따라 값이 크게 달라지므로 FP16, BF16, FP8 중 무엇을 기준으로 한 수치인지
확인해야 한다.

**MFU**  실제 달성한 연산량을 하드웨어 이론 최대치로 나눈 비율이다. 대규모 학습에서 40에서
50퍼센트면 잘 나온 축이다. 이 값이 낮으면 통신, 데이터 로딩, 커널 효율 중 하나가 발목을 잡는다.

**Roofline**  산술 강도를 가로축에, 달성 성능을 세로축에 두고 어떤 한계에 걸렸는지 보는
그림이다. 왼쪽 기울어진 구간에 있으면 메모리 대역폭에, 오른쪽 평평한 구간에 있으면 연산량에
묶인 상태다.

**Occupancy**  GPU의 스케줄링 단위가 얼마나 채워졌는지를 나타낸다. 높다고 항상 빠른 것은
아니지만 지나치게 낮으면 지연을 감출 여유가 없어진다.

**GPU 사용률**  `nvidia-smi`가 보여주는 값은 커널이 하나라도 돌고 있던 시간의 비율이다.
연산 유닛이 얼마나 바쁜지가 아니다. 사용률 100퍼센트인데 실제 처리량이 낮은 상황이 흔하며,
이때는 프로파일러로 커널 단위를 봐야 한다.

MFU는 직접 계산한다. 스텝 시간과 배치에 든 토큰 수만 알면 나온다.

```python
# 토큰당 연산량은 파라미터 수의 6배 안팎이다. 활성값 재계산을 켜면 8배로 잡는다
flops_per_token = 6 * n_params
achieved = flops_per_token * tokens_per_step / step_seconds / n_gpus
mfu = achieved / peak_flops_per_gpu          # H100 bf16 이면 989e12
print(f"MFU {mfu:.1%}")
```

40퍼센트 아래면 원인을 찾을 값어치가 있다. 통신 비중, 데이터 로더 대기, 커널 효율 순으로
확인한다.

## 관측과 운영

**Xid**  NVIDIA 드라이버가 커널 로그에 남기는 오류 코드다. 번호마다 의미가 다르고, 하드웨어
쪽과 애플리케이션 쪽이 섞여 있다. 모듈 08에서 자세히 다룬다.

**DCGM**  NVIDIA의 GPU 관리와 진단 도구 모음이다. 지표 수집, 상시 감시, 단계별 진단을 함께
제공한다. Exporter를 붙이면 Prometheus로 지표가 넘어간다.

**행 리매핑**  ECC 오류가 난 메모리 행을 예비 행으로 바꾸는 기능이다. 예비가 소진되면
`remapped_rows.failure`가 1이 되고, 그 카드는 교체 대상이다.

**스로틀링**  전력이나 온도 한계에 닿아 클럭을 낮추는 동작이다. 사유가 `SW Power Cap`이면
전력 상한, `HW Thermal Slowdown`이면 냉각 문제다. 오류 없이 느려지는 상황의 첫 번째 용의자다.

**프로파일러**  `nsys`는 CPU와 GPU에 걸친 타임라인을 보여주고, `ncu`는 커널 하나를 세밀하게
분해한다. 병목이 어디인지 모를 때 `nsys`로 범위를 좁힌 뒤 `ncu`로 파고드는 순서가 무난하다.

**드라이버와 런타임 버전**  CUDA 런타임은 드라이버보다 새로울 수 없다. 컨테이너 안의 CUDA
버전이 호스트 드라이버보다 높으면 실행이 실패한다. 노드마다 드라이버 버전이 어긋나 있으면
같은 이미지가 어떤 노드에서만 죽는 현상이 생긴다.
