GPU를 아무리 늘려도 데이터가 제때 오지 않으면 소용이 없다. 노드 수백 대가 같은 파일시스템을
동시에 두드리는 상황에서 무엇이 먼저 무너지는지, 어떻게 나눠 저장하는지를 본다.

## NFS로는 왜 부족한가

NFS는 서버 한 대가 모든 요청을 받는다. 클라이언트가 몇 대일 때는 문제가 없지만 노드가 늘면
두 곳에서 막힌다.

- 대역폭. 서버 한 대의 네트워크와 디스크가 상한이다. 노드 100대가 동시에 읽으면 각자 백분의
  일씩 가져간다.
- 메타데이터. 파일을 열고 닫고 속성을 확인하는 요청이 한 서버에 몰린다. 작은 파일이 많은
  워크로드에서 여기가 먼저 포화된다.

병렬 파일시스템은 데이터와 메타데이터를 여러 서버에 나눠 이 두 상한을 걷어낸다. 클라이언트는
파일 하나를 읽을 때도 여러 서버에서 동시에 받아온다.

## Lustre의 구성

Lustre는 역할이 다른 서버 세 종류로 이루어진다.

| 구성 | 이름 | 하는 일 |
| --- | --- | --- |
| MGS | 관리 서버 | 파일시스템 설정을 배포한다. 부하는 거의 없다 |
| MDS / MDT | 메타데이터 서버와 타깃 | 디렉터리 구조, 파일 이름, 권한, 파일이 어느 OST에 있는지를 관리한다 |
| OSS / OST | 객체 저장 서버와 타깃 | 실제 데이터를 담는다. 용량과 대역폭은 여기서 늘린다 |

클라이언트는 파일을 열 때 MDS에 물어 조각의 위치를 받고, 그다음부터는 OSS와 직접 주고받는다.
읽기와 쓰기가 MDS를 거치지 않기 때문에 대역폭이 OSS 수에 비례해 늘어난다.

용량을 늘리려면 OST를 더하고, 파일 개수와 열기 성능을 늘리려면 MDT를 더한다. 둘은 별개의
축이라 한쪽만 늘리면 다른 쪽이 병목으로 남는다.

## 스트라이핑

파일 하나를 여러 OST에 나눠 저장하는 것이 스트라이핑이다. 조각 수를 늘리면 그만큼 여러
서버에서 동시에 읽는다.

```bash
lfs getstripe /scratch/dataset/train.bin      # 현재 설정과 조각 위치
lfs setstripe -c 8 -S 4M /scratch/bigfiles    # 조각 8개, 조각 크기 4MB
lfs setstripe -c 1 /scratch/smallfiles        # 작은 파일은 한 곳에 둔다
```

설정은 파일을 만들 때 정해지고, 이미 있는 파일에는 적용되지 않는다. 디렉터리에 걸어 두면 그
아래 새로 만드는 파일이 물려받는다. 기존 파일을 바꾸려면 복사해서 새로 써야 한다.

| 파일 성격 | 조각 수 | 이유 |
| --- | ---: | --- |
| 수 GB 이상 단일 파일 | 8 이상 | 여러 OSS에서 동시에 읽어야 대역폭이 나온다 |
| 수백 MB | 2에서 4 | 적당히 나누면 충분하다 |
| 수 MB 이하 다수 | 1 | 나누면 관리 비용만 늘고 이득이 없다 |
| 체크포인트 | 4에서 8 | 짧은 시간에 몰아 쓰므로 분산이 필요하다 |

작은 파일에 조각을 많이 주면 오히려 느려진다. 파일마다 여러 OST에 접속을 열어야 하고, 각
조각은 수십 KB에 그쳐 이득이 없다.

## 메타데이터가 병목일 때

대역폭은 남는데 느린 경우가 있다. 이때는 대개 메타데이터 쪽이다. 한 디렉터리에 파일 수십만
개를 두거나, 학습 한 스텝마다 작은 파일 수천 개를 여는 패턴이 원인이다.

```bash
lfs df -h            # OST별 용량과 사용률
lfs df -i            # inode 사용률. 여기가 먼저 차는 일이 흔하다
lctl get_param mdt.*.md_stats     # 메타데이터 요청 종류별 횟수
```

해결은 대개 파일시스템이 아니라 데이터 배치 쪽에 있다.

- 작은 파일을 묶는다. 이미지 수백만 장을 그대로 두지 말고 수백 MB 단위 묶음으로 만든다.
  WebDataset의 tar 샤드나 TFRecord 같은 형식이 이 목적이다.
- 디렉터리를 나눈다. 한 디렉터리에 파일 수를 만 단위 아래로 유지한다.
- 반복해서 읽는 데이터는 노드의 로컬 NVMe에 캐시한다. 첫 에폭만 공유 스토리지를 쓰고 이후는
  로컬에서 읽으면 부하가 크게 준다.
- MDT를 늘린다. 디렉터리를 여러 MDT에 흩는 기능을 쓰면 메타데이터 부하가 나뉜다.

```bash
lfs mkdir -i -1 -c 4 /scratch/many-files    # 디렉터리를 MDT 4개에 흩는다
```

## 다른 선택지

| 파일시스템 | 성격 |
| --- | --- |
| Lustre | 대규모 HPC에서 가장 널리 쓴다. 대역폭 확장이 강하고 운영 난도가 있다 |
| GPFS (Storage Scale) | IBM 제품. 기능이 많고 관리 도구가 갖춰져 있다. 라이선스 비용이 든다 |
| BeeGFS | 설치와 운영이 상대적으로 쉽다. 중간 규모에 맞는다 |
| WekaIO | NVMe 기반 상용 제품. 작은 파일과 메타데이터에 강하다 |
| 객체 스토리지 | S3 호환. 용량 확장과 비용이 유리하고 POSIX가 필요 없는 워크로드에 맞는다 |

학습 데이터를 객체 스토리지에 두고 노드 로컬 디스크로 당겨 쓰는 구성이 늘고 있다. 공유
파일시스템의 메타데이터 부하를 피하면서 용량 비용을 낮출 수 있어서다. 대신 첫 접근 지연과
캐시 관리가 새로 생긴다.

## 성능 재기

체감으로 판단하지 말고 도구로 잰다. 대역폭과 메타데이터를 따로 재야 어디가 막혔는지 갈린다.

```bash
# 대역폭. 노드 여러 대에서 동시에 돌려야 실제 값이 나온다
mpirun -np 32 ior -a POSIX -b 4g -t 4m -F -e -o /scratch/iortest

# 메타데이터. 파일 생성과 조회 성능
mpirun -np 32 mdtest -n 10000 -d /scratch/mdtest

# 단일 노드에서 빠르게 확인할 때
fio --name=read --rw=read --bs=1m --size=8g --numjobs=8 --directory=/scratch
```

`ior`에서 `-F`는 프로세스마다 파일을 따로 쓰는 방식이고, 빼면 한 파일에 함께 쓴다. 실제
워크로드가 어느 쪽인지에 맞춰 재야 의미가 있다.

측정값은 노드 수를 늘려가며 기록한다. 어느 지점부터 총 대역폭이 늘지 않으면 거기가 서버 쪽
상한이다. 그 이상 노드를 붙여도 각자 몫만 줄어든다.

## 학습 워크로드에서 자주 겪는 일

**체크포인트가 학습을 멈춘다**  512 프로세스가 동시에 큰 파일을 쓰면 스토리지가 포화되고 그
동안 계산이 멈춘다. 랭크 0만 쓰게 하거나, 분산 체크포인트로 나눠 쓰거나, 쓰는 동안 계산이
진행되도록 비동기로 처리한다.

**첫 에폭만 느리다**  페이지 캐시가 채워지기 전이라 그렇다. 정상이며, 데이터가 메모리보다
크면 계속 느리다. 이때는 로컬 캐시를 검토한다.

**특정 노드만 느리다**  그 노드의 마운트 상태나 네트워크를 본다. `lfs check servers`로 연결
상태를 확인하고, 다른 노드와 같은 파일을 읽어 비교한다.

**용량은 남는데 쓸 수 없다**  inode가 찼거나 특정 OST만 가득 찬 경우다. `lfs df -i`와
`lfs df -h`를 함께 보고, OST 편중이면 새 파일의 스트라이프 설정을 조정한다.
