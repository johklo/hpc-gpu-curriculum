GPU를 아무리 늘려도 데이터가 제때 오지 않으면 계산 유닛은 논다. 노드 수백 대가 같은
파일시스템을 동시에 두드릴 때 무엇이 먼저 무너지는지, 그 부하를 어떻게 나누는지, GPU 학습에서
스토리지가 어디에 끼어드는지를 본다.

## NFS로는 왜 부족한가

노드 여러 대로 학습을 돌리려면 모든 노드가 같은 데이터를 같은 경로에서 볼 수 있어야 한다.
`/scratch/dataset/shard-000.tar`가 1번 노드와 64번 노드에서 같은 파일을 가리켜야 학습 코드를
노드마다 고치지 않아도 된다. 이 일을 하는 것이 공유 파일시스템이다.

가장 익숙한 방식이 NFS다. 서버 한 대가 디스크를 들고 있고 나머지가 네트워크로 그 디렉터리를
마운트한다. 설치가 쉽고 어디서나 돌기 때문에 작은 클러스터의 기본 선택지다. 노드가 늘면
두 곳에서 막힌다.

첫째는 대역폭이다. 서버 한 대의 네트워크 카드와 디스크가 상한이다. 100GbE 한 장을 단 서버라면
이론상 12.5 GB/s이고, 노드 100대가 동시에 읽으면 노드당 125 MB/s로 떨어진다. GPU 8장이 달린
노드에서 이 값은 데이터 로더 하나도 채우지 못한다.

둘째는 메타데이터다. 파일을 열고 닫고 속성을 확인하는 요청이 전부 한 서버로 간다. 학습 한
스텝마다 이미지 파일 수천 개를 여는 워크로드에서는 대역폭이 남아도 여기서 먼저 포화된다.

| 노드 수 | NFS 서버 1대 기준 노드당 몫 | GPU 8장 노드에 필요한 양 | 결과 |
| ---: | ---: | ---: | --- |
| 4 | 3.1 GB/s | 1.9 GB/s | 견딘다 |
| 16 | 780 MB/s | 1.9 GB/s | GPU가 놀기 시작한다 |
| 64 | 195 MB/s | 1.9 GB/s | 계산보다 대기가 길다 |
| 100 | 125 MB/s | 1.9 GB/s | 학습이 스토리지에 묶인다 |

병렬 파일시스템은 데이터와 메타데이터를 여러 서버로 나눠 이 두 상한을 걷어낸다. 클라이언트는
파일 하나를 읽을 때도 여러 서버에서 동시에 받아온다. 서버를 늘리면 총 대역폭이 함께 늘어나는
구조가 핵심이다.

## Lustre의 구조와 접근 경로

Lustre는 역할이 다른 서버 세 종류와 그 사이를 잇는 전용 네트워크 계층으로 이루어진다.

| 구성 | 이름 | 하는 일 | 늘리면 좋아지는 것 |
| --- | --- | --- | --- |
| MGS | 관리 서버 | 파일시스템 설정을 클라이언트에 배포한다 | 없음. 부하가 거의 없다 |
| MDS / MDT | 메타데이터 서버와 타깃 | 디렉터리 구조, 이름, 권한, 그리고 각 파일이 어느 OST에 어떻게 놓였는지를 관리한다 | 파일 개수, 열기와 조회 성능 |
| OSS / OST | 객체 저장 서버와 타깃 | 파일의 실제 내용을 조각으로 담는다 | 용량, 읽기와 쓰기 대역폭 |
| LNet | 네트워크 계층 | InfiniBand나 이더넷 위에서 위 셋을 잇는다 | 경로 이중화, 라우팅 |

![클라이언트는 MDS에 파일 위치를 물은 뒤 OSS와 직접 데이터를 주고받는다](img/lustre-architecture.svg)

파일을 읽을 때 벌어지는 일을 순서대로 보면 구조가 왜 이런지 이해된다.

1. 클라이언트가 `open()`을 부른다. 요청은 MDS로 간다.
2. MDS는 이름을 찾아 권한을 확인하고, 그 파일의 배치 정보를 돌려준다. 배치 정보에는 조각이
   몇 개이고 각각 어느 OST에 있는지가 들어 있다.
3. 이후의 `read()`와 `write()`는 **MDS를 거치지 않는다**. 클라이언트가 해당 OSS들과 직접
   주고받는다.

읽기와 쓰기가 MDS를 통과하지 않기 때문에 총 대역폭이 OSS 수에 비례해 늘어난다. 반대로 파일을
여는 동작은 전부 MDS를 지나므로, 작은 파일을 많이 여는 워크로드에서는 OSS를 아무리 늘려도
빨라지지 않는다. 용량과 대역폭은 OST로 늘리고, 파일 개수와 열기 성능은 MDT로 늘린다. 두 축이
따로 놀기 때문에 한쪽만 늘리면 다른 쪽이 병목으로 남는다.

일관성은 분산 락으로 지킨다. 여러 클라이언트가 같은 파일 영역을 동시에 쓰면 락 경합이 생기고,
심하면 대역폭보다 락이 먼저 병목이 된다. 프로세스마다 다른 파일에 쓰는 방식이 한 파일에
같이 쓰는 방식보다 대개 빠른 이유가 여기 있다.

## 스트라이핑

파일 하나를 여러 OST에 나눠 저장하는 것이 스트라이핑이다. 조각 크기만큼 잘라 정해진 개수의
OST에 번갈아 배치한다.

![파일을 조각 크기 단위로 잘라 여러 OST에 번갈아 저장한다](img/lustre-striping.svg)

```bash
lfs getstripe /scratch/dataset/train.bin      # 현재 설정과 조각이 놓인 OST
lfs setstripe -c 8 -S 4M /scratch/bigfiles    # 조각 8개, 조각 크기 4MB
lfs setstripe -c 1 /scratch/smallfiles        # 작은 파일은 한 곳에 둔다
lfs setstripe -c -1 /scratch/huge             # 모든 OST에 펼친다
```

설정은 파일을 만드는 시점에 정해지고 이미 있는 파일에는 적용되지 않는다. 디렉터리에 걸어 두면
그 아래 새로 만드는 파일이 물려받는다. 기존 파일의 배치를 바꾸려면 옮겨 써야 한다.

```bash
lfs migrate -c 8 /scratch/dataset/train.bin   # 배치를 바꾸며 다시 쓴다
```

조각 수는 파일 크기에 맞춰 정한다. 기준은 **조각 하나가 최소 수백 MB는 되게** 하는 것이다.

| 파일 크기 | 조각 수 | 이유 |
| --- | ---: | --- |
| 1 GB 미만 | 1 | 나눠도 조각이 작아 이득이 없고 접속만 늘어난다 |
| 1~10 GB | 4 | 조각당 수백 MB로 여러 OSS를 동시에 쓴다 |
| 10~100 GB | 8~16 | 단일 파일 대역폭이 필요한 구간이다 |
| 100 GB 이상 | -1 | 전체 OST에 펼친다 |

요즘 Lustre는 크기에 따라 배치를 다르게 하는 방식을 지원한다. 한 번 걸어 두면 작은 파일과 큰
파일을 따로 관리할 필요가 없어진다.

```bash
# 처음 1MB는 조각 1개, 1GB까지는 4개, 그 이상은 16개로 늘린다
lfs setstripe -E 1M -c 1 -E 1G -c 4 -E -1 -c 16 /scratch/mixed
```

아주 작은 파일은 아예 MDT에 본문까지 넣을 수 있다. OST 접속을 열지 않으므로 열기와 읽기가
한 번에 끝난다.

```bash
lfs setstripe -E 64K -L mdt -E -1 -c 4 /scratch/manysmall
```

## GPU 클러스터에서의 데이터 경로

학습 중 데이터는 네 구간을 지난다. 뒤로 갈수록 빨라지고, 맨 앞이 가장 느리다.

![공유 스토리지에서 로컬 NVMe, 페이지 캐시, GPU 메모리로 갈수록 대역폭이 커진다](img/gpu-data-path.svg)

필요한 대역폭은 계산할 수 있다. GPU 한 장이 초당 처리하는 샘플 수에 샘플 하나의 크기를 곱하면
된다. 이미지 학습에서 GPU 한 장이 초당 2,000장을 처리하고 평균 파일 크기가 120 KB라면 GPU당
약 240 MB/s, 8장이 달린 노드는 약 1.9 GB/s가 필요하다. 노드 64대면 총 123 GB/s다. 이 값이
공유 스토리지가 감당해야 하는 규모다.

토큰으로 학습하는 언어 모델은 사정이 다르다. 전처리된 토큰은 샘플당 수 KB 수준이라 같은
연산량에서도 필요한 대역폭이 훨씬 작다. 반면 체크포인트 쓰기는 훨씬 무겁다. 워크로드에 따라
병목이 읽기 쪽인지 쓰기 쪽인지가 갈린다.

이 계산에서 세 가지가 따라 나온다.

- 노드당 필요한 대역폭이 인터커넥트 한 포트로 감당되는지 확인해야 한다. 200Gb IB 한 포트는
  이론상 25 GB/s이고 실효는 그보다 낮다.
- 총 요구량을 OSS 수로 나눠 서버당 부하를 본다. 서버 한 대가 낼 수 있는 값을 넘으면 OSS를
  늘려야 한다.
- 같은 데이터를 여러 에폭 반복해 읽는다면 첫 에폭에만 공유 스토리지를 쓰고 이후에는 노드 로컬
  NVMe에서 읽는 편이 낫다. 데이터셋이 로컬 디스크에 들어가는 크기라면 효과가 크다.

```bash
# 첫 에폭 전에 노드마다 자기 몫을 로컬로 내려받는다
srun --ntasks-per-node=1 bash -c '
  mkdir -p /local/nvme/data
  rsync -a --info=progress2 /scratch/dataset/shard-$SLURM_NODEID-*.tar /local/nvme/data/'
```

## 노드 수백 대가 한꺼번에 붙을 때

Lustre 클라이언트는 따로 세우는 서버가 아니라 컴퓨트 노드마다 올라가는 커널 모듈이다. GPU
노드 64대로 학습을 돌리면 클라이언트도 64개이고, 그 64개가 같은 MDS와 같은 OST를 동시에
두드린다. 실제로 요청을 만드는 주체는 노드보다 훨씬 많다.

| 층 | 개수 | 근거 |
| --- | ---: | --- |
| 노드 | 64 | 작업이 잡은 노드 수 |
| 랭크(프로세스) | 512 | 노드당 GPU 8장, GPU 하나에 프로세스 하나 |
| 데이터 로더 워커 | 4,096 | 랭크당 8개 |
| 동시에 열려 있는 파일 | 4,096 이상 | 워커마다 최소 하나 |

랭크는 분산 학습에서 프로세스마다 붙는 전역 번호다. 파일을 여는 요청은 이 4,096개 주체에서
각각 나오고, 전부 MDS 한 대로 모인다.

**시작하는 순간이 가장 위험하다.** 512개 랭크가 같은 초에 파이썬을 켠다. `import torch` 한
줄이 파일 수천 개를 연다. 라이브러리가 공유 파일시스템에 설치돼 있으면 512 곱하기 수천 건의
메타데이터 요청이 몇 초 안에 MDS로 몰린다. 대역폭 그래프는 0에 붙어 있는데 작업이 몇 분째
시작되지 않는 상태가 이것이다. 원인을 대역폭에서 찾으면 아무것도 나오지 않는다.

```bash
# 작업을 띄운 직후 메타데이터 요청이 몰리는지 확인한다
lctl get_param mdc.*.stats | grep -E 'open|getattr|statfs'
```

대응은 파이썬 환경을 공유 파일시스템에서 빼는 것이다.

- 컨테이너 이미지에 환경을 담는다. Enroot는 이미지를 노드 로컬에 풀어 두므로 `import`가 로컬
  디스크에서 일어나고 MDS에 요청이 가지 않는다.
- 컨테이너를 쓰지 않는다면 작업 시작 시 환경을 노드 로컬로 복사하고 그쪽에서 실행한다.
- 둘 다 어려우면 랭크 시작을 몇 초씩 흩는다. 증상은 줄지만 원인은 남는다.

**읽는 파일이 겹치는지가 속도를 가른다.** 랭크마다 자기 샤드를 읽으면 파일이 겹치지 않고,
파일이 많으니 OST 전체에 저절로 흩어진다. 반대로 모두가 큰 파일 하나를 읽는 구성에서는 그
파일의 조각 수가 곧 동원되는 OST 수다. 조각 수가 1이면 512개 랭크가 서버 한 대에 붙는다.

![랭크마다 자기 파일을 읽으면 OST 전체에 흩어지고, 조각 수 1인 큰 파일 하나를 함께 읽으면 서버 한 대로 몰린다](img/rank-shard-map.svg)

```bash
lfs getstripe /scratch/dataset/tokens.bin   # 이 파일이 실제로 몇 대에 걸쳐 있는지
lfs setstripe -c 16 /scratch/dataset        # 앞으로 만들 파일을 16대에 나눠 둔다
```

**읽기 락은 서로 막지 않는다.** 여러 클라이언트가 같은 영역을 읽는 것은 공유 락이라 경합이
없다. 512개 랭크가 같은 파일의 다른 구간을 읽는 구성 자체는 문제가 아니다. 문제는 쓰기다. 두
랭크가 같은 파일의 같은 영역에 쓰면 락이 오가면서 대역폭보다 먼저 병목이 된다. 체크포인트를
랭크마다 다른 파일에 쓰라는 권고가 여기서 나온다.

## LLM 학습에서 오가는 트래픽

학습이 도는 동안 노드와 Lustre 사이에는 다섯 종류의 트래픽이 오간다. 방향도 양도 빈도도
전부 다르다.

![학습 시작 시 체크포인트 읽기, 매 스텝 토큰 읽기, 주기적 체크포인트 쓰기, 장애 후 되읽기, 계속되는 로그 쓰기가 방향별로 오간다](img/llm-io-traffic.svg)

| 시점 | 방향 | 무엇 | 양 |
| --- | --- | --- | --- |
| 시작할 때 한 번 | 스토리지에서 노드로 | 체크포인트, 토크나이저, 설정 | 980 GB |
| 매 스텝 | 스토리지에서 노드로 | 토큰 샤드 | 초당 1.6 MB |
| 30분마다 | 노드에서 스토리지로 | 체크포인트 | 980 GB를 49초에 |
| 노드가 빠진 뒤 | 스토리지에서 노드로 | 마지막 체크포인트 | 980 GB |
| 학습 내내 | 노드에서 스토리지로 | 로그, 지표, 이벤트 파일 | 양은 작고 여는 횟수가 많다 |

**토큰 읽기는 생각보다 훨씬 작다.** 계산해 보면 이유가 드러난다.

- 토큰 하나를 학습하는 데 드는 연산은 파라미터 수의 6배 안팎이다. 70B 모델이면 토큰당
  4.2 곱하기 10의 11승 FLOP이다.
- H100 한 장이 bf16으로 실효 400 TFLOP/s를 낸다면 초당 950토큰 정도를 처리한다. 활성값
  재계산을 켜면 700토큰 안팎으로 내려간다.
- GPU 512장이면 초당 40만 토큰이다.
- 전처리된 토큰은 정수 하나로 저장한다. 어휘가 65,536개 이하면 2바이트, 넘으면 4바이트다.
- 40만 곱하기 4바이트는 초당 1.6 MB다.

클러스터 전체가 초당 1.6 MB를 읽는다. 노트북 한 대가 감당하는 양이다. 같은 문서 앞부분에서
계산한 이미지 워크로드는 같은 규모에서 123 GB/s를 요구했다. 샘플 하나가 120 KB짜리 JPEG이냐
몇 KB짜리 정수 배열이냐의 차이가 여기서 갈린다.

| 워크로드 | 샘플 하나 | 클러스터 전체 읽기 | 먼저 막히는 곳 |
| --- | --- | ---: | --- |
| 이미지 분류 | 120 KB JPEG | 123 GB/s | 읽기 대역폭과 메타데이터 |
| 토큰 사전학습 | 수 KB 정수 배열 | 1.6 MB/s | 체크포인트 쓰기 |
| 멀티모달 | 둘이 섞인다 | 수십 GB/s | 양쪽 다 |

LLM 사전학습만 놓고 보면 Lustre로 가는 트래픽의 거의 전부가 체크포인트다. 데이터셋 읽기를
기준으로 스토리지를 설계하면 규모를 크게 잘못 잡는다. 파인튜닝이나 멀티모달로 넘어가면 다시
읽기가 커지므로 워크로드부터 확인해야 한다.

**기울기를 합치는 트래픽은 스토리지를 지나지 않는다.** 매 스텝 모든 랭크가 계산한 기울기를
서로 더한다. 70B 모델의 bf16 기울기는 140 GB이고, 링 방식 all-reduce는 그 두 배 가까운 양을
실어 나른다. 스텝마다 280 GB가 노드 사이를 오간다. 이 트래픽은 InfiniBand 위에서만 돌고 MDS도
OST도 거치지 않는다. 스토리지 지표가 조용한데 네트워크가 포화라면 여기를 보고 있는 것이다.

한 가지 예외가 패브릭을 공유하는 구성이다. 스토리지도 같은 InfiniBand를 쓴다면 체크포인트를
쓰는 49초 동안 all-reduce와 대역폭을 다툰다. 저장이 끝난 뒤에도 몇 스텝 동안 스텝 시간이
길어지는 현상이 이것이다. 스토리지 트래픽용 레일을 따로 두거나 QoS로 나누면 갈라진다.

## 시간축에서 본 스토리지 부하

![토큰 읽기는 바닥에 깔리고 체크포인트 쓰기만 주기적으로 상한까지 치솟는다](img/training-io-timeline.svg)

부하의 모양이 계획을 정한다. 평균으로 잡으면 틀린다. 980 GB를 1,800초로 나눈 평균은 0.54 GB/s
이지만, 실제로는 49초 동안 20 GB/s를 요구하고 나머지 시간에는 거의 놀린다. 40배 차이다.
스토리지 대역폭은 평균이 아니라 이 봉우리에 맞춰 잡는다.

저장하는 동안 계산이 멈춘다면 그 시간은 그대로 손실이다. 간격을 늘리면 정지는 줄지만 장애가
났을 때 되돌아가는 양이 늘어난다.

| 저장 간격 | 시간당 정지 | 정지 비율 | 장애 시 평균 손실 |
| ---: | ---: | ---: | ---: |
| 10분 | 294초 | 8.2% | 5분 |
| 30분 | 98초 | 2.7% | 15분 |
| 60분 | 49초 | 1.4% | 30분 |
| 120분 | 24.5초 | 0.7% | 60분 |

두 손실의 합이 가장 작아지는 지점이 있다. 저장에 걸리는 시간과 평균 무장애 시간만 알면
계산된다. 최적 간격은 저장 시간과 평균 무장애 시간을 곱해 2를 곱한 값의 제곱근이다.

| 평균 무장애 시간 | 최적 저장 간격 |
| ---: | ---: |
| 6시간 | 24분 |
| 12시간 | 34분 |
| 24시간 | 49분 |
| 72시간 | 84분 |

저장에 49초가 걸리고 하루에 한 번 노드가 빠지는 클러스터라면 49분 근처가 답이다. 노드가 자주
빠질수록 자주 저장해야 한다. 무장애 시간은 짐작하지 말고 작업 재시작 기록에서 뽑는다.

동시에 도는 작업이 여럿이면 봉우리가 겹치는 문제가 하나 더 생긴다. 20 GB/s짜리 스토리지에서
작업 네 개가 같은 순간에 저장하면 각자 5 GB/s로 떨어지고 정지 시간이 네 배가 된다. 저장 시각을
작업마다 흩거나, 간격에 약간의 무작위를 섞는다.

```python
import random

# 작업마다 간격을 조금씩 어긋나게 두어 저장이 겹치지 않게 한다
interval = 2900 + random.randint(-300, 300)
```

용량도 봉우리 기준으로 잡는다. 체크포인트 하나가 980 GB이고 최근 세 개를 남긴다면 작업 하나에
2.9 TB다. 실험 다섯 개를 동시에 돌리면 15 TB가 상시 점유된다. 보존 개수를 정해 두지 않으면
이 값이 무한히 늘어난다.

## 체크포인트가 만드는 부하

체크포인트는 짧은 시간에 대량으로 쓴다. 크기는 모델 파라미터 수에서 계산한다. 파라미터 하나에
가중치 2바이트(bf16), 옵티마이저 상태 8바이트(Adam의 1차·2차 모멘트를 fp32로), 마스터 가중치
4바이트를 잡으면 파라미터당 14바이트 안팎이다.

| 모델 크기 | 가중치만 | 옵티마이저까지 포함한 전체 상태 |
| ---: | ---: | ---: |
| 7B | 약 14 GB | 약 98 GB |
| 13B | 약 26 GB | 약 182 GB |
| 70B | 약 140 GB | 약 980 GB |

70B 모델의 전체 상태를 저장하면 1 TB에 가깝다. 스토리지가 20 GB/s를 낸다 해도 50초가 걸리고,
그동안 계산이 멈춘다면 그대로 손실이다. 대응은 세 가지다.

- **분산 저장**. ZeRO나 FSDP로 상태를 랭크마다 나눠 갖고 있다면 각자 자기 몫만 쓴다. 파일이
  랭크 수만큼 생기므로 조각 수는 1로 두고 파일을 흩는 편이 낫다.
- **비동기 저장**. GPU 메모리에서 호스트 메모리로 먼저 복사하고, 디스크 쓰기는 백그라운드로
  넘긴다. 계산은 복사가 끝나는 즉시 재개한다.
- **간격 조정**. 한 번 저장하는 데 걸리는 시간의 20배에서 50배 사이를 간격으로 잡는다. 저장에
  1분이 걸린다면 20분에서 50분 간격이 출발점이다.

보존 개수도 정해 둔다. 최근 두세 개만 남기고 지우지 않으면 체크포인트가 파일시스템을 채운다.
용량 경보가 울리는 원인 중에 이것이 흔하다.

**512개 파일이 같은 순간에 만들어진다.** 랭크마다 자기 몫을 쓰면 파일 개수도 랭크 수만큼이다.
그 파일이 전부 한 디렉터리에 생기면 디렉터리를 담당하는 MDT 한 대가 512건의 생성 요청을 한꺼번에
받는다. 쓰기 대역폭은 남는데 파일이 만들어지지 않아 저장이 늘어지는 상황이 여기서 나온다.
디렉터리를 여러 MDT에 나눠 두면 갈라진다.

```bash
# 체크포인트 디렉터리를 MDT 4대에 나눈다. 만들 때 한 번만 하면 된다
lfs mkdir -c 4 /scratch/run-42/checkpoints
lfs getdirstripe /scratch/run-42/checkpoints
```

조각 수는 파일 하나에 1로 둔다. 파일이 512개나 되므로 파일 단위로 이미 흩어진다. 여기서 조각
수를 크게 잡으면 파일 하나가 여러 OST에 걸치면서 512 곱하기 조각 수만큼의 연결이 생기고,
서버마다 작은 쓰기가 잘게 쏟아져 오히려 느려진다.

```bash
lfs setstripe -c 1 /scratch/run-42/checkpoints
```

PyTorch는 이 형태의 저장을 표준으로 제공한다. 랭크마다 자기 샤드를 자기 파일에 쓰고, 불러올
때 다시 모은다.

```python
import torch.distributed.checkpoint as dcp

# 랭크마다 자기 몫만 쓴다. 파일이 랭크 수만큼 생긴다
dcp.save(state_dict, checkpoint_id=f"/scratch/run-42/checkpoints/step-{step}")

# 되돌릴 때. world_size 가 달라져도 다시 나눠 읽는다
dcp.load(state_dict, checkpoint_id=f"/scratch/run-42/checkpoints/step-{last}")
```

저장이 끝났는지 확인하는 절차도 필요하다. 모든 랭크가 쓰기를 마치기 전에 작업이 죽으면
반쯤 쓰인 체크포인트가 남는다. 불러오기가 실패하는 것보다, 조용히 깨진 값을 읽는 쪽이 더
나쁘다. 마지막에 완료 표시 파일을 하나 남기고 불러올 때 그 파일이 있는 체크포인트만 쓴다.

```python
if rank == 0:
    (path / "COMPLETE").write_text(str(step))     # 전원이 끝난 뒤에만 남긴다
```

## 메타데이터가 병목일 때

대역폭은 남는데 느린 경우가 있다. 대개 메타데이터 쪽이다. 한 디렉터리에 파일 수십만 개를
두거나, 학습 스텝마다 작은 파일 수천 개를 여는 패턴이 원인이다.

```bash
lfs df -h                          # OST별 용량과 사용률
lfs df -i                          # inode 사용률. 용량보다 먼저 차는 일이 흔하다
lctl get_param mdt.*.md_stats      # 메타데이터 요청 종류별 횟수
lctl get_param llite.*.stats       # 클라이언트 쪽에서 본 통계
```

해결은 대개 파일시스템 설정이 아니라 데이터 배치 쪽에 있다.

**작은 파일을 묶는다.** 이미지 수백만 장을 그대로 두지 말고 수백 MB 단위 묶음으로 만든다.
WebDataset의 tar 샤드나 TFRecord가 이 목적이다. 파일 500만 개가 샤드 500개로 줄면 열기 요청도
그만큼 줄어든다. 순차 읽기가 되므로 대역폭도 잘 나온다.

```bash
# 이미지 디렉터리를 샤드로 묶는다
tar --sort=name -cf shard-000.tar $(ls images | head -10000)
```

**디렉터리를 나눈다.** 한 디렉터리의 파일 수를 만 단위 아래로 유지한다. 해시 앞 두 자리로
하위 디렉터리를 만드는 방식이 흔하다.

**메타데이터를 여러 MDT에 흩는다.** 디렉터리 단위로 MDT를 나눌 수 있다.

```bash
lfs mkdir -i -1 -c 4 /scratch/many-files    # 하위 디렉터리를 MDT 4개에 분산한다
lfs getdirstripe /scratch/many-files        # 현재 분산 상태
```

## 클라이언트 쪽 조정

서버가 멀쩡한데 특정 노드만 느리면 클라이언트 설정을 본다.

```bash
lctl get_param osc.*.max_rpcs_in_flight     # 동시에 날리는 요청 수, 기본 8
lctl get_param osc.*.max_dirty_mb           # 쓰기 버퍼 크기
lctl get_param llite.*.max_read_ahead_mb    # 미리 읽기
lctl set_param osc.*.max_rpcs_in_flight=16  # 대역폭이 남으면 늘려 본다
```

큰 파일을 순차로 읽는 워크로드는 요청 수와 미리 읽기를 늘리면 효과가 있다. 작은 파일이 많은
워크로드는 늘려도 소용이 없고 메모리만 쓴다.

체크섬은 CPU를 쓴다. 신뢰할 수 있는 네트워크에서 대역폭이 아쉬우면 끄는 선택지가 있다. 데이터
무결성과 맞바꾸는 결정이라 정책으로 정해 둔다.

```bash
lctl get_param osc.*.checksums
```

네트워크 계층은 따로 확인한다.

```bash
lnetctl net show                 # LNet 인터페이스
lctl ping <서버 NID>             # 서버까지 닿는지
lfs check servers                # MDS와 OST 연결 상태
```

## 운영에서 만나는 상황

**OST 하나만 가득 찬다.** 배치가 편중된 경우다. 남은 공간이 적은 OST는 새 파일 배치에서
빠지지만, 이미 그 위에 있는 큰 파일은 그대로다. 파일을 옮겨 균형을 맞춘다.

```bash
lfs df -h | sort -k5 -h                     # 사용률 순으로 본다
lfs find /scratch --ost 3 -size +10G        # 특정 OST의 큰 파일을 찾는다
lfs migrate -c 8 <파일>                      # 다시 배치한다
```

**클라이언트가 축출된다.** 서버가 응답 없는 클라이언트를 끊는 동작이다. `dmesg`에 evicted가
남고 그 노드의 작업은 I/O 오류로 죽는다. 원인은 대개 네트워크나 노드 부하다. 해당 노드를
드레인하고 LNet 상태부터 본다.

**용량은 남는데 쓸 수 없다.** inode가 찼거나 쿼터에 걸린 것이다.

```bash
lfs quota -u $USER /scratch
lfs quota -g team-ml /scratch
```

**특정 노드만 느리다.** 마운트 상태, LNet 경로, 클라이언트 설정을 차례로 본다. 같은 파일을
다른 노드에서 읽어 비교하면 노드 문제인지 파일시스템 문제인지 바로 갈린다.

## 다른 선택지

| 파일시스템 | 성격 | 맞는 곳 |
| --- | --- | --- |
| Lustre | 대역폭 확장이 강하고 사례가 많다. 운영 난도가 있다 | 대규모 HPC, 큰 파일 위주 |
| GPFS (Storage Scale) | 기능과 관리 도구가 갖춰져 있다. 라이선스 비용이 든다 | 기업 환경, 혼합 워크로드 |
| BeeGFS | 설치와 운영이 상대적으로 쉽다 | 중간 규모 |
| WekaIO | NVMe 기반 상용 제품. 작은 파일과 메타데이터에 강하다 | 작은 파일이 많은 학습 |
| 객체 스토리지 | S3 호환. 용량 비용이 낮고 POSIX가 없다 | 데이터 레이크, 아카이브 |

학습 데이터를 객체 스토리지에 두고 노드 로컬 디스크로 당겨 쓰는 구성이 늘고 있다. 공유
파일시스템의 메타데이터 부하를 피하면서 용량 비용을 낮출 수 있어서다. 대신 첫 접근 지연과
캐시 관리라는 문제가 새로 생긴다.

고르는 순서는 워크로드에서 시작한다. 파일이 크고 순차로 읽는지, 작고 많은지가 첫 갈림길이다.

| 확인할 것 | 그렇다면 |
| --- | --- |
| 파일 하나가 수백 MB 이상이고 순차로 읽는다 | Lustre나 GPFS가 잘 맞는다 |
| 파일이 수백만 개이고 하나가 수백 KB다 | 먼저 샤드로 묶는다. 그래도 남으면 WekaIO 같은 제품을 본다 |
| 체크포인트 쓰기가 부하의 대부분이다 | 쓰기 대역폭 기준으로 OSS 수를 잡는다 |
| 같은 데이터를 여러 번 읽는다 | 노드 로컬 NVMe 캐시를 먼저 둔다. 공유 계층은 그 뒤다 |
| 운영 인력이 한두 명이다 | Lustre는 부담이 크다. 관리형 서비스나 BeeGFS를 본다 |

용량과 대역폭은 따로 잡는다는 점을 기억한다. 500 TB가 필요하다고 500 TB짜리를 사면 대역폭이
모자라고, 20 GB/s가 필요하다고 그 값만 보면 용량이 모자란다. 둘 중 큰 쪽이 서버 대수를 정한다.

## 객체 스토리지를 계층으로 두기

병렬 파일시스템은 비싸다. 용량 단가로 보면 객체 스토리지가 몇 배 싸기 때문에, 원본 데이터는
객체 스토리지에 두고 학습에 쓰는 것만 병렬 파일시스템으로 올리는 계층 구성이 늘고 있다.

| 계층 | 무엇을 두나 | 성격 |
| --- | --- | --- |
| 객체 스토리지 | 원본 데이터, 지난 체크포인트, 결과물 | 용량이 싸다. POSIX가 아니다 |
| 병렬 파일시스템 | 지금 도는 학습이 읽는 데이터, 최근 체크포인트 | 빠르다. 비싸다 |
| 노드 로컬 NVMe | 반복해 읽는 샤드 | 가장 빠르다. 작업이 끝나면 사라진다 |

자체 구축에서 객체 스토리지를 올리는 방법은 두 갈래다. MinIO는 설치가 가볍고 S3 규약을 그대로
따르므로 작은 규모에서 빠르게 세운다. Ceph는 객체와 블록과 파일을 함께 제공하고 RADOS
Gateway가 S3 창구 역할을 한다. 운영 난도는 높지만 규모가 커질수록 유리하다.

```bash
# 객체 스토리지에서 학습 데이터를 병렬 파일시스템으로 올린다
mc alias set store https://s3.internal ACCESS SECRET
mc mirror --overwrite store/datasets/imagenet-shards /scratch/dataset/

# 끝난 실험의 체크포인트를 내려 용량을 비운다
mc mv --recursive /scratch/run-41/checkpoints store/archive/run-41/
```

객체 스토리지는 POSIX가 아니라는 점이 중요하다. 파일을 부분만 고쳐 쓸 수 없고, 디렉터리도
실제로는 이름 앞부분일 뿐이다. 학습 코드가 `open()`과 `seek()`을 그대로 쓰고 있다면 객체
스토리지를 직접 읽게 만들 수 없다. 세 가지 선택지가 있다.

- **미리 내려받는다.** 작업 시작 시 필요한 샤드만 로컬이나 공유 파일시스템으로 옮긴다. 가장
  단순하고 성능이 예측된다. 데이터가 크면 시작이 오래 걸린다.
- **읽기 라이브러리를 쓴다.** WebDataset이나 각 프레임워크의 S3 데이터셋 구현이 객체를 스트림
  으로 읽는다. 코드를 고쳐야 하지만 내려받기가 사라진다.
- **파일시스템처럼 붙인다.** s3fs 같은 도구로 마운트한다. 코드를 안 고쳐도 되지만 메타데이터
  요청마다 네트워크를 타므로 작은 파일이 많으면 느리다. 학습 데이터 경로에는 권하지 않는다.

```python
# 객체 스토리지의 샤드를 스트림으로 읽는 구성
import webdataset as wds

url = "pipe:mc cat store/datasets/imagenet-{000000..000999}.tar"
dataset = wds.WebDataset(url, shardshuffle=True).decode("pil")
```

계층 사이를 옮기는 일은 정책으로 자동화한다. 마지막 접근이 30일을 넘긴 데이터셋과 두 세대 이전
체크포인트를 객체 스토리지로 내리는 규칙을 두면 병렬 파일시스템 용량 경보가 크게 준다.

```bash
# 30일 이상 손대지 않은 데이터셋을 찾아 내린다
lfs find /scratch/dataset -atime +30 -type d -maxdepth 1
```

## 컨테이너에서 공유 스토리지 붙이기

Kubernetes 쪽 워크로드도 같은 데이터를 봐야 한다. 노드에 이미 마운트된 경로를 그대로 붙이는
방식이 가장 단순하다.

```yaml
volumes:
  - name: scratch
    hostPath: { path: /scratch, type: Directory }
```

단순한 대신 파드가 노드의 마운트 상태에 그대로 묶인다. 마운트가 빠진 노드에 파드가 뜨면 빈
디렉터리를 보고 조용히 잘못된 결과를 낸다. 규모가 커지면 CSI 드라이버로 정식 볼륨으로 다루는
편이 낫다. 볼륨이 준비되지 않으면 파드가 아예 뜨지 않으므로 조용한 실패가 사라진다.

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: scratch-lustre
spec:
  capacity: { storage: 500Ti }
  accessModes: [ReadWriteMany]
  persistentVolumeReclaimPolicy: Retain
  csi:
    driver: lustre.csi.example.com
    volumeHandle: scratch
    volumeAttributes:
      mgsAddress: 10.0.0.10@o2ib
      fsName: scratch
```

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: scratch
spec:
  accessModes: [ReadWriteMany]
  storageClassName: ""
  volumeName: scratch-lustre
  resources:
    requests: { storage: 500Ti }
```

| 방식 | 좋은 점 | 나쁜 점 |
| --- | --- | --- |
| hostPath | 설정이 없다. 성능 손실도 없다 | 마운트 누락을 파드가 모른다. 권한 통제가 없다 |
| CSI 정적 볼륨 | 볼륨이 없으면 파드가 안 뜬다. 접근 제어가 붙는다 | 드라이버 설치와 관리가 필요하다 |
| CSI 동적 프로비저닝 | 사용자가 알아서 잡는다 | 병렬 파일시스템에서는 잘 쓰지 않는다 |
| 객체 스토리지 직접 | 스토리지 계층이 필요 없다 | POSIX가 아니라 코드를 고쳐야 한다 |

접근 권한은 파일시스템의 uid로 매겨진다는 점을 다시 확인한다. CSI로 붙여도 파드가 root로 돌면
Slurm 쪽에서 만든 파일과 권한이 어긋난다. `securityContext`에 실제 uid를 지정해야 양쪽이 같은
파일을 다룬다.

## 성능 재기

체감으로 판단하지 말고 도구로 잰다. 대역폭과 메타데이터를 따로 재야 어디가 막혔는지 갈린다.

```bash
# 대역폭. 노드 여러 대에서 동시에 돌려야 실제 값이 나온다
mpirun -np 32 ior -a POSIX -b 4g -t 4m -F -e -o /scratch/iortest

# 한 파일에 함께 쓰는 방식 (-F 를 뺀다). 락 경합이 드러난다
mpirun -np 32 ior -a POSIX -b 4g -t 4m -e -o /scratch/iortest-shared

# 메타데이터. 파일 생성과 조회 성능
mpirun -np 32 mdtest -n 10000 -u -d /scratch/mdtest

# 단일 노드에서 빠르게 확인할 때
fio --name=read --rw=read --bs=1m --size=8g --numjobs=8 --directory=/scratch
```

`-e`는 쓰기 후 동기화를 강제해 페이지 캐시 효과를 걷어낸다. 이것을 빼면 메모리 속도를 재게
되어 값이 부풀려진다.

측정은 노드 수를 늘려가며 기록한다. 노드를 두 배로 늘렸을 때 총 대역폭이 두 배 가까이 늘면
그 구간까지는 서버가 여유가 있다는 뜻이다. 어느 지점부터 총량이 늘지 않으면 거기가 서버 쪽
상한이고, 그 이상 노드를 붙여도 각자 몫만 줄어든다.

## 학습 워크로드에서 자주 겪는 일

| 증상 | 확인할 것 | 대개의 원인 |
| --- | --- | --- |
| 첫 에폭만 느리다 | 페이지 캐시 적중률 | 정상이다. 데이터가 메모리보다 크면 계속 느리다 |
| GPU 사용률이 톱니처럼 오르내린다 | 데이터 로더 워커 수, 샤드 크기 | 읽기가 계산을 못 따라간다 |
| 체크포인트 때마다 멈춘다 | 저장 방식과 간격 | 동기 저장으로 전체가 대기한다 |
| 특정 랭크만 느리다 | 그 노드의 마운트와 LNet | 노드 개별 문제 |
| 파일 목록 조회가 오래 걸린다 | 디렉터리당 파일 수 | 메타데이터 부하 |
| 용량이 갑자기 찬다 | 체크포인트 보존 개수 | 오래된 체크포인트가 쌓였다 |

증상만으로 원인을 정하지 말고 순서대로 좁힌다. 스토리지 문제인지 아닌지부터 가른 뒤 안으로
들어간다.

```bash
# 1. 스토리지가 문제인지부터 가린다. 데이터를 로컬에서 읽어 같은 학습을 짧게 돌린다
srun -N1 --gres=gpu:8 python train.py --data /local/nvme/data --max-steps 50

# 2. 스토리지 쪽이라면 대역폭인지 메타데이터인지 가린다
lfs df -h                                   # OST 사용률 편중
lctl get_param mdc.*.stats | grep -E 'open|getattr'
lctl get_param llite.*.stats | grep -E 'read_bytes|write_bytes'

# 3. 특정 노드만 느린지 확인한다. 같은 파일을 노드마다 읽어 비교한다
srun -N8 --ntasks-per-node=1 bash -c \
  'echo -n "$(hostname) "; dd if=/scratch/dataset/shard-000.tar of=/dev/null bs=1M count=4096 2>&1 | tail -1'
```

1번에서 빨라지면 공유 스토리지가 원인이고, 그대로면 스토리지가 아니라 계산이나 통신 쪽이다.
이 한 번의 비교로 조사 범위가 절반으로 준다.

데이터 로더가 얼마나 기다리는지는 학습 코드에서 직접 재는 편이 정확하다. 배치를 꺼내는 데
걸린 시간을 스텝 시간과 함께 남기면 읽기가 계산을 따라오는지 바로 보인다.

```python
import time

wait = 0.0
tick = time.perf_counter()
for batch in loader:
    wait += time.perf_counter() - tick        # 배치를 기다린 시간
    train_step(batch)
    tick = time.perf_counter()

print(f"데이터 대기가 전체의 {wait / total * 100:.1f}%")
```

이 값이 10퍼센트를 넘으면 읽기 쪽을 손볼 값어치가 있다. 워커 수를 늘리고, 샤드를 키우고,
반복해 읽는 데이터는 로컬 NVMe로 내린다. 5퍼센트 아래면 스토리지를 더 손봐도 학습 속도는
거의 그대로다.
