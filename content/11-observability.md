노드 수백 대에서 무슨 일이 벌어지는지 사람이 하나씩 열어 보는 방식은 오래가지 못한다. 지표와
로그를 한곳에 모아 두고, 문제가 사용자 문의로 올라오기 전에 화면과 알림으로 잡아내는 구조를
짜는 것이 이 모듈이다. 03의 모니터링 절이 뼈대라면, 여기서는 무엇을 어떻게 모으고 어디서
끊어 볼지까지 내려간다.

## 지표와 로그와 추적

관측의 재료는 세 갈래다. 셋은 답하는 질문이 서로 다르고, 하나로 나머지를 대신하지 못한다.

지표(metric)는 시간에 따라 찍히는 수치다. GPU 사용률 87퍼센트, 온도 72도, 대기 작업 40개처럼
숫자 하나가 일정 주기로 쌓인다. "얼마나", "몇 번", "지금 어느 수준인가"에 답한다. 값이 작고
규칙적이라 오래 보관해도 부담이 적고, 합치고 평균 내고 비율을 내기 좋다. 추세와 이상의 조짐을
보는 데 쓴다.

로그(log)는 그 순간 무슨 일이 있었는지를 문장으로 남긴 기록이다. `slurmd`가 노드를 잃었다는
줄, 커널이 찍은 Xid 줄, 학습 스크립트가 뱉은 스택 트레이스가 로그다. "그때 정확히 무슨 일이
났는가"에 답한다. 지표가 "72도에서 갑자기 튀었다"까지 보여주면, 그 시각의 로그가 "전력 상한에
걸려 클럭을 낮췄다"는 이유를 준다. 지표로 이상을 찾고 로그로 원인을 확인하는 순서가 기본이다.

추적(trace)은 요청 하나가 여러 구성 요소를 거치며 어디서 시간을 썼는지 잇는 기록이다. 웹
서비스에서는 핵심이지만, 배치 학습 위주의 GPU 클러스터에서는 비중이 낮다. 다만 추론 서빙이나
데이터 파이프라인이 여러 단계를 거친다면 단계별 지연을 잇는 용도로 쓸모가 있다. 학습 작업의
스텝 시간 분해도 넓은 의미의 추적에 든다.

무엇을 모을지는 질문에서 거꾸로 정한다. "이 카드가 정상인가", "이 학습이 자원을 쓰고 있는가",
"자원을 더 사야 하는가"에 답하는 지표는 모은다. 답할 질문이 없는 지표는 모으지 않는다. 특히
초 단위로 찍히는 세밀한 커널 프로파일이나 모든 함수 호출 기록은 저장 비용이 크고 평소에는 볼
일이 없어, 필요할 때 해당 작업에서만 켜는 편이 낫다. 상시 수집은 넓고 성기게, 심층 수집은
좁고 촘촘하게 가른다.

| 재료 | 답하는 질문 | GPU 클러스터에서의 쓸모 | 보관 성향 |
| --- | --- | --- | --- |
| 지표 | 얼마나, 몇 번, 어느 수준 | 사용률·온도·대기열 추세, 이상 조짐 | 길게, 싸게 |
| 로그 | 그때 무슨 일이 났는가 | Xid, 노드 다운, 작업 실패 원인 | 중간, 라벨 최소로 |
| 추적 | 어디서 시간을 썼는가 | 서빙·파이프라인 단계별 지연 | 짧게, 표본만 |

세 재료를 하나의 축으로 잇는 열쇠가 작업 번호다. 지표에도 로그에도 작업 번호가 붙어 있으면,
느린 학습 하나를 잡고 그 작업의 GPU 사용률과 그 작업이 남긴 로그를 바로 오갈 수 있다. 이
연결을 처음부터 설계에 넣는 것이 관측 체계의 값을 좌우한다.

세 재료를 한 규약으로 다루려는 표준이 OpenTelemetry다. 계측 방식과 전송 형식을 정해 두고,
수집기가 받아서 원하는 저장소로 나눠 보낸다. GPU 클러스터에서 당장 필요한 물건은 아니지만,
추론 서빙이나 데이터 파이프라인처럼 여러 단계를 거치는 워크로드를 함께 운영한다면 값어치가
나온다. 학습 쪽 지표는 이미 각 수집기가 프로메테우스 형식으로 내보내므로 그대로 두고, 새로
붙이는 서비스 계층에만 적용하는 식으로 나눠 쓰는 구성이 무난하다.

```yaml
# 수집기 하나가 여러 형식을 받아 각각의 저장소로 보낸다
receivers:
  otlp:
    protocols: { grpc: { endpoint: 0.0.0.0:4317 } }
  prometheus:
    config:
      scrape_configs:
        - job_name: dcgm
          static_configs: [{ targets: ["gpu07:9400"] }]

exporters:
  prometheusremotewrite:
    endpoint: http://prometheus:9090/api/v1/write
  otlphttp/logs:
    endpoint: http://loki:3100/otlp

service:
  pipelines:
    metrics: { receivers: [otlp, prometheus], exporters: [prometheusremotewrite] }
    logs: { receivers: [otlp], exporters: [otlphttp/logs] }
```

층을 하나 더 두는 만큼 장애가 났을 때 확인할 곳도 하나 늘어난다. 수집기가 죽으면 지표가 통째로
비므로, 수집기 자신의 상태도 감시 대상에 넣는다.

## 무엇을 모을 것인가

클러스터는 여러 층으로 쌓여 있고, 층마다 봐야 할 지표와 적당한 수집 주기가 다르다. 빠르게
변하는 값은 촘촘하게, 느리게 변하는 값은 성기게 찍는다. 온도는 초 단위로 튀지 않으니 10초면
충분하고, 대기열 길이는 15초면 되지만, GPU 사용률은 짧은 스파이크를 놓치지 않으려면 5초가
낫다. 주기를 줄일수록 저장 용량과 수집 부하가 함께 는다.

| 층 | 대표 지표 | 수집 주기 | 무엇을 보는가 |
| --- | --- | --- | --- |
| 노드 | CPU·메모리·부하·디스크 여유 | 15초 | 서버가 건강한가 |
| GPU | 사용률·메모리·온도·전력·Xid | 5~10초 | 카드가 일을 하는가 |
| 스케줄러 | 대기 작업·상태별 노드·대기 시간 | 15초 | 대기열이 흐르는가 |
| 파일시스템 | 용량·inode·메타데이터 지연 | 30초 | 저장이 막히는가 |
| 네트워크 | 링크 오류·드롭·대역폭 | 15초 | 통신이 성한가 |
| 학습 작업 | 스텝 시간·처리량·손실 | 작업이 정함 | 학습이 도는가 |

학습 작업 지표는 결이 다르다. 스텝 시간이나 처리량은 클러스터가 밖에서 재기 어렵고, 학습
코드가 스스로 내보내는 값이라 사용자에게 맡긴다. 클러스터는 GPU 사용률로 간접 추정하고,
정밀한 값은 작업이 푸시게이트웨이나 자체 exporter로 올린 것을 받는다.

층을 나누는 이유는 카디널리티(cardinality) 때문이다. 카디널리티는 라벨 조합의 가짓수다.
프로메테우스는 라벨 조합 하나하나를 별도 시계열로 저장하므로, 조합이 폭발하면 메모리와 저장이
같이 터진다. 노드 200대에 지표 종류 50개면 시계열 1만 개로 감당할 만하지만, 여기에 값이 계속
바뀌는 라벨을 붙이면 순식간에 수백만 개로 늘어난다.

라벨로 붙이면 안 되는 값은 정해져 있다.

| 위험한 라벨 | 왜 터지는가 | 대안 |
| --- | --- | --- |
| 작업 번호 전부 | 하루 수만 개가 영원히 쌓인다 | 실행 중 작업만, 끝나면 시계열 소멸 |
| 사용자별 요청 ID | 무한히 늘어난다 | 로그에만 남긴다 |
| 타임스탬프·에폭 | 매 순간 새 값 | 절대 라벨로 쓰지 않는다 |
| 파일 경로 | 경로 수만큼 폭발 | 상위 디렉터리로 묶는다 |

작업 번호는 미묘하다. 실행 중인 작업에만 라벨을 붙이고 작업이 끝나면 exporter가 그 시계열을
더 내보내지 않게 하면, 프로메테우스가 일정 시간 뒤 그 시계열을 정리한다. 이렇게 하면 동시에
도는 수백 개의 작업만 라벨로 유지되어 카디널리티가 유계로 묶인다. 끝난 작업까지 영구히 라벨로
남기면 안 되고, 과거 작업의 자원 사용은 스케줄러 회계(`sacct`)나 로그에서 따로 뽑는다.

## 수집 스택 구성

프로메테우스는 당겨오는(pull) 방식이다. 각 노드가 지표를 밖으로 밀어 보내는 대신, 노드마다
`/metrics` 경로로 현재 값을 노출하고 프로메테우스 서버가 주기적으로 긁어 간다. 긁는 쪽이
목록을 쥐고 있어, 어떤 노드가 응답을 안 하면 그 사실 자체가 신호가 된다. 밀어 보내는 방식은
노드가 죽으면 조용해질 뿐이라 죽음을 구별하기 어렵다.

![노드와 GPU와 스케줄러의 지표는 프로메테우스로, 로그는 로키로 모여 대시보드와 알림이 같은 저장소를 본다](img/observability-stack.svg)

수집기(exporter)는 노드에 둔다. `node_exporter`는 CPU·메모리·디스크·네트워크를 내보내고,
DCGM exporter는 GPU를, Slurm exporter는 스케줄러 상태를 내보낸다. 앞의 둘은 모든 노드에 두고,
Slurm exporter는 스케줄러가 도는 관리 노드 한 곳에 둔다. 스케줄러 상태는 클러스터 전체에 하나뿐
이라 노드마다 둘 이유가 없다.

```yaml
# prometheus.yml
global:
  scrape_interval: 15s
  scrape_timeout: 10s

scrape_configs:
  - job_name: node
    scrape_interval: 15s
    static_configs:
      - targets: ['gpu01:9100', 'gpu02:9100', 'gpu03:9100']

  - job_name: dcgm
    scrape_interval: 10s
    static_configs:
      - targets: ['gpu01:9400', 'gpu02:9400', 'gpu03:9400']

  - job_name: slurm
    scrape_interval: 15s
    static_configs:
      - targets: ['mgmt01:8080']
```

노드가 수백 대면 `static_configs`에 손으로 적는 대신 파일 기반 탐색을 쓴다. 노드 목록을 파일로
두고 프로메테우스가 그 파일을 다시 읽게 하면, 노드를 넣고 뺄 때 설정을 재시작하지 않아도 된다.

```yaml
  - job_name: dcgm
    file_sd_configs:
      - files: ['/etc/prometheus/targets/dcgm/*.yml']
        refresh_interval: 1m
    relabel_configs:
      - source_labels: [__address__]
        regex: '([^:]+):.*'
        target_label: node
        replacement: '$1'
```

저장 용량은 곱셈으로 어림한다. 필요한 저장은 대략 시계열 개수 × (보존 기간 ÷ 수집 주기) ×
표본당 바이트다. 프로메테우스는 표본 하나를 압축 후 평균 1~2바이트로 저장한다. 시계열 100만
개를 15초 주기로 30일 보관하면, 100만 × (30일 ÷ 15초) × 2바이트로 약 345GB가 나온다.

| 항목 | 값 | 계산 |
| --- | --- | --- |
| 시계열 개수 | 1,000,000 | 노드 × 지표 종류 × 라벨 조합 |
| 초당 표본 | 66,667 | 1,000,000 ÷ 15초 |
| 30일 표본 수 | 1,728억 | 66,667 × 2,592,000초 |
| 저장 용량 | 약 345GB | 표본당 2바이트 |

로컬 디스크로 30일이면 위 정도지만, 1년치 추세를 보려면 로컬 저장으로는 감당이 안 된다. 이때
원격 저장(remote write)으로 넘긴다. 프로메테우스가 긁은 지표를 Thanos나 Mimir 같은 장기 저장소로
계속 흘려보내면, 로컬은 최근 며칠만 쥐고 오래된 것은 객체 저장소에서 값싸게 보관한다.

```yaml
remote_write:
  - url: http://mimir:9009/api/v1/push
    queue_config:
      max_samples_per_send: 5000
      capacity: 20000
```

원격 저장으로 넘길 때는 전부 넘기지 말고 오래 볼 지표만 규칙으로 골라 넘긴다. 초 단위 세밀
지표까지 1년 보관하면 저장소가 커지므로, 장기 보관은 사용률·전력·대기열처럼 추세가 의미 있는
것으로 좁힌다.

## GPU 지표 수집

GPU 지표는 DCGM exporter가 맡는다. 배포 방식은 호스트에 직접 데몬으로 두는 방식과 컨테이너로
띄우는 방식 둘 다 된다. 베어메탈 노드가 고정돼 있으면 데몬이 단순하고, 쿠버네티스로 GPU를
관리하면 데몬셋 컨테이너가 맞는다.

호스트에 데몬으로 두는 경우, `nv-hostengine`이 뜬 상태에서 exporter를 서비스로 등록한다.

```bash
# 호스트 배포
systemctl enable --now nvidia-dcgm          # DCGM 호스트 엔진
dcgm-exporter -f /etc/dcgm-exporter/counters.csv &
curl -s localhost:9400/metrics | grep DCGM_FI_DEV_GPU_UTIL
```

컨테이너로 띄우는 경우, GPU 드라이버를 컨테이너 안으로 넣어야 하므로 `--gpus all`과 함께
호스트 PID 네임스페이스를 공유한다.

```bash
# 컨테이너 배포
docker run -d --gpus all --rm -p 9400:9400 \
  --cap-add SYS_ADMIN \
  -v /etc/dcgm-exporter/counters.csv:/etc/dcgm-exporter/default-counters.csv \
  nvcr.io/nvidia/k8s/dcgm-exporter:latest
```

무엇을 수집할지는 필드 선택 파일로 고른다. 기본값은 필드가 많아 카디널리티를 키우므로, 실제로
보는 필드만 남긴다. 파일은 필드 이름과 지표 종류, 설명을 한 줄씩 적는다.

```csv
# counters.csv
DCGM_FI_DEV_GPU_UTIL,        gauge, GPU 사용률(%)
DCGM_FI_DEV_MEM_COPY_UTIL,   gauge, 메모리 복사 사용률(%)
DCGM_FI_PROF_SM_ACTIVE,      gauge, SM 점유율(0~1)
DCGM_FI_DEV_FB_USED,         gauge, 프레임버퍼 사용(MiB)
DCGM_FI_DEV_FB_FREE,         gauge, 프레임버퍼 여유(MiB)
DCGM_FI_DEV_GPU_TEMP,        gauge, GPU 온도(C)
DCGM_FI_DEV_POWER_USAGE,     gauge, 전력(W)
DCGM_FI_DEV_ECC_DBE_VOL_TOTAL, counter, 정정 불가 ECC 누적
DCGM_FI_DEV_XID_ERRORS,      gauge, 최근 Xid 코드
DCGM_FI_DEV_CLOCK_THROTTLE_REASONS, gauge, 스로틀 사유 비트마스크
```

각 필드가 답하는 질문이 다르다. `DCGM_FI_DEV_GPU_UTIL`은 커널이 돈 시간 비율이라 "이 카드가
할당만 받고 놀고 있는가"를 잡고, `DCGM_FI_PROF_SM_ACTIVE`는 SM 점유율이라 "돌긴 도는데 실제로
연산 유닛이 차 있는가"까지 내려간다. 사용률이 100인데 SM 점유가 낮으면 커널이 성기게 도는
것이다. `DCGM_FI_DEV_FB_USED`는 OOM을 예측하고, `DCGM_FI_DEV_GPU_TEMP`와
`DCGM_FI_DEV_POWER_USAGE`는 스로틀의 원인을 가른다. `DCGM_FI_DEV_XID_ERRORS`와 ECC 카운터는
하드웨어 장애의 조기 신호이며, `DCGM_FI_DEV_CLOCK_THROTTLE_REASONS`는 클럭이 왜 낮은지를 비트로
알려준다.

| 필드 | 답하는 질문 |
| --- | --- |
| `DCGM_FI_DEV_GPU_UTIL` | 카드가 일을 하는가, 놀고 있는가 |
| `DCGM_FI_PROF_SM_ACTIVE` | 연산 유닛이 실제로 차 있는가 |
| `DCGM_FI_DEV_FB_USED` | 메모리가 곧 넘치는가 |
| `DCGM_FI_DEV_GPU_TEMP` | 열로 스로틀에 걸릴 상태인가 |
| `DCGM_FI_DEV_POWER_USAGE` | 전력 상한에 붙어 있는가 |
| `DCGM_FI_DEV_XID_ERRORS` | 방금 GPU 오류가 났는가 |

지표에 작업 번호와 사용자 라벨을 붙이면 카드 하나의 값을 학습 하나로 묶을 수 있다. DCGM
exporter는 HPC 작업 매핑 디렉터리를 읽어 각 GPU가 지금 어느 작업에 배정됐는지 라벨로 붙인다.
Slurm 프롤로그에서 배정 정보를 그 디렉터리에 적고, 에필로그에서 지운다.

```bash
# prolog: 이 노드에서 이 작업이 쓰는 GPU를 매핑 파일에 적는다
for g in $(echo $CUDA_VISIBLE_DEVICES | tr ',' ' '); do
  echo "$SLURM_JOB_ID" > /var/run/dcgm/job_$g
done
```

라벨이 붙으면 작업 단위 집계가 된다. `avg by (hpc_job) (DCGM_FI_DEV_GPU_UTIL)`로 작업별 평균
사용률을 내고, 그것이 낮으면 그 학습이 GPU 밖에서 막혀 있다는 뜻이다. 라벨이 없으면 노드
평균밖에 못 내, 한 노드에서 여러 작업이 섞여 돌 때 누가 놀고 있는지 가릴 수 없다.

## 스케줄러 지표 수집

GPU 지표가 "카드가 도는가"라면 스케줄러 지표는 "대기열이 흐르는가"에 답한다. Slurm exporter는
관리 노드에서 `squeue`, `sinfo`, `sdiag`를 주기적으로 읽어 프로메테우스 형식으로 내보낸다.

| 지표 | 뜻 |
| --- | --- |
| `slurm_queue_pending` | 대기 중인 작업 수 |
| `slurm_queue_running` | 실행 중인 작업 수 |
| `slurm_nodes_idle` | 비어 있는 노드 수 |
| `slurm_nodes_alloc` | 배정된 노드 수 |
| `slurm_nodes_down` | 죽은 노드 수 |
| `slurm_partition_gpus_alloc` | 파티션별 배정된 GPU 수 |

이 값으로 대기열 건강을 본다. 대기 작업이 계속 늘고 유휴 노드는 0이면 자원이 부족한 것이고,
대기 작업이 쌓였는데 유휴 노드가 남아 있으면 스케줄러 설정이나 자원 요청 조건이 잘못돼 배정이
안 되는 것이다. 후자는 자원을 더 사도 해결되지 않으므로 구별이 중요하다.

```promql
# 파티션별 대기 작업이 30분 넘게 50개 이상인가
slurm_queue_pending{partition="gpu"} > 50

# 유휴 GPU가 있는데 대기 작업이 쌓여 있는가
(slurm_nodes_idle > 0) and (slurm_queue_pending > 20)
```

exporter가 안 내보내는 값은 `sacct`에서 직접 뽑아 보조 지표로 만든다. 대기 시간, 작업별 GPU
점유 시간, 종료 코드 분포 같은 회계성 값이 여기 든다. 짧은 배치로 뽑아 푸시게이트웨이에 올리면
프로메테우스가 긁어 간다.

```bash
# 최근 한 시간에 끝난 작업의 대기 시간(제출~시작)을 초로 뽑는다
sacct -a -S "$(date -d '1 hour ago' +%FT%T)" -X \
  -o JobID,Submit,Start,State,ExitCode --parsable2 --noheader
```

GPU 지표와 스케줄러 지표는 작업 번호로 잇는다. DCGM 지표에 `hpc_job` 라벨이 있고 스케줄러
쪽에도 작업 번호가 있으면, 대기가 긴 작업 하나를 잡고 그 작업이 배정받은 GPU의 사용률을 바로
겹쳐 볼 수 있다. 대기는 길었는데 막상 사용률이 낮다면, 그 학습은 자원을 오래 기다려 잡고도
제대로 못 쓰는 것이라 자원 요청을 재검토할 근거가 된다.

```promql
# 작업 12345가 잡은 GPU들의 평균 사용률
avg(DCGM_FI_DEV_GPU_UTIL{hpc_job="12345"})
```

## 로그 수집

로그는 Loki로 모은다. 프로메테우스가 지표를 라벨로 색인하듯, Loki도 로그 줄 전체를 색인하지
않고 라벨만 색인한다. 라벨을 최소로 두고 본문은 압축해 저장하므로 저장이 싸고, 대신 검색은
라벨로 먼저 좁힌 뒤 본문을 훑는 식이다. 수집 에이전트는 promtail이 맡아 각 노드의 로그 파일을
읽어 Loki로 밀어 보낸다.

```yaml
# promtail-config.yml
clients:
  - url: http://loki:3100/loki/api/v1/push

scrape_configs:
  - job_name: slurm
    static_configs:
      - targets: [localhost]
        labels:
          job: slurmd
          host: gpu01
          __path__: /var/log/slurm/slurmd.log
  - job_name: kernel
    journal:
      matches: _TRANSPORT=kernel
      labels:
        job: kernel
        host: gpu01
```

무엇을 모을지는 조사에 실제로 쓰는 것으로 좁힌다. 관리 노드의 `slurmctld`는 스케줄링 결정과
작업 실패를, 계산 노드의 `slurmd`는 작업 시작과 종료를, `dmesg`와 커널 저널은 Xid와 하드웨어
오류를, 작업 stdout은 학습 코드의 예외를 남긴다. 넷이면 GPU 클러스터 조사의 대부분을 덮는다.

| 로그원 | 어디에 | 무엇을 잡는가 |
| --- | --- | --- |
| `slurmctld` | 관리 노드 | 스케줄링 결정, 작업 거절 |
| `slurmd` | 계산 노드 | 작업 시작·종료, 프롤로그 실패 |
| `dmesg`·커널 | 계산 노드 | Xid, ECC, PCIe, OOM 킬 |
| 작업 stdout | 스크래치 | 학습 예외, 스택 트레이스 |

로그 라벨 설계에서 카디널리티 함정은 지표와 똑같다. 라벨에 작업 번호나 요청 ID, 컨테이너
해시를 넣으면 라벨 조합이 폭발해 Loki 색인이 무너진다. 이런 값은 라벨이 아니라 로그 본문에
남기고, 검색은 본문 필터로 한다. 라벨은 `job`, `host`, `partition`처럼 값의 가짓수가 유계인
것만 둔다.

```logql
# 라벨로 좁히고 본문에서 작업 번호를 찾는다
{job="slurmd", host="gpu07"} |= "12345"

# 커널 로그에서 최근 Xid만
{job="kernel"} |= "Xid" | logfmt
```

지표와 로그를 오가는 축도 작업 번호다. 대시보드에서 사용률이 떨어진 작업 하나를 잡으면, 그
작업의 GPU 지표 옆에 같은 작업 번호로 필터한 로그를 붙여 둔다. Grafana에서 지표 패널의 시간
구간을 그대로 Loki 질의에 넘기면, 사용률이 꺼진 그 순간의 `slurmd` 로그와 커널 로그가 같은
화면에 뜬다. 이렇게 이어 두면 "사용률이 왜 떨어졌나"에서 "그 시각 커널이 Xid를 찍었다"까지
클릭 몇 번으로 내려간다.

## 대시보드 설계

한 화면에 모든 지표를 올리면 아무도 안 보게 된다. 패널이 마흔 개면 어느 것이 평소와 다른지
눈에 안 들어오고, 다들 화면을 열었다가 닫는다. 보는 사람과 목적에 따라 화면을 나누는 것이
기본이다. 같은 지표라도 운영자와 사용자와 장애 대응자는 다른 각도로 본다.

운영자용 화면은 클러스터 전체가 성한지 한눈에 보는 데 목적이 있다. 개별 카드가 아니라 집계와
비율, 그리고 평소와 다른 것만 도드라지게 둔다.

| 패널 | 지표 |
| --- | --- |
| 파티션별 유휴·배정·다운 노드 | `slurm_nodes_*` |
| 클러스터 전체 GPU 사용률 분포 | `DCGM_FI_DEV_GPU_UTIL` 히스토그램 |
| 대기 작업 수와 대기 시간 추세 | `slurm_queue_pending`, `sacct` 보조 |
| 최근 Xid·ECC 발생 노드 목록 | `DCGM_FI_DEV_XID_ERRORS`, ECC 카운터 |
| 스토리지 사용률 상위 파일시스템 | `node_filesystem_avail_bytes` |

사용자용 화면은 "내 작업이 잘 돌고 있는가"에만 답한다. 작업 번호로 필터해 그 작업이 잡은
GPU만 보여주고, 클러스터 전체 상태는 감춘다. 사용자는 남의 노드에 관심이 없고, 자기 학습의
사용률과 메모리와 스텝 시간만 본다.

```promql
# 사용자용 패널: 선택한 작업의 GPU별 사용률
DCGM_FI_DEV_GPU_UTIL{hpc_job="$job"}

# 같은 작업의 메모리 사용 비율
DCGM_FI_DEV_FB_USED{hpc_job="$job"}
  / (DCGM_FI_DEV_FB_USED{hpc_job="$job"} + DCGM_FI_DEV_FB_FREE{hpc_job="$job"})
```

장애 대응용 화면은 노드 한 대에 집중한다. 의심 노드 하나를 고르면 그 노드의 GPU 8장, PCIe,
NVLink, 온도, 전력, 그리고 그 노드의 커널 로그가 한 화면에 뜬다. 조사하는 사람은 이 노드에서
무슨 일이 나는지만 보면 되므로, 전체 집계는 방해가 된다.

| 화면 | 보는 사람 | 핵심 질문 |
| --- | --- | --- |
| 전체 상태 | 운영자 | 클러스터가 성한가 |
| 내 작업 | 사용자 | 내 학습이 도는가 |
| 단일 노드 | 장애 대응자 | 이 노드가 왜 이상한가 |

화면을 나눌 때 변수(variable)를 쓰면 하나의 대시보드로 여러 대상을 본다. 노드 이름이나 작업
번호를 드롭다운 변수로 두고 패널 질의에 `$node`, `$job`으로 끼워 넣으면, 노드마다 대시보드를
복제하지 않아도 된다. 대시보드는 적게, 변수로 대상만 바꾸는 구조가 유지비가 낮다.

## 알림 설계

알림은 사람이 지금 당장 뭔가 해야 하는 것만 건다. 대시보드를 열면 보이는 것과 새벽에 사람을
깨우는 것은 기준이 다르다. 노드 다운, 정정 불가 ECC, 스토리지 포화처럼 방치하면 피해가 커지는
것만 알림으로 두고, 사용률이 낮다거나 대기가 조금 길다는 것은 화면에만 둔다.

임계값은 절대값이 아니라 자기 클러스터 기준으로 정한다. "온도 80도"라는 숫자는 카드 세대와
냉각 설계에 따라 정상일 수도 위험일 수도 있다. 평소 이 클러스터에서 부하 중 온도가 70도 근처면
85도가 이상이고, 평소 78도면 85도는 흔한 값이다. 남의 숫자를 그대로 가져오면 잘못된 알림이
쏟아진다. 며칠간 기록한 평소 분포에서 위쪽 꼬리를 임계로 잡는다.

순간 스파이크를 거르는 것이 `for` 절이다. 조건이 참이 되자마자 울리면, 잠깐 튀었다 돌아오는
값에도 매번 깨어난다. `for: 10m`을 붙이면 조건이 10분 내내 참일 때만 울려, 일시적 스파이크가
걸러진다.

```yaml
# alert-rules.yml
groups:
  - name: gpu
    rules:
      - alert: GPUOverTemp
        expr: DCGM_FI_DEV_GPU_TEMP > 85
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.node }} GPU {{ $labels.gpu }} 온도 {{ $value }}C"

      - alert: NodeDown
        expr: up{job="dcgm"} == 0
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }} DCGM 수집 중단"

      - alert: UncorrectableECC
        expr: increase(DCGM_FI_DEV_ECC_DBE_VOL_TOTAL[10m]) > 0
        for: 0m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.node }} 정정 불가 ECC 발생"
```

정정 불가 ECC처럼 한 번이라도 나면 바로 봐야 하는 것은 `for: 0m`으로 즉시 울리고, 온도처럼
잠깐 튈 수 있는 것은 지속 시간을 준다. 심각도를 나눠 critical은 사람을 깨우고 warning은 채널에만
남기면, 밤중 호출이 준다.

알림 피로는 대개 같은 실수에서 온다.

| 실수 | 결과 | 고침 |
| --- | --- | --- |
| 화면에 둘 것을 알림으로 | 울림이 잦아 무시하게 됨 | 행동이 필요한 것만 알림 |
| `for` 절 없이 순간값 | 스파이크마다 깨어남 | 지속 시간을 준다 |
| 노드마다 같은 알림 | 한 원인에 수십 통 | 라벨로 묶어 한 통으로 |
| 남의 임계값 복사 | 오탐·미탐 동시에 | 자기 분포에서 잡음 |

한 원인이 여러 알림을 낳는 것도 묶는다. 스위치 하나가 죽어 노드 20대가 동시에 다운되면 알림
20통이 아니라 한 통이 와야 한다. 알림 매니저에서 같은 원인의 알림을 묶고, 반복은 억제하고,
정비 중인 노드는 잠재운다.

## 정상 상태를 먼저 정의하기

이상을 잡으려면 정상이 무엇인지 알아야 한다. 평소 값을 모른 채 임계값을 걸면, 정상인데 울리거나
이상인데 조용하다. 정상 상태는 감으로 두지 말고 숫자로 기록한다. 며칠에서 몇 주간 부하 중과
유휴 시의 사용률·온도·전력·스텝 시간 분포를 재서, 각 지표가 평소 어느 구간에 있는지를 기준선
(baseline)으로 남긴다.

정상은 하나의 값이 아니라 상황에 따라 다른 여러 값이다. 계절성(seasonality)을 무시하면 안 된다.
클러스터는 요일과 시간대에 따라 부하가 다르다. 논문 마감 전 주말에는 대기열이 꽉 차고, 평일
새벽에는 유휴 노드가 는다. 이 리듬을 모르고 "대기 작업 100개 이상이면 이상"으로 걸면 마감 주에
알림이 쏟아지고, "유휴 노드 50대 이상이면 이상"으로 걸면 새벽마다 울린다. 기준선은 요일별,
시간대별로 따로 잡는다.

절대 임계값이 아예 통하지 않는 지표도 있다. 스텝 시간은 모델과 배치 크기에 따라 절대값이
제각각이라, "스텝 500밀리초 이상이면 느림"이라는 고정선이 무의미하다. 이런 지표는 같은 작업
안에서의 상대 변화로 본다. 이 학습의 스텝 시간이 처음 안정 구간 대비 20퍼센트 늘었는가처럼,
자기 자신을 기준으로 잰다.

```promql
# 이 작업의 현재 사용률이 지난 1시간 중앙값보다 크게 낮아졌는가
DCGM_FI_DEV_GPU_UTIL{hpc_job="$job"}
  < 0.6 * quantile_over_time(0.5, DCGM_FI_DEV_GPU_UTIL{hpc_job="$job"}[1h])
```

통계 기반 이탈 탐지에는 한계가 뚜렷하다. 평균에서 표준편차 몇 배를 벗어나면 이상으로 보는
방식은, 분포가 한쪽으로 쏠려 있거나 정상 자체가 여러 봉우리를 가지면 오탐을 낸다. GPU 사용률은
0 근처와 100 근처에 몰리는 두 봉우리 분포라, 단순 평균·표준편차로는 정상과 이상을 못 가른다.
이런 지표는 분위수로 보거나 상태를 나눠 따로 본다.

| 지표 | 정상의 모양 | 맞는 판정법 |
| --- | --- | --- |
| GPU 사용률 | 0과 100에 몰린 두 봉우리 | 상태를 나눠 각각 분위수 |
| 온도 | 부하 중 한 봉우리 | 자기 분포의 상위 꼬리 |
| 스텝 시간 | 작업마다 다름 | 자기 기준 상대 변화 |
| 대기 작업 | 요일·시간대에 따라 | 계절성 반영 기준선 |

자동 탐지에 기대기 전에 갖출 것이 있다. 라벨이 제대로 붙어 있고, 기준선이 기록돼 있고, 정상의
계절성이 파악돼 있어야 자동 탐지가 쓸모를 낸다. 이것 없이 이상 탐지 알고리즘부터 얹으면 오탐의
바다에 빠진다. 그리고 자동 탐지가 무언가를 짚어도 마지막 판단은 사람이 한다. 통계가 "이 노드가
다르다"까지 좁혀 주면, 그것이 진짜 장애인지 정상적인 다른 작업인지는 로그와 맥락을 보고 사람이
정한다. 08의 노드 좁히기 절차가 그 판단의 순서를 잇는다.

## 병목이 어디인지 좁히기

학습이 느릴 때 원인은 크게 셋이다. 계산이 느리거나, GPU 사이 또는 노드 사이 통신이 막히거나,
데이터를 읽어 오는 저장이 막힌 것이다. 지표만으로도 셋 중 어디인지 상당히 좁힐 수 있다. 노드에
들어가기 전에 화면에서 방향을 잡는 절차다.

첫 갈림은 GPU가 일을 하고 있는가다. `DCGM_FI_DEV_GPU_UTIL`이 높고 `DCGM_FI_PROF_SM_ACTIVE`도
높으면 GPU가 실제로 연산에 차 있는 것이라, 병목은 계산 자체다. 이때는 모델이 크거나 커널이
비효율적인 것이라 저장이나 통신이 아니다. 반대로 사용률이 낮게 오르내리면 GPU가 무언가를
기다리는 것이라 계산 밖을 본다.

사용률이 규칙적으로 떨어졌다 오르는지, 아니면 계속 낮게 깔리는지가 다음 갈림이다. 규칙적으로
스텝마다 뚝 떨어지면 통신 대기를 의심한다. 올리듀스로 가중치를 주고받는 동안 GPU가 쉬기 때문
이다. 이때 NVLink나 InfiniBand 지표를 겹쳐 본다. 사용률이 계속 낮게 깔리고 그 사이 CPU와
디스크가 바쁘면 데이터 로딩이 병목이다.

```promql
# GPU는 노는데 노드 디스크가 포화인가 (저장 병목 신호)
(avg by (node) (DCGM_FI_DEV_GPU_UTIL) < 30)
  and (rate(node_disk_io_time_seconds_total[5m]) > 0.9)

# GPU는 노는데 IB 링크 오류가 늘고 있는가 (통신 병목 신호)
(avg by (node) (DCGM_FI_DEV_GPU_UTIL) < 30)
  and (rate(node_infiniband_port_rcv_errors_total[5m]) > 0)
```

판정은 지표 하나가 아니라 조합으로 한다. 한 지표만 보면 오해하기 쉽고, 두세 개를 겹쳐야 방향이
잡힌다.

| 판정 | GPU 사용률 | SM 점유 | 함께 보는 지표 |
| --- | --- | --- | --- |
| 계산 병목 | 높음 | 높음 | 전력이 상한 근처, 클럭 최대 |
| 통신 병목 | 스텝마다 뚝뚝 | 중간 | NVLink 대역폭, IB 오류·대역폭 |
| 저장 병목 | 낮게 깔림 | 낮음 | 디스크 `%util`, CPU I/O 대기 |
| 스로틀 | 높지만 처리량 낮음 | 중간 | 온도·전력 상한, 스로틀 사유 비트 |
| 유휴 | 바닥 | 바닥 | 스케줄러는 배정, 작업은 대기 |

스로틀은 헷갈리기 쉬운 갈래다. 사용률은 높은데 스텝 시간이 늘면, 계산 병목처럼 보이지만 실은
클럭이 낮아진 것일 수 있다. `DCGM_FI_DEV_CLOCK_THROTTLE_REASONS` 비트가 서 있고 온도나 전력이
상한에 붙어 있으면 스로틀이라, 냉각과 전력 문제로 넘어간다. 여기서 좁힌 방향을 08의 하드웨어
점검 절차로 넘겨 노드 안에서 확인한다.

## 장애 리포트 쓰기

장애가 끝나면 무슨 일이 있었는지 남긴다. 기록이 없으면 같은 장애가 반복될 때마다 처음부터
조사하고, 원인을 아는 사람이 자리를 비우면 지식이 사라진다. 리포트는 기억이 아니라 지표와
로그로 쓴다.

리포트에 빠지면 안 되는 항목이 있다. 발생 시각과 복구 시각, 영향 범위, 증상, 확인한 것, 원인,
조치, 재발 방지다. 영향 범위는 몇 명이 몇 시간 동안 무엇을 못 했는지 숫자로 적는다. "느렸다"가
아니라 "노드 12대에서 3시간 동안 학습 47건이 중단됐다"로 적어야 우선순위가 선다.

지표 그래프와 로그를 근거로 붙인다. Grafana 패널은 장애 구간을 고정한 링크로 걸고, 그 순간의
커널 로그와 스케줄러 로그를 발췌해 넣는다. 그래프가 언제 무엇이 튀었는지 보여주고, 로그가 그
순간의 이유를 준다. 시각을 맞춰 나란히 두면 인과가 드러난다.

비난하지 않는 기록이 중요하다. "누가 잘못했다"로 쓰면 다음부터 사람들이 사실을 숨기고, 그러면
진짜 원인이 묻힌다. 사람이 아니라 구조를 본다. 왜 그 실수가 가능했는지, 왜 미리 못 막았는지를
적으면 재발 방지가 나온다. 개인을 지목하는 순간 리포트는 조사 도구가 아니라 처벌 도구가 되고,
아무도 솔직하게 쓰지 않게 된다.

```markdown
# 장애 리포트: gpu07~gpu18 학습 중단

- 발생: 2026-08-14 02:14 KST
- 복구: 2026-08-14 05:31 KST (3시간 17분)
- 영향: gpu 파티션 노드 12대, 학습 47건 중단, 사용자 9명

### 증상
- 02:14부터 gpu07~gpu18에서 DCGM 수집 중단 알림(NodeDown)
- 해당 노드의 학습이 NCCL 통신 타임아웃으로 실패

### 확인한 것
- Grafana: 02:14에 12대 동시 다운 (링크)
- 커널 로그: gpu07 dmesg에 PCIe 링크 다운 없음
- 스위치 로그: leaf-switch-03가 02:13에 재부팅됨
- 12대 모두 leaf-switch-03 하위에 연결

### 원인
- leaf-switch-03의 펌웨어 결함으로 예기치 않은 재부팅
- 재부팅 동안 하위 노드의 IB 링크가 끊겨 NCCL 통신 실패

### 조치
- 스위치 재부팅 후 링크 자동 복구 확인
- 실패한 학습 47건 중 체크포인트 있는 41건 재제출

### 재발 방지
- leaf 스위치 펌웨어를 결함 수정 버전으로 교체 (담당·기한 명시)
- 스위치 재부팅 이벤트를 알림에 추가해 조기 인지
- 단일 leaf 하위 노드에 한 학습을 몰지 않도록 배치 규칙 검토
```

서식을 정해 두면 리포트마다 빠지는 항목이 없고, 나중에 같은 증상을 검색하기도 쉽다. 리포트는
쌓아 두는 것으로 끝이 아니라, 재발 방지 항목이 실제로 반영됐는지 다음 점검에서 확인해야 값을
낸다. 조치가 완료로 닫히지 않은 리포트는 열린 채로 추적한다.
